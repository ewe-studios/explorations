What Resonate Is

Resonate is a durable execution platform built on durable promises and durable functions. A durable promise is a named record with a state, a parameter, a value, and a deadline. A durable task is the executable half of that same row: it is acquired by a worker with a lease and a version, it can be suspended while it waits for other promises, and it is resumed when those promises settle.

The repository is organized as a specification first and implementations second. spec/ holds an executable abstract machine written in Lean 4, a catalogue of 92 properties, a TLA+ model, and trace checkers. Each implementation is held to that machine: the Rust core is compared step for step against an executable oracle, the Postgres server is one SQL file, and the Zig server keeps its whole durable state in an object store. There is no root-level build. Each directory has its own README, build, and tests.

Documentation Goal

A reader must be able to:

  1. State what a durable promise, a durable task, and a schedule are, and how

their states change.

  1. Trace one function invocation from the SDK through the gateway, the server,

the storage engine, the transport, the worker, and back.

  1. Explain how Resonate defers work: how task.suspend registers callbacks,

how settlement resumes a task, and how timeouts fire.

  1. Read the formal specification and understand what the 92 properties claim

and what is proved versus open.

  1. Name every plugin kind, every storage backend, every transport, and every

gateway, and say where each lives in the source.

  1. Explain how the TypeScript SDK implements both execution engines and how the

other four SDKs relate to the protocol.

  1. Compare Resonate with an append-only durable stream, and design a system

that uses both.

  1. Explain how each SDK creates promise and task identifiers, and how the

server validates them.

  1. Explain how each storage backend holds one origin, and compare the write

cost of one transition with SQLite as the baseline.

Quality Requirements

The ten Iron Rules from markdown_engineering/documentation_directive.md apply:

  1. Detailed sections with real source snippets.
  2. Thesis first in every section.
  3. Clear articulation in ASD-STE100 Simplified Technical English.
  4. At least two Mermaid diagrams per document.
  5. Good visual assets: tables, ASCII trees, diagrams.
  6. Generated HTML with the shared build.
  7. Cross-references between documents.
  8. Source path references with line numbers.
  9. At least one Aha moment per document.
  10. Index and previous/next navigation.

Every abbreviation is spelled out at first use. Every number is checked against the source. Every flow diagram is checked against the actual call path.

Expected Outcome

After reading this exploration, a reader can explain Resonate end to end from the formal specification to the Zig object-store server, can operate the server, can write durable functions in any of the five SDKs, and can decide when to use Resonate with an append-only durable stream instead of, or together with, it.
