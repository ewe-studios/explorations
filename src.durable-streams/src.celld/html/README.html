celld: a Workers platform that runs on your machines

celld is a self-hosted implementation of the Cloudflare Workers platform. A Worker is an application program that the runtime runs for each request. A Workers platform is the runtime around that program: the module loader, the network listeners, the bindings to storage and other services, and the Durable Objects. A Durable Object is a named object with one owner at a time, private SQLite storage, and a handler that runs one event at a time. In celld, a fleet of nodes runs Worker modules and Durable Objects. The nodes share one object store bucket. The bucket holds every durable byte. This exploration covers the whole system: the runtime, the Durable Objects, every service, the ownership rules, the security model, the limits, and two comparisons with the Resonate server that stores its state in an Amazon Simple Storage Service (S3) bucket.

The one-page thesis

A celld node is a process that embeds the V8 JavaScript engine. The node owns a set of cells. A cell is one Durable Object instance. A cell has its own SQLite database, one owner node at a time, and one fencing epoch. A facet is a child database that shares the root cell's owner record and its epoch.

A node acknowledges a write only after it holds a durability proof. celld has two proofs, and the operator selects one with CELLD_DURABILITY.

In a fleet proof, the owner sends each committed Lite Transaction (LTX) segment to as many as two other nodes. These nodes are the followers. A fleet proof needs at least one follower. When the owner has one follower, it keeps acknowledging and recruits a second follower when one becomes available. Each recruited follower writes the segment to its own local disk and calls fsync. Only then does the owner acknowledge the write. The owner uploads the segments to the bucket later, in the background. If the owner dies before that upload, the takeover gate uploads the followers' retained copies before the new owner restores the cell.

In a bucket proof, the owner uploads the segment to the bucket and then reads the ownership record once. The upload is the durability point. The read does not prove durability. It shows that no other node has taken the cell, so a paused node cannot acknowledge a write after a network partition.

A node's local disk is never the permanent record. The local SQLite file is a cache that a restore can rebuild. A follower holds a segment only until the owner uploads it. The bucket is the source of truth for every acknowledged write.

A node uses the fleet proof only when at least one other live node can act as a follower. A single-node fleet, or a node whose peers are all unavailable, asks the fleet posture for permission and does not get it. Such a node uses the bucket proof. A change in fleet size does not change a write that is already acknowledged: the proof that covered it remains valid.

Ownership is a record in the bucket, not a message between nodes. A node claims a cell by a conditional write to cells//own.json. The record holds the owner name and a fencing epoch. The epoch is a counter: a new claim takes the highest epoch it read and adds one. The store applies one conditional write and rejects the other claimant, so only one epoch wins. Every log segment lives under cells//ltx/e/. A node log is the set of segments that a node has acknowledged but not yet uploaded. It lives in the node's lease record and under log//.

A node proves that it is alive with a lease at nodes/.json. The lease expires after CELLD_TTL_MS, and the default is 10,000 milliseconds. A peer takes over a cell only after the lease of its owner expires. An acknowledged write is not lost in that takeover. A request that has no acknowledgement can fail or be retried.

A handoff snapshot sits at level 9, the compaction level for complete database snapshots. Level 0 holds the new segments and the epoch-base snapshot. These level numbers are a Litestream convention.

A restore reads the chain of epochs that ends at the current epoch. It walks back through the epochs whose snapshots and segments link together, and it ignores a prefix from an epoch outside that chain. A node that loses its lease can continue to append under its old prefix, but no restore reads that prefix, so the database is not corrupted. The node must still stop acknowledging clients. It watches the expiry that it published. When that expiry passes, it fences itself and exits. A stale writer is therefore harmless to the database, but not harmless to a client. The prefix fence and the self-fence together make the acknowledgement safe.

Aha: The ownership record is the lock, and the epoch is the lock's version. The log prefix repeats the epoch. A restore follows one epoch chain and ignores every prefix outside it. The conditional write selects the owner; the prefix then makes a loser harmless.

The system in one diagram

The diagram shows the four planes. The request plane accepts Hypertext Transfer Protocol (HTTP) and WebSocket traffic. The execution plane runs JavaScript in V8. The storage plane holds the SQLite database and the LTX log. The fleet plane holds the leases and the ownership records that decide which node owns each cell. The bucket is the shared source of truth for the storage plane and the fleet plane.
