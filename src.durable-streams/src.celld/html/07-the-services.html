The services

celld provides the Cloudflare services through three homes for state. A service either uses one reserved cell, uses keys in the fleet bucket, or runs on the node that owns its parent. The Key-Value store, the Queues broker, the D1 database service, Workflows, and Cron Triggers use a reserved cell. The R2 object store and the static asset store use the fleet bucket directly. A Dynamic Worker runs in an isolate on the node of its loader, and a container runs in the container engine on the node that owns the parent cell.

The homes mix at the edges. A Key-Value namespace keeps its rows in a cell and puts a value above 1 MiB in the bucket. A static asset body is durable in the bucket, and the serving node also caches it on local disk. An R2 multipart upload keeps its in-progress state on the node that opened it. A container image is durable in the bucket, and the container itself is local. Each section names the second home where it matters.

The home is the important part. A service that is a cell inherits every promise of the cell: one owner, serial events, a SQLite transaction, a fencing epoch, and the output gate. The service code does not repeat those promises. It adds a public Application Programming Interface (API) on top of them.

The three homes

A service that is a cell has one name, and that name becomes a Durable Object identifier through the same namespace derivation as an application class. The derivation has two rounds. The first round hashes the namespace key with SHA-256, and that hash becomes a Keyed-Hash Message Authentication Code (HMAC) key. The second round signs the cell name with that key. Celld caches the result for each thread, because the same name must always produce the same identifier. The namespace key is written out, not computed, because it is a stable address:

// crates/celld/engine_api.rs:507-520
pub(crate) const D1_NAMESPACE_KEY: &str = "cells:v1:d1:__D1Database";
pub(crate) const KV_NAMESPACE_KEY: &str = "cells:v1:kv:__KvNamespace";
pub(crate) const QUEUE_NAMESPACE_KEY: &str = "cells:v1:queue:__Queue";

The class name comes first in the cell scope. D1, the Key-Value namespace, and the Queue broker use one class name for the whole fleet:

// crates/celld/deploy.rs:72-89 (abridged)
pub const D1_CLASS: &str = "__D1Database";
pub const WORKFLOW_CLASS: &str = "__Workflow";
pub const KV_CLASS: &str = celld_logic::kv::RESERVED_CLASS;
pub const QUEUE_CLASS: &str = celld_logic::queue::RESERVED_CLASS;
pub const RESERVED_CLASSES: &[&str] = &[D1_CLASS, WORKFLOW_CLASS, KV_CLASS, QUEUE_CLASS];

A Workflow is the exception. The bare __Workflow name in RESERVED_CLASSES reserves the name and stops a user export from using it. The class of a real Workflow cell is different: it carries the script name after a dot, because one Workflow instance belongs to one script:

// crates/celld/deploy.rs:112-114
pub fn workflow_class(script_name: &str) -> String {
    format!("{WORKFLOW_CLASS}.{script_name}")
}

is_reserved_class accepts the bare __Workflow and every __Workflow.
