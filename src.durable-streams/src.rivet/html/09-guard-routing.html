09 Guard: HTTP and WebSocket routing, TLS, and the reverse proxy

Guard is the public edge of Rivet. It accepts Hypertext Transfer Protocol (HTTP) requests and WebSocket connections. It decides which internal service receives a request, wakes a sleeping Actor when necessary, and then serves the request through a custom gateway handler or a reverse proxy. Guard also terminates Transport Layer Security (TLS) when an operator configures it. The certificate resolver in this commit is a stub. This document follows the call graph from rivet_guard::start to the point where Guard writes a response to the client. It explains the path grammar, the header grammar, the WebSocket subprotocols, the reverse proxy, the hibernation handshake, and the wake protocol. It also explains the cache that is never filled, and the exact status that a client sees for each failure. It states which behavior belongs to the legacy runner path and which behavior belongs to the newer envoy path.

Three names recur in this document. An Actor is a keyed process that Pegboard schedules on a host. It keeps its state when it sleeps or moves. Pegboard is the scheduling service that owns the Actor workflows and allocates them to hosts; 04 Pegboard describes it. The source has two host paths. The legacy runner path uses a runner process, runner_id, and the version 1 Actor workflow. The newer envoy path uses an envoy process, envoy_key, and the version 2 Actor workflow. Both paths exist in this commit.

2. Startup and shared state

rivet_guard::start creates a standalone context, one SharedState, the routing function, the cache-key function, and the certificate resolver. PubSub is the Publish-Subscribe (PubSub) service. It carries tunnel messages and workflow signals. The ups handle is the PubSub pool that ctx.ups() returns.

// engine/packages/guard/src/lib.rs:11-42
#[tracing::instrument(skip_all)]
pub async fn start(config: rivet_config::Config, pools: rivet_pools::Pools) -> Result<()> {
	let cache = rivet_cache::CacheInner::from_env(&config, pools.clone())?;
	let ctx = StandaloneCtx::new(
		db::DatabaseKv::new(config.clone(), pools.clone()).await?,
		config.clone(),
		pools,
		cache,
		"guard",
		Id::new_v1(config.dc_label()),
		Id::new_v1(config.dc_label()),
	)?;

	// Share shared context
	let shared_state = shared_state::SharedState::new(&ctx, ctx.ups()?)?;
	shared_state.start().await?;

	// Create handlers
	let routing_fn = routing::create_routing_function(&ctx, shared_state.clone());
	let cache_key_fn = cache::create_cache_key_function();
	let cert_resolver = tls::create_cert_resolver(&ctx).await?;

	if let Some(_) = &cert_resolver {
		tracing::info!("TLS certificate resolver configured");
	} else {
		tracing::info!("No TLS configuration found, HTTPS will not be enabled");
	}

	// Start the server
	tracing::info!("starting proxy server");
	rivet_guard_core::run_server(config, routing_fn, cache_key_fn, cert_resolver).await
}

4. The route resolution call graph

ProxyService::handle_request resolves the route before it applies admission control (engine/packages/guard-core/src/proxy_service.rs:748-769). Route resolution runs inside race_request_authorization_deadline. That function subscribes to the token deadline that authentication publishes. If the deadline passes first, it returns auth.token_expired and drops the route future. The route work therefore stops even if it has not finished (engine/packages/guard-core/src/utils.rs:634-692). The request fails with status 401.

Admission runs after the route and before the handler. admit_request gets or creates a ClientState for the client address. ClientState holds an optional RateLimiter with a fixed window and an optional InFlightCounter. try_admit takes a rate token first and an in-flight slot second. A rate token is still spent when the in-flight limit rejects the request. AdmissionRejection::RateLimit returns guard.rate_limit and status 429. AdmissionRejection::MaxInFlight returns guard.max_in_flight and status 400, because the pair is not in the status map (engine/packages/guard-core/src/utils.rs:28-74 and proxy_service.rs:766-801). On success, Guard generates a unique 4-byte protocol::RequestId and stores an InFlightPermit on the context. The permit owns the slot, the request identifier, and the guard_in_flight_request_count gauge. Drop releases all three, so a cancelled request cannot leak them (engine/packages/guard-core/src/utils.rs:76-143).

// engine/packages/guard/src/routing/actor_path.rs:104-156
/// Parse actor routing information from path.
/// Matches patterns:
/// - /gateway/{actor_id}/{...path}
/// - /gateway/{actor_id}@{token}/{...path}
/// - /gateway/{name}/{...path}?rvt-namespace=...&rvt-method=...
///
/// Returns `Ok(None)` for paths that are not gateway paths or for malformed
/// direct paths (backwards-compatible silent fallthrough). Returns `Err` for
/// malformed query paths so clients receive actionable error messages.
pub fn parse_actor_path(path: &str) -> Result<Option<ParsedActorPath>> {
	// Extract base path and raw query from the original path string directly,
	// without running through a URL parser, to preserve actor query params
	// byte-for-byte (no re-encoding of %20, +, etc.).
	let (base_path, raw_query) = split_path_and_query(path);

	if base_path.contains("//") {
		return Ok(None);
	}

	let segments: Vec<&str> = base_path
		.split('/')
		.filter(|segment| !segment.is_empty())
		.collect();
	if segments.first().copied() != Some("gateway") {
		return Ok(None);
	}

	let raw_query_str = raw_query.unwrap_or("");

	// Check if any raw query param key starts with rvt-.
	let has_rvt = !raw_query_str.is_empty()
		&& raw_query_str
			.split('&')
			.any(|part| part.split('=').next().unwrap_or("").starts_with(RVT_PREFIX));

	if has_rvt {
		let rvt_params = extract_rvt_params_from_raw_query(raw_query_str)?;
		let actor_query_string = strip_rvt_query_params(raw_query_str);
		return parse_query_actor_path(base_path, &segments, &rvt_params, &actor_query_string)
			.map(|path| Some(ParsedActorPath::Query(path)));
	}

	// Direct path: pass the raw query string through unchanged.
	let raw_query_string = match raw_query {
		Some(q) => format!("?{q}"),
		None => String::new(),
	};
	Ok(parse_direct_actor_path(
		base_path,
		&segments,
		&raw_query_string,
	))
}

A direct path splits the Actor segment at the first @. Both sides must be non-empty. Both sides are percent-decoded. The remaining path is built from the segments after the Actor segment plus the original query (engine/packages/guard/src/routing/actor_path.rs:158-193).

All Actor routes converge on route_request_inner. The function receives the Actor identifier, the stripped path, the token, and the skip-ready-wait flag.

The first check is the datacenter label. A Rivet Id carries a label. If the Actor label differs from the current datacenter label, Guard calls config.dc_for_label. The reverse proxy path handles RoutingOutput::Route. In this commit, the only Route outputs in rivet-guard are the two cross-datacenter handoffs, one for a direct Actor path and one for a query path. Actor traffic normally uses CustomServe and the tunnel.

The keepalive task runs only for hibernating requests. The source uses hws as the short prefix for a hibernating WebSocket, as in hws_message_ack_timeout and hws_max_pending_size. 					}
					res = in_flight_req.send_message(open_message, false) => res?,

The async block then waits on msg_rx. A ToRivetWebSocketOpen message returns the message to the caller. The caller reads can_hibernate from it. A ToRivetWebSocketClose message returns WebSocketClosedBeforeOpen. Any other message is logged and ignored (engine/packages/pegboard-gateway2/src/lib.rs:477-545). created is false when create_or_wake_in_flight_request finds an existing entry, so resumed_from_hibernation is true only for an existing entry on a reconnect.

The envoy replies with ToRivetWebSocketOpen. The message carries can_hibernate. The gateway stores that flag with toggle_hibernatable. That method adds or removes hibernation_state on an Active request. It does nothing on a request that is already hibernating (engine/packages/pegboard-gateway2/src/shared_state.rs:931-963 and engine/packages/pegboard-gateway2/src/lib.rs:664-670).

On the runtime side, the exact rule is in engine/CLAUDE.md. NAPI is the Node-API (NAPI) interface that the TypeScript runtime uses to call Rust.

Restored hibernatable WebSockets must rebuild runtime WebSocket handlers from callbacks and call on_open; pre-sleep NAPI callbacks are not reusable after actor wake.

engine/CLAUDE.md:119

The rule has two parts. The runtime must rebuild the handler from callbacks. The old NAPI callback objects from before sleep are not valid after wake. The rebuilt handler then calls on_open. The source states the rule but not the reason.

This runtime on_open is not the same as the client-visible TypeScript onOpen event. The TypeScript hibernation test is named "onOpen is not emitted again after hibernation wake" (rivetkit-typescript/packages/rivetkit/tests/driver/actor-conn-hibernation.test.ts:100). 14.7 Garbage collection

The gateway garbage-collects hibernating requests on two conditions. The first is an unacknowledged client message older than hws_message_ack_timeout. The default is 30,000 milliseconds. The second is a last_ping older than hibernation_timeout, which comes from hibernating_request_eligible_threshold, default 90,000 milliseconds.

// engine/packages/pegboard-gateway3/src/shared_state.rs:2340-2378
	fn expired(
		&self,
		hws_message_ack_timeout: &Duration,
		now: &Instant,
		hibernation_timeout: &Duration,
	) -> Option<MsgGcReason> {
		match &self.state {
			InFlightRequestState::Active {
				hibernation_state: Some(hibernation_state),
				..
			}
			| InFlightRequestState::PendingHibernation { hibernation_state }
			| InFlightRequestState::Hibernating {
				hibernation_state, ..
			} => {
				if let Some(earliest_pending_ws_msg) = hibernation_state.pending_ws_msgs.first() {
					if &now.duration_since(earliest_pending_ws_msg.send_instant)
						> hws_message_ack_timeout
					{
						return Some(MsgGcReason::WebSocketMessageNotAcked {
							first_msg_index: earliest_pending_ws_msg.message_index,
							last_msg_index: self.message_index,
						});
					}
				}

				let hs_elapsed = hibernation_state.last_ping.elapsed();
				tracing::debug!(
					hs_elapsed=%hs_elapsed.as_secs_f64(),
					timeout=%hibernation_timeout.as_secs_f64(),
					"checking hibernating state elapsed time"
				);

				if &hs_elapsed > hibernation_timeout {
					return Some(MsgGcReason::HibernationTimeout);
				}

				None
			}

The garbage collection (GC) interval is 15,000 milliseconds (engine/packages/config/src/config/pegboard.rs:323-325). The GC task calls expired for each in-flight request. message_index in the GC reason is the protocol::MessageIndex of the oldest unacknowledged client message. The maximum pending size is not a GC condition. It is a separate admission check. gateway_hws_max_pending_size defaults to 128 MiB. The gateway returns WebsocketPendingLimitReached when the pending buffer is too large (engine/packages/config/src/config/pegboard.rs:335-338 and engine/packages/pegboard-gateway3/src/lib.rs:49-55).

14.8 Closing during hibernation

This subsection starts after the hibernation task and the keepalive task return. PegboardGateway2 joins the two results at engine/packages/pegboard-gateway2/src/lib.rs:1181-1219. Continue keeps the request. Close or an error stops it. The close code 1000 in section 14.1 is the Actor-stop path when hibernation is not allowed. It is not the client-close path here.

If the hibernation task returns Close, the gateway reconnects to the Actor and then closes. The gateway 2 code sets ws_hibernation_close = true when handle_websocket_hibernation returns Close. The next handler iteration reconnects and sends the close through the tunnel. The source comment says this reconnect is necessary so the Actor knows that the connection closed (engine/packages/guard-core/src/proxy_service.rs:1897-1903).

If handle_websocket_hibernation returns Continue, the gateway does not stop the in-flight request. It reconnects and keeps the same request identifier. If it returns Close or an error, the gateway calls in_flight_req.stop(...) and deletes the UniversalDB (UDB) hibernating-request entry (engine/packages/pegboard-gateway2/src/lib.rs:1195-1214).

21. What the design costs

Aha: Guard routes path-first and keeps the Actor location out of the client. The client sends /gateway/{actor_id}/... or a query path. Guard looks up the Actor, waits for readiness, and then hands the request to a gateway object that owns a tunnel request identifier. The obvious alternative is to return the runner address to the client, or to put the runner address in a redirect. That alternative would remove the wake wait and the tunnel lookup from Guard. It would also make the client responsible for retries, for the Actor move, and for the sleep state. Every client would need the scheduling logic. The cost of the Guard design is that Guard holds the request during a cold start. The wait can last 30,000 milliseconds, and the whole route has a 60,000 millisecond backstop. A sleeping Actor therefore costs a held connection and a long tail. The source does not state a reason for the path-first order. The order is visible in the call graph.

The second cost is the tunnel. Guard does not connect to the Actor directly. It publishes to EnvoyReceiverSubject::new(namespace_id, envoy_key). It subscribes to its own GatewayReceiverSubject::new(gateway_id). The envoy replies on that subject. The protocol::RequestId selects the in-flight entry, so many requests share one gateway subscription (engine/packages/pegboard-gateway2/src/lib.rs:185-190 and engine/packages/pegboard-gateway2/src/shared_state.rs:236-300). A lost envoy becomes a tunnel error, not a TCP reset. The client sees 503 or 504. The benefit is that the Actor can move between envoys without a new client address.
