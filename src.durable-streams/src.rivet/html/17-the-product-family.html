17 The product family

The Rivet product family is a set of seven sibling repositories. Six build a developer product on top of Rivet. The seventh publishes the public website and documentation. This document reads each repository at its own commit. It shows the code that connects each runtime consumer to Rivet. It then tests one claim against all seven: a product adds an Actor definition and a developer experience, not a scheduler. That claim holds for Agents, Workflows, Dynamic Apps, OpenOrange, hosted agentOS, and the migrator example. The stronger claim, that every product is a Runner configuration plus a RivetKit registry plus a control plane namespace, fits OpenOrange fully. It fits hosted agentOS, Agents, Workflows, and Dynamic Apps partly. It fits the migrator package and the website not at all.

3. agentOS: a virtual machine for each agent

3.1 Purpose

agentOS gives one agent a small Linux-compatible computer. The computer has a process table, a filesystem, a network view, and a permission model. It runs many guests in one process. A guest is JavaScript in a V8 isolate or a compiled tool in WebAssembly. The product states that it is a library, not extra infrastructure, and that it does not need a hypervisor or nested virtualization (README.md:25-35).

agentOS has two modes. In library mode, the virtual machine runs inside the backend process that the operator already runs. In hosted mode, the virtual machine is a durable Actor on Rivet Cloud or on a self-hosted Rivet cluster. README.md:60-69 gives the full comparison. The hosted mode adds a scoped JSON Web Token (JWT) for browser clients and expiring preview URLs. The library mode has neither.

3.2 Language, build system, package layout, entry point

agentOS is a mixed Rust and TypeScript workspace. The Rust side is a Cargo workspace under crates/. The TypeScript side is a pnpm workspace under packages/. The root manifest is package.json:1-2, named @rivet-dev/agentos-workspace.

The Cargo workspace holds kernel, vfs, v8-runtime, execution, runtime, native-sidecar, sidecar-protocol, and related crates. The README describes the sidecar as a Rust process that runs separately from the application process (README.md:292-301).

3.3 How agentOS uses Rivet

agentOS uses the control plane in hosted mode only. It does not use RivetKit in either mode. A search of every package.json in the repository for the string "rivetkit" returned no line. The repository also does not contain a setup({ use }) registry. The hosted path speaks the control plane HTTP Application Programming Interface (API) directly.

The raw HTTP example in the README is the clearest evidence. It creates the Actor with a name, a key, a Runner selector, a crash policy, and a namespace.

3.4 Inside agentOS

The architecture is a trust boundary. The application process or the HTTP API connects to the sidecar. The sidecar holds a trusted kernel and all guest code. The kernel owns the process table, the virtual filesystem, networking, and permissions. Guest code runs in V8 isolates and WebAssembly. Guest code reaches the kernel only through syscalls (README.md:292-310).

The TypeScript surface has three important shapes. AgentOs is the library handle, with create, createSidecar, and getSharedSidecar. The object from create exposes process, filesystem, and javascript (README.md:81-100). AgentOsSidecar owns the sidecar process (packages/core/src/agent-os.ts:6258). I read only its declaration, so this document does not list its fields. VirtualFileSystem has one method for each filesystem operation that the guest can issue. The excerpt below is a prefix, not the whole interface.

The sandbox client has a smaller surface. The README example sets maxProcesses: 64 and maxFilesystemBytes: 256 1024 1024 (README.md:152-153). The caller chooses them, and the source states no default.

3.5 Status

The README uses no preview, beta, experimental, or general availability label for agentOS; the only match is the feature name "preview URLs". The website gives no status badge, and every public runtime package is 0.0.1. The source states no status.

3.6 Limits and what agentOS does not do

  • The library mode has no control plane. It runs until dispose() or process

exit (README.md:64-65) and does not survive the death of the host process.

  • The hosted mode sleeps when idle unless a process runs (README.md:65).
  • Only the hosted mode creates an expiring preview URL for a port (README.md:67).
  • agentOS is not a micro virtual machine. It uses V8 isolates and WebAssembly,

so it does not run an arbitrary Linux kernel or native binary (README.md:31).

  • The repository does not contain a hosted Actor definition. The Actor named

agentOS is a control-plane object, so its definition is outside this tree.

4. Agents: an agent loop inside an Actor

4.1 Purpose

The Agents repository holds two products. Rivet Agents runs the Pi coding agent as a durable Rivet Actor. Sandbox Agent runs coding agents in sandboxes and controls them over HTTP (README.md:7-10). The main package is @rivet-dev/pi, described as "Run the Pi coding agent as a durable Rivet Actor" (packages/pi/package.json:4).

The Actor owns one Pi Durable harness. Pi Durable is the agent harness package @earendil-works/pi-durable. The harness stores conversations, tasks, and documents in the Actor's SQLite database. A run survives sleep, an upgrade, and a crash. The run resumes when the Actor wakes. The actions of the Actor match the Pi Durable API one to one (packages/pi/src/actor.ts:130-137).

4.2 Language, build system, package layout, entry point

The repository is a pnpm workspace. The root manifest pins pnpm 9.15.0 (package.json:5) and builds every package under packages/ with pnpm -r --filter './packages/*' build (package.json:8). The Pi package builds with tsc -p tsconfig.build.json (packages/pi/package.json:43-45).

4.3 How Agents uses Rivet

The product uses RivetKit. It imports actor, event, and the type helpers from rivetkit, and it imports db from rivetkit/db (packages/pi/src/actor.ts:2-9). The peer range is >=2.3.28 <2.4.0 || ^3.0.0-preview.2, and the development version is 3.0.0-preview.2 (packages/pi/package.json:58, packages/pi/package.json:67). That range spans the 2.x line and the 3.0 preview line.

The Actor definition shows the main Rivet features that the product uses.

PI_RUNTIME is the symbol key, createPiRuntime builds the runtime, withPiAccess and wrapActions wrap actions, and withPi wraps a hook. onWake opens the harness, runs the application onWake, and then resumes interrupted work. onSleep and onDestroy close it after the application hook runs.

The shared configuration sets two timing values. actionTimeout is ten minutes (packages/pi/src/actor-config.ts:4-5). sleepGracePeriod is DEFAULT_SLEEP_GRACE_PERIOD_MS, which is 15 minutes (packages/pi/src/drain.ts:1-5). The caller's options spread after both, so the caller can override them. The reason is in the comment at packages/pi/src/actor-config.ts:4: Pi waits such as waitForIdle, prompt, and submission.wait outlive the RivetKit one-minute default.

The onWake failure path is careful. If openOnWake fails, the Actor stays up. The error is logged, and each action later reports the cause. The comment says that a schema newer than the code is one such cause (packages/pi/src/actor.ts:221-241). That choice protects the recovery path. A crash loop would hide the cause. The cost is that a broken Actor stays awake until an operator acts or the application destroys it.

4.4 Inside Agents

The main components are pi(), the Pi runtime slot, the action layer, and the harness.

The pi() function checks the input, builds the Pi actions, and calls actor(). The Pi runtime is created lazily and stored in a symbol slot on the Actor variables. The symbol is PI_RUNTIME, and the factory is createPiRuntime (packages/pi/src/actor.ts:206).

The action layer has two wrappers. withPiAccess opens the harness when an action needs it. withPi wraps a lifecycle hook and controls whether the hook opens the harness (packages/pi/src/actor.ts:188-198).

The harness is the Pi Durable object. It owns the conversations, the tasks, and the documents. The Actor owns the harness. The Actor does not own a model connection across a sleep. onWake resumes the interrupted work after the application onWake runs (packages/pi/src/actor.ts:221-240).

The product documentation draws a state machine with five states: Idle, Running, Compacting, Sleeping, and Sandbox (docs/content/docs/architecture.mdx:13). The diagram below repeats its transitions.

stateDiagram-v2 [*] --> Idle Idle --> Running: prompt Running --> Idle: run ends or is cancelled Running --> Compacting: context is full Compacting --> Running: compaction is done Idle --> Sleeping: idle Sleeping --> Idle: next action wakes the Actor Running --> Sandbox: tool call Sandbox --> Running: tool result

The source files do not declare these names as an enum, so treat the diagram as the product model.

The sleep grace period is 15 minutes by default (docs/content/docs/architecture.mdx:115), the value of DEFAULT_SLEEP_GRACE_PERIOD_MS (packages/pi/src/drain.ts:5). Actions wait up to ten minutes, and a timed-out wait leaves the run going (docs/content/docs/architecture.mdx:117). The source does not state why the action timeout equals the wait limit. The comment in the code states only that the Pi waits outlive the one-minute RivetKit default.

The Pi Durable dependency is in beta: "Pi Durable is still in beta, so expect its API to change between releases" (docs/content/docs/pi.mdx:10). The @rivet-dev/pi package is 0.5.4. The Sandbox Agent backend is 0.1.0 and carries no label. The website hides the Agents product from its switcher (website/src/sitemap/product-metadata.ts:144-157).

5. Workflows: durable execution on top of an Actor

5.1 Purpose

Workflows turns a multi-step operation into a durable, replayable run inside an Actor. The package description is "Durable, replayable workflows for Rivet Actors" (packages/workflows/package.json:4). A workflow is a normal Actor with one extra field: run. The run function calls ctx.step(...). Each step result goes into the Actor database. After a crash or a sleep, the workflow replays the recorded steps and does not repeat them.

The package preserves the existing workflow history encoding. It uses only the public workflow-host capabilities of RivetKit. It re-exports RivetKit, so a workflow Actor and a regular actor(...) definition can share one registry (README.md:30-35).

After migration, application traffic returns migrator.moved, so a late write cannot land on the old copy. migrationRoute(req, env, { token }) is the route entry.

The Rivet example is the important part for this document. The room Actor imports its own data in onMigrate. The hook runs on every Actor start, before the Actor serves anything. The import itself runs only when the marker table is absent. The comment states the safety argument: only one instance of an Actor runs at a time, so lazy migration and backfill cannot import the same Durable Object twice.

RivetKit has two onMigrate positions. The example uses the top-level actor({ onMigrate }) hook. The Agents product uses db({ onMigrate }). The top-level hook runs on every start after state loads and before onWake; the provider hook runs with the database client (rivet/rivetkit-typescript/packages/rivetkit/src/actor/config.ts:1608-1625).

// durable-object-migrator/examples/rivet/registry.ts:17-45
export const room = actor({
	db: db(),
	// Runs on every start, before the actor serves anything. Only one instance
	// of an actor runs at a time, so lazy migration and backfill cannot import
	// the same Durable Object twice.
	onMigrate: async (c) => {
		const moved = await c.db.execute(`SELECT 1 FROM sqlite_master WHERE name = '__do_meta'`);
		if (moved.length > 0) return;

		const key = c.key[0]!;
		const id = key.startsWith(UNNAMED_PREFIX)
			? key.slice(UNNAMED_PREFIX.length)
			: (await migrator.resolve("ROOMS", { name: key })).id;

		// All or nothing. If the export throws (for example MigrationDirtyError),
		// nothing is kept and the next start tries again.
		await c.db.transaction(async (tx) => {
			// The export can insert a child row before its parent. Foreign keys
			// cannot be turned off inside a transaction, so check them at commit.
			await tx.execute("PRAGMA defer_foreign_keys = ON");
			for await (const page of migrator.exportObject({ binding: "ROOMS", id })) {
				for (const stmt of page.statements) await tx.execute(stmt);
			}
		});
	},
	actions: {
		ping: () => "pong",
	},
});

The export writes the object id, name, and alarm time into __do_meta at the end of the last page (src/worker.ts:559-563). That tail is how __do_meta reaches the Actor. The guard works because the Actor database then contains the marker table.

The backfill script creates a createRivetClient client and calls getOrCreate([name]).ping() for every Durable Object. Each Actor imports its own data (examples/rivet/backfill.ts:10-27).

The product uses three Rivet features here: an Actor with a key, the onMigrate hook, and the Actor SQLite database. The backfill uses the client getOrCreate call to create or wake the Actor. The Actor key is the Durable Object name, or cloudflare: when the object has no name (examples/rivet/registry.ts:14-15).

The Worker creates __do_kv and __do_meta at the start of the first export page and skips their existing rows (src/worker.ts:389-392, src/worker.ts:579-588). So the import copies the marker table's schema and the tail row, not the old table rows.

The failure path is all or nothing. If the export throws, for example with MigrationDirtyError, the transaction rolls back and the next start tries again. The client also has a hard check. If the Worker does not answer with the x-migrator header, the client throws migrator.not_a_migrator and explains that workerUrl must still reach Cloudflare after the Domain Name System (DNS) cutover (src/client.ts:84-91).

8.4 Inside the migrator

The Worker side has a state table for the migration, a key-value table for Durable Object storage values in the devalue serialization format, and a metadata table for the object metadata.

The client side has three operations. exportObject yields pages of SQL statements and fetches the next page while the caller writes the current page, so the Durable Object stays awake between pages (src/client.ts:109-129). resolve turns a name into an id or an id into a name. backfill lists every object with stored data and calls the user function for each one. The defaults are concurrency = 8 and retries = 3 (src/client.ts:146-148).

The backfill position is a cursor and an index. The saved position never passes an object that failed, so a resumed run retries it (src/client.ts:153-155).

13. Where the pattern bends

The pattern bends in four places. Each bend has a source citation.

13.1 The hosted agentOS path has no registry

agentOS uses the control plane API directly. A PUT /actors call creates the Actor named agentOS (README.md:217-225). The repository has no RivetKit setup call and no RivetKit actor call. The hosted definition must live in the service that serves the services Runner pool, and that service is not in this working tree.

The trade-off is visible in the API. The caller must know the Actor name (agentOS), the key shape (my-vm), the Runner selector (services), and the crash policy (sleep). With a registry, the Runner selector and the crash policy would live in the Actor definition, not in the request. The raw path makes the product independent of the SDK version. That may be the reason, but the source does not state it.

13.2 The migrator defines an Actor only in an example

The package manifest has no rivetkit dependency. The exports are ./worker, ./client, and ./alchemy (package.json:23-27). The room Actor is in examples/rivet/registry.ts, because Rivet is one of several destinations.

13.3 The website is not a runtime product

The website has no registry, no Actor, and no namespace. Its only Rivet code is a documentation sample (cloud/examples/docs/actor-nodes/server.ts:4-19). It is a distribution surface, not a consumer of the scheduler.

14. The product strategy and its cost

Aha: The same control plane schedules every Actor product, so a product adds an Actor definition and a developer experience, not a scheduler. The evidence is direct for Agents, Workflows, Dynamic Apps, OpenOrange, and the migrator's Rivet example. Each of these cases defines an Actor, or an Actor example, and hands it to the same setup and actor path. The product code contains no placement logic, no lease, no membership, and no node registry. The control plane owns those. The product contains a builder, a harness, a history format, a compatibility layer, or an import protocol; those are the real product.

The claim needs one narrowing. Hosted agentOS consumes the scheduler through the raw control plane API, not through RivetKit. It still does not add a scheduler, so the core of the claim holds. But its Actor definition is outside the agentOS repository, so a reader cannot see the full product in one tree. The claim also does not apply to the agentOS library mode, which has no control plane at all, and it does not apply to the website, which has no runtime.

The benefit is that a product team writes an Actor definition and some product logic. The team gets placement, wake, sleep, crash recovery, regions, tokens, namespaces, SQLite, and a bucket-backed durable store without writing them. These products build very different things: an agent loop, a workflow engine, a deployment platform, a Workers runtime, and a migration target.

The cost is that the product inherits the control plane's limits and its version surface. The agentOS product cannot run without a Rivet cluster in hosted mode. OpenOrange must pin a release candidate of RivetKit, and it records a silent key change between versions. Workflows cannot move to RivetKit 3 without changing its peer range. Agents accepts both 2.x and 3.0 preview, which means it carries two compatibility paths. The family has one scheduler but not one SDK; that split is the price of the shared base.

The obvious alternative is a separate scheduler for each product, so each product owns placement and recovery. That would need one lease system for each product, plus membership views, wake paths, and storage layers. The source does not state that the team considered it, but five products call the same setup and actor functions.
