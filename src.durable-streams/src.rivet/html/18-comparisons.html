18 Comparisons: Rivet, Durable Objects, Kubernetes, and durable state systems

Rivet makes a keyed Actor, its SQLite database, and its workflow state durable. SQLite is an embedded database. It uses Structured Query Language (SQL). This document compares Rivet with six systems that also keep the state of a distributed program: Cloudflare Durable Objects, Kubernetes, Temporal, Resonate, Electric Durable Streams, and celld. The comparison asks one question. Where does the durable memory of a distributed program live, and which system pays which cost to keep it there? The answer is not a ranking. Each system makes a different part of the problem durable. Rivet makes the Actor durable. A Durable Object makes one object durable. Kubernetes keeps a workload specification and its volume durable. The controller creates replacement pods around that specification. Temporal and Resonate make a workflow history durable. Electric makes an ordered log durable. celld makes one Workers object and its bucket proof durable.

The document uses the source at commit 4a58441c50d1ce20d8803cfb1ab7c3285a5141d6 (version 2.3.31) for every Rivet claim. It uses the sibling explorations in this parent directory for Resonate, Electric, and celld. It marks every other claim with its own label.

Aha: The deepest difference is not speed or storage size. It is the unit that survives a crash. Rivet survives as a keyed Actor and its state. A Durable Object survives as an object and its SQLite database. Kubernetes keeps the workload specification and the Persistent Volume. The controller creates a replacement pod after a failure. Temporal and Resonate survive as an event history. Electric survives as a byte log. celld survives as a cell plus its ownership epoch. The unit of survival decides the recovery path, the failure model, and the operational cost.

A fair comparison starts with the unit of survival, because the unit decides everything that follows. The table gives the short answer. The sections give the mechanism. Three names appear in the table before their full explanation. Pegboard is the Rivet scheduling and placement layer. An envoy is the node process that hosts Actors on the version 2 path. UniversalDB is the transactional key-value store that holds Rivet records.

The lookup uses the namespace, the name, and the key. It returns one actor_id (engine/packages/guard/src/routing/pegboard_gateway/resolve_actor_query.rs:71-100). The actor_id is the durable identifier after the lookup. A caller that already holds the actor_id does not need the lookup.

CrashPolicy is a small enum. The enum marks Destroy as the default variant (engine/packages/types/src/actors.rs:40-47). A caller that constructs the default value gets Destroy. The getOrCreate query is different. It supplies Sleep when the request names no policy (engine/packages/guard/src/routing/pegboard_gateway/resolve_actor_query.rs:53). The policy has a different effect on each Actor workflow.

The version 1 workflow reads the policy after an ungraceful exit (engine/packages/pegboard/src/workflows/actor/mod.rs:1242-1292). A Restart policy allocates the Actor again. A Sleep policy marks the Actor sleeping. A Destroy policy removes the Actor. A graceful exit destroys the Actor whatever the policy says.

The version 2 workflow does not read crash_policy. Its input struct has no such field (engine/packages/pegboard/src/workflows/actor2/mod.rs:21-33). The create operation builds that input without the policy (engine/packages/pegboard/src/ops/actor/create.rs:113-121). The workflow decides from the stop result instead. A graceful stop destroys. An error or a lost envoy sleeps (engine/packages/pegboard/src/workflows/actor2/runtime.rs:639-663). The stored policy has no effect on this path.

Guard is the Rivet request router. For getOrCreate, it passes the policy value to the create operation. The version 2 create input has no field for it, so the value stops there. A reader must not expect it to change the version 2 stop behavior.

Destroy removes durable data on the version 2 path. The workflow writes the destroy timestamp and removes the active Actor index (engine/packages/pegboard/src/workflows/actor2/mod.rs:1211-1277). It then clears the Actor key-value subspace and the version 2 storage (engine/packages/pegboard/src/workflows/actor2/mod.rs:1288-1311). The storage clear removes the page index, the commit rows, and the delta chunks that carry page bytes (engine/packages/pegboard/src/actor_sqlite.rs:38-60). Depot is the Rivet per-Actor storage engine. The version 1 destroy workflow does the same work at engine/packages/pegboard/src/workflows/actor/destroy.rs:103-150.

Neither published latency measurement runs a crash. The 6.92 ms cold start creates a new Actor. The 4.37 ms wake follows a sleep of at least 10 seconds (README.md:153-154). Neither measurement names a crash policy, because neither path runs the crash decision.

The Actor's workflow keeps two durable records. The State type holds the identity, the pool, the timestamps, and the current error. It has no generation field. The LifecycleState holds the generation, the current Transition, an alarm time, and a retry backoff state.

State is workflow state. Gasoline, the Rivet durable execution engine, saves it through a StateGuard (engine/packages/gasoline/src/workflow.rs:27-70). The guard holds the state as a shared raw JavaScript Object Notation (JSON) value. A write through the guard sets a dirty flag. On drop, the guard serializes the struct back into that shared value (engine/packages/gasoline/src/workflow.rs:60-64). Gasoline later writes the workflow record that holds the value (engine/packages/gasoline/src/db/mod.rs:333-341). UniversalDB receives the record, not one field at a time. On replay, Gasoline reads the record and reconstructs State.

LifecycleState is loop state. A loop is a bounded repetition in one workflow. The workflow passes the state to ctx.lupe().with_state(...) (engine/packages/pegboard/src/workflows/actor2/mod.rs:247-255). lupe returns a loop builder, and with_state attaches the state to it (engine/packages/gasoline/src/builder/workflow/lupe.rs:19-40). Gasoline stores each loop checkpoint in a LoopEvent (engine/packages/gasoline/src/builder/workflow/lupe.rs:64-80).

Gasoline keeps both records in UniversalDB. UniversalDB is the transactional key-value store. It holds workflow records and the Depot records for Actor SQLite in different key subspaces. Epoxy is the Rivet consensus layer for geo-distributed keys. It is not a store for Actor data. In this source it serves Actor key reservation only (engine/packages/epoxy/README.md:37-42). Its own consensus records commit in UniversalDB (engine/packages/epoxy/README.md:51). The Actor's SQLite database is a logical database that Depot builds from its records. It is not a third store. The workflow state is separate from the application rows. A reader must keep the two apart. The workflow state holds scheduling and lifecycle facts.

The next section compares the Rivet unit with the Cloudflare unit. The two units look similar at the surface. The differences are in placement, runtime, and limits.

3. Cloudflare Durable Objects

Cloudflare Durable Objects is a platform with one named object for each key. A Durable Object class defines the object. The platform gives each object an identifier. The object runs on the Cloudflare network. The object can use SQLite storage and a key-value storage Application Programming Interface (API). The platform can hibernate an idle object and wake it on the next request. These model facts come from the Cloudflare Durable Objects documentation at https://developers.cloudflare.com/durable-objects/. This document labels them external. The Rivet repository does not contain the Cloudflare implementation, so this snapshot cannot verify them.

The Rivet README makes four specific claims about Durable Objects. It says Durable Objects have a 128 megabyte (MB) memory cap. It says they have a 10 gigabyte (GB) SQLite limit. It says the platform can evict them at random. It says they use a custom runtime. The same paragraph says Rivet removes each constraint. This document labels these statements as Rivet product claims. The source is README.md:281-283.

3.2 Lifecycle and hibernation

Rivet's lifecycle has nine states. The Transition enum names every state. The state machine is durable. A crash does not lose the transition. Gasoline replays the workflow and continues from the stored state.

SleepIntent and StopIntent have different causes. An idle Actor or the sleep Application Programming Interface (API) causes SleepIntent. The runtime sends a sleep intent on the Actor's behalf. A stop request causes StopIntent. The workflow sets the transition and sends the stop command to the envoy (engine/packages/pegboard/src/workflows/actor2/mod.rs:715-765).

The handle_stopped function makes the decision. It deallocates the slot first. It then reads the transition and the stop result. A graceful stop from StopIntent destroys the Actor. An error or a lost envoy sleeps the Actor. A SleepIntent with rewake_after_stop set reallocates the Actor. The source is engine/packages/pegboard/src/workflows/actor2/runtime.rs:607-733.

The Sleeping state has no envoy. The workflow listens for a wake signal or for an alarm. The alarm path is explicit in the signal loop. A timeout produces a fake Wake signal. A request that arrives through Guard also wakes the Actor.

The wait survives a control-plane crash. listen_n_until writes a sleep event with a deadline and a state before it waits (engine/packages/gasoline/src/ctx/workflow.rs:925-962). On replay, the workflow reads the recorded deadline and waits only for the remaining time (engine/packages/gasoline/src/ctx/workflow.rs:1001-1005). If the deadline has passed, the wait returns at once. A recorded signal event also replays without a new wait (engine/packages/gasoline/src/ctx/workflow.rs:967-996).

The Cloudflare model also has hibernation. The difference is what remains resident. A hibernated Durable Object keeps its identity and its SQLite data. A sleeping Rivet Actor keeps its workflow state and its SQLite pages. Neither keeps a running process.

3.3 Where each is the right choice

Cloudflare Durable Objects is the right choice when the application already runs on Cloudflare, the object fits the platform limits, and the operator does not want to run any infrastructure. The platform supplies global placement, Transport Layer Security (TLS), identity, and storage. The cost is vendor dependence, the platform runtime, and the stated limits. These are External document claims. The named external document is https://developers.cloudflare.com/durable-objects/. This document did not fetch it.

Rivet is the right choice when the application must self-host. It also fits when the code needs the standard Node.js or Bun ecosystem. It fits when one key needs more than 10 GB on the native path. It fits when the Actors must run near data in the operator's own cloud. The cost is a control plane, a bucket, and nodes to operate. The price is also a more complex protocol. These claims come from this exploration's ./README.md and the Rivet repository README.

4. Kubernetes

Kubernetes schedules pods. A pod is one or more containers that share a network namespace and a set of volumes. The kube-scheduler assigns the pod to a node. The kubelet on that node starts the containers. A Persistent Volume (PV) holds data across pod restarts. The storage class and the Container Storage Interface (CSI) driver decide whether a replacement pod can use the same volume on another node. These are External document claims. The named external document is https://kubernetes.io/docs/concepts/workloads/pods/. This document did not fetch it.

Rivet schedules Actors. An Actor is not a pod. It is a task inside a node process that the operator already runs. The README says this directly: "An Actor lives inside a node process you already run, not in its own container or VM. A server that held hundreds of pods holds hundreds of thousands of Actors." The source is README.md:64.

4.1 The unit, the cold start, and the memory

A pod has a container image, a runtime, a network namespace, and a volume. The scheduler must find a node with enough central processing unit (CPU), memory, and storage. The kubelet must pull the image if it is not cached. The container runtime must start the process. That chain takes seconds in the typical case. A warm node with a cached image is faster than a cold node. The README's ~6 seconds is a typical value, not a floor.

An Actor has no image pull and no container boot. The node process already runs the Actor runtime. Pegboard sends a start command to the envoy. The envoy starts the Actor task and loads its state. The new Actor's empty SQLite database becomes available. The new Actor fetches no pages, because it has none. A woken Actor can have evicted pages, and it may fetch them from the bucket. The README does not report that case. The 6.92 ms p50 measurement covers the new Actor chain.

The memory difference follows from the unit. A pod reserves memory for the container runtime, the base image, and the Node.js or other language runtime. An Actor shares the node process and adds its own state. The 72.4 KB is the RSS increase per Actor. It does not include the shared node process. A reader must not multiply 72.4 KB by the number of Actors and compare that number with the total memory of a pod. The right comparison is per running unit, with the shared process counted once.

Aha: The 72.4 KB figure is honest only when the shared process is counted once. A node with 1,000 Actors pays one Node.js process plus 1,000 state increments. A Kubernetes node with 1,000 pods pays 1,000 runtimes. The design choice is to share the runtime. The obvious alternative is one container per Actor. That alternative buys isolation and costs density.

4.2 Storage, scale, and network

A pod's volume is a Persistent Volume. The volume can be a network disk, a local disk, or a CSI-backed store. A pod is not moved. The controller deletes it and creates a replacement pod. The replacement pod can use the volume only when the storage class supports multi-attach or reattachment. A local volume cannot follow the workload. The data model is a filesystem. The application must choose a database, a file format, and a backup method.

An Actor's storage is part of the Actor. Each Actor gets a SQLite database and a key-value space. The control plane replicates writes to the local disks of several instances. A background process moves pages to the bucket. The bucket is not on the write path. The README states that storage never runs out and the bucket never sits on the write path. The source is README.md:68. This is a product claim. The native SQLite path supports it. The WebAssembly and remote SQL path has a 256 MiB database limit, as section 10 explains.

The scale difference is one control plane for billions of Actors versus about 5,000 nodes per cluster. The two numbers measure different things. The Kubernetes number is a node count. The Rivet number is an Actor count. A single Kubernetes node can host many Actors. The correct comparison is the scheduling unit and the control plane load, not the raw counts. The README uses the numbers as a density argument. The source is README.md:66 and README.md:147.

The network models also differ. Kubernetes gives each pod an Internet Protocol (IP) address on the pod network. A Service is a stable virtual address for a group of pods. Ingress is a Hypertext Transfer Protocol (HTTP) router that exposes a Service outside the cluster. Network policy controls traffic. The model is general purpose. It can carry any protocol.

Rivet uses Guard. Guard is the Rivet request router. It receives HTTP and WebSocket traffic. It routes the request by Actor key to the envoy that hosts the Actor. A node opens an outbound connection to the control plane. The node needs no public address for Actor traffic. The model is narrow. It carries HTTP and WebSocket to keyed Actors. The benefit is that the client never learns the node address. Guard resolves the Actor identity to the current envoy on each request. The architecture page says the Actor keeps the same address when it moves (docs/general/content/architecture.mdx:42). That address is the stable Actor address, not the node address. The source is README.md:168 and docs/general/content/architecture.mdx:38-42.

5. Temporal

Temporal is a durable execution platform. A Temporal workflow is a program with a deterministic history. A worker runs the workflow code. An activity is a step with side effects. The Temporal service stores the workflow history in a persistence database. A worker fleet polls task queues. After a crash, a worker replays the history and continues. These are general Temporal facts from https://docs.temporal.io/. This document labels them external. This snapshot does not contain the Temporal source or a Temporal deployment.

The Rivet repository does not mention Temporal. A search of the Markdown and Rust files at this commit found no Temporal reference. This document therefore cannot make a product comparison from the Rivet side. It compares mechanisms instead. The Rivet side comes from the Gasoline source. The Temporal side is general knowledge, not verified here. This section reads the source directly to compare the mechanisms.

5.1 The Temporal shape

Temporal puts durable execution in a separate service. The service has a front end, a history service, a matching service, and an internal worker service. The history service stores the event history in a database. The matching service hands tasks to user workers. The internal worker service runs the platform's own system workflows, such as archival. The user worker fleet is separate from the service. A user runs those workers. The service runs the history and the task queues. The database is a Cassandra, PostgreSQL, or MySQL deployment. These are general facts. They are external.

The separation has a clear cost. The user operates or buys a Temporal service and a database. The worker fleet scales separately. The history store grows with the number of workflow events. The service is a second distributed system beside the application.

5.2 The Gasoline shape

Gasoline is a crate inside the Rivet control plane. A crate is a Rust package or library. It is not a separate service. A workflow is an asynchronous Rust function. The workflow context holds the input, the state, the event history, and a cursor. The Gasoline worker pulls workflows from UniversalDB. A bump subscription wakes the worker when a workflow is ready. A bump subscription is a notification on the gasoline.worker.bump subject of universalpubsub, the publish-and-subscribe crate (engine/packages/gasoline/src/db/mod.rs:391-421). The worker polls on a timer and also wakes on that notification (engine/packages/gasoline/src/worker.rs:74-90). The worker runs the workflow and writes the state back.

In this snapshot, Gasoline workflows are internal to the control plane. The public Actor application programming interface does not expose Gasoline. Control-plane code writes the workflows in Rust with the Gasoline macros (engine/packages/gasoline-macros/src/lib.rs:20-45). The Pegboard Actor workflow is one such workflow.

The word worker has three meanings in the Temporal and Gasoline comparison. The Temporal internal worker service runs the platform's own workflows. The user worker fleet is the set of processes that run user workflow code. The Gasoline worker is a loop inside the control plane process that pulls workflows (engine/packages/gasoline/src/worker.rs:74-145). The matching service is not a worker. It pairs a task with a user worker. Each use below names the meaning. The Resonate section uses worker for the separate process that runs user task code.

The WorkflowData type shows the durable shape. It holds the workflow identifier, the name, the input, the state, the output, and a wake-condition flag. The state and input are raw JSON values. The history is separate. It is a map from location to a list of events.

6. Resonate

Resonate is a durable execution platform built on durable promises and durable tasks. A durable promise is a named record with a state, a parameter, a value, a set of tags, and a deadline. A durable task is the executable half of the same record. A worker acquires the task with a lease and a version. The server resumes the task when the promises it waits on settle. The source for these statements is the Resonate exploration at ../../src.resonate/markdown/README.md:8-10 and ../../src.resonate/markdown/03-durable-promises-and-tasks.md:13-24. The underlying Resonate repository is at commit 9c72d818.

Resonate is not an Actor runtime. It does not own the placement of user code. It owns the durable record and the dispatch of work to a worker. The worker is a separate process. This is the key difference from Rivet. Rivet owns the Actor, the placement, the request route, and the state. Resonate owns the promise, the task, and the wake.

6.1 The promise and the task

A durable promise has five states: pending, resolved, rejected, rejected_canceled, and rejected_timedout. A durable task also has five states: pending, acquired, suspended, halted, and fulfilled. The version is the fence. A worker that lost its lease holds an old version. Its write is refused. The source is ../../src.resonate/markdown/03-durable-promises-and-tasks.md:12-26 and ../../src.resonate/markdown/03-durable-promises-and-tasks.md:212-228.

The task transitions are these. task.acquire moves pending to acquired. task.heartbeat keeps acquired. task.suspend moves acquired to suspended when all awaited promises are pending. When an awaited promise settles, resumeOne moves the task from suspended to pending. task.release or a lease timeout moves acquired to pending. task.halt moves any non-fulfilled state to halted. task.continue moves halted to pending when the promise is still pending. When the task's own promise settles, the task moves from any non-fulfilled state to fulfilled. The source is ../../src.resonate/markdown/03-durable-promises-and-tasks.md:160-197 and ../../src.resonate/markdown/03-durable-promises-and-tasks.md:417-438.

The one-row model is the important design choice. A promise and its task share one identifier. The promise face holds the promise state, the parameter, the value, the tags, the timeouts, and the callbacks. The task face holds the task state, the version, the time to live, the process identifier, the lease deadline, the retry deadline, and the resume list. The tags decide the semantics. The resonate:target tag carries a worker address. It makes the promise runnable, and it also makes the promise awaitable. The resonate:timer tag makes a deadline resolve the promise instead of rejecting it. The resonate:scope tag with value global makes the promise awaitable. The source is ../../src.resonate/markdown/03-durable-promises-and-tasks.md:20-68.

This model is close to an Actor in one way. Both have a stable identity and a durable record. It is different in another way. An Actor processes commands. A promise stores a result. The Actor has a mailbox and mutable state. The promise has a state machine and a value. An Actor can serve many calls over its life. A promise usually represents one call or one step.

6.2 The server and the control plane

These are Sibling source claims. Each paragraph cites its exploration file. The Resonate server is a plugin host. A port here is a Rust trait that a plugin implements. A network port is called a socket. The four port roles are a server, a worker, a gateway, and a router. The gateway role accepts a request from a transport and sends it to the server role. The server role applies one protocol request. The worker role delivers one message to an address. The router role selects a worker for an address scheme. A route table is a shared table of HTTP routes that plugins add to (../../src.resonate/markdown/01-architecture.md:18-29). The composition root loads the plugins and starts them (../../src.resonate/markdown/01-architecture.md:40-51).

The address scheme is the text before ://, such as http or poll (../../src.resonate/markdown/01-architecture.md:26). A concrete request path is this. A client sends an HTTP request to the gateway port. The gateway accepts it. The shared route table sends it to the server port. The server port applies one protocol request. When the protocol needs a worker message, the server port gives the address to the outbound worker port. The outbound worker port asks the router for a worker. The router reads the scheme and returns the matching worker plugin. The worker plugin delivers the message. This is the path that the four ports describe. The source is ../../src.resonate/markdown/01-architecture.md:40-51.

The Rivet control plane is also a plugin-like host, but the comparison stops there. The Rivet control plane places Actors on envoys, routes client requests, and stores Actor state. The Resonate server does not place user code. It stores promises and tasks and delivers messages to a worker that the user runs. A Resonate worker pulls or receives a task. A Rivet Actor runs where Pegboard placed it.

The Wake mechanism also differs. Resonate does not keep a callback function that it fires. It keeps a callback record on the promise. When the promise settles, the server removes that record and calls resumeOne. resumeOne moves the task from suspended to pending and sets a retry deadline. The server sweep reads the deadline and emits an execute message (../../src.resonate/markdown/03-durable-promises-and-tasks.md:405-411). A server sweep is the periodic loop that fires timers, expires leases, and retries tasks (../../src.resonate/markdown/01-architecture.md:31). The wake is a state that the server reads, not an event that it delivers. If the server dies between the callback and the dispatch, the pending state and the deadline survive. A new server reads them and dispatches.

Rivet wakes an Actor through Guard and Pegboard. The request is the wake. The Actor workflow also has an alarm time for a scheduled wake. The Resonate model is a dependency graph of promises. The Rivet model is a keyed process with a queue and a state.

7. Electric and the durable stream model

Electric Durable Streams is an append-only log with offsets. A stream has six properties: append-only, ordered, typed, addressable, closeable, and forkable. Typed means the stream has one content type, set at creation. Addressable means the stream is reachable at a URL. The six operations are create, append, close, read, delete, and head. A fork is a property, not one of the six operations. A fork is a new stream that shares a prefix with a source stream at a chosen offset. Head returns stream metadata and the current tail without a body. An offset is an opaque token. A client stores an offset and returns it to resume. The source is the Electric exploration ../../src.electric/markdown/03-the-durable-stream-primitive.md:11-39 and ../../src.electric/markdown/03-the-durable-stream-primitive.md:86-101.

The stream is the durable unit. It does not execute application code. A consumer reads the log and decides what to do. The producer appends facts. Many readers can read the same log from their own offsets. A subscription can send a webhook or write a wake record. A wake record is one JSON message with the subscription identifier, the changed stream, the generation, and a timestamp. A runner claims the wake with a lease. A runner is the process that claims and processes wakes. A lease is a time-limited claim. An expired lease makes the wake claimable again. A generation is a subscription counter that increases on every wake. A stale generation is rejected. The source is ../../src.electric/markdown/03-the-durable-stream-primitive.md:159-195 and ../../src.electric/markdown/durable-streams/03-live-reads-and-subscriptions.md:406.

An Actor is a process with a mailbox and a state. The mailbox orders commands. The Actor executes one command and changes its state. The state is the result of the commands. A client can call the Actor and wait for a reply. The Actor can broadcast to connected clients. The source is ./README.md:7-12 and ./README.md:33-48.

The two models answer different questions. A stream answers "what happened, in what order?" An Actor answers "what should happen next, for this key?" A stream is good at distribution, sync, replay, fan-out, and audit. An Actor is good at command execution, transactions, timers, and per-key state.

7.2 Where each model fits

A stream is the right choice for seven jobs.

  1. Change distribution. One writer appends a change. Many clients read it.
  2. Sync. A client stores an offset and catches up after a disconnect.
  3. Audit. The log keeps every fact in order.
  4. Fan-out. A subscription sends each new event to a target.
  5. Forking. A conversation or document branches at an offset without a copy.
  6. Idempotent append. A producer sequence number prevents a duplicate.
  7. Cross-language consumers. Any HTTP client can read the log.

An Actor is the right choice for six jobs.

  1. Command execution. A client calls an action and waits for a result.
  2. Per-key state. A user, room, document, or tenant has one owner.
  3. Transactions. Several rows change together in SQLite.
  4. Timers and cron. The Actor sets an alarm and wakes on schedule.
  5. Realtime broadcast. The Actor holds WebSocket connections.
  6. Durable workflows. Gasoline replays a multi-step operation.

The two models combine well. An Actor can append to a stream. A stream consumer can call an Actor. The Electric agent runtime does exactly this. An entity stream is the stream for one agent entity. The agents-server writes an inbox event to that stream. A webhook subscription then wakes the runtime. The runtime is the process that reads the stream from its last acknowledged offset, runs the entity handler, and appends the results to the same stream. The source is ../../src.electric/markdown/README.md:97-110. The stream is the durable memory of the agent. The runtime is the process that acts on it.

Aha: A stream is shared memory. An Actor is a private memory with one writer. The stream can serve a thousand readers from one history. The Actor can make a decision that no reader can make. A design that needs both should use both. The Actor writes the decision to the stream, and the stream distributes it.

8. celld

celld is a self-hosted implementation of the Cloudflare Workers platform. A cell is one Durable Object instance. A cell has its own SQLite database, one owner node at a time, and one fencing epoch. An epoch is a number that increases when ownership changes. A writer from an older epoch is stale. The next restore clips the stale writes at the cut. The cut is the last transaction identifier that the new chain covers. The bucket holds a chain of Lite Transaction (LTX) segments across these epochs. A snapshot is one segment that carries every page of the database at one transaction. A restore walks the chain from the newest epoch down to a snapshot (../../src.celld/markdown/05-cell-storage-and-durability.md:7-17). The bucket is the eventual home of every durable byte. The bucket is also the proof of an acknowledgement in bucket mode. In fleet mode, a follower fsync is the proof, and the bucket upload catches up later (../../src.celld/markdown/05-cell-storage-and-durability.md:685-687). A follower is another node that receives each write. fsync is the system call that forces the bytes to disk. The source is ../../src.celld/markdown/README.md:3-13 and ../../src.celld/markdown/05-cell-storage-and-durability.md:1-9. The celld repository is at commit 8702f6d186c77698dbfb30cf29e3b1922a88f008, version 0.6.3. The source is ../../src.celld/markdown/README.md:15-19.

celld is the closest system to Rivet in this set. Both keep one SQLite database per keyed unit. Both write a log. Both use a bucket. Both restore a unit after a failure. The differences are in the owner model, the write proof, and the runtime.

8.1 One cell and one Actor

The celld activation path is explicit. The cell scope is the class name, a colon, and the identifier (../../src.celld/markdown/04-durable-objects.md:367-383). The application calls namespace.get(id) and receives a stub. The first fetch or Remote Procedure Call (RPC) activates the cell.

The owner node reads cells//own.json. The record names a node and an epoch. The node decides whether another owner is live by reading that owner's lease at nodes/.json. A lease is dead when its recorded expiry is at or before the reader's clock (../../src.celld/markdown/06-ownership-failure-and-rebalancing.md:212-216). If the owner is live, the request forwards to that node. Otherwise the node claims the next epoch. A missing record claims epoch 1. A released record or a dead owner claims epoch + 1. A record that names this node also claims epoch + 1 for a new session. Only a clean local reload reuses the same epoch (../../src.celld/markdown/04-durable-objects.md:429-437).

The restore then runs. It starts at the newest ownership record. It reads the epoch, lists the epoch prefixes, and builds a chain from the newest epoch down to one that opens with a snapshot (../../src.celld/markdown/05-cell-storage-and-durability.md:690-730). It opens the log prefix cells//ltx/e/. It builds the JavaScript instance (../../src.celld/markdown/04-durable-objects.md:438-440).

The Rivet path is different. A request arrives at Guard. Guard asks Pegboard for the Actor. Pegboard reads the Actor workflow state. If the Actor is running and connectable, the request goes to the envoy. If the Actor is sleeping, Guard sends a wake signal. It then holds the client request. If the Actor is not connectable for another reason, Guard holds the client request and waits for a ready event. Section 8.1.1 gives the full path. If the Actor does not exist, Guard returns not found. Guard does not create the Actor on a plain get path. Only a getOrCreate query creates it. The Actor state is in the workflow state and the Actor's storage. There is no ownership record in a bucket. The placement decision is in Pegboard, not in a shared object. The source is docs/general/content/architecture.mdx:42.

8.1.1 The Rivet request path during a start

The client-visible behavior is a wait, not a queue in the Actor. The wait happens in Guard. The request is not stored in the Actor mailbox before the Actor starts. The mailbox holds commands after the Actor runs. Guard holds the request open. Guard subscribes to the ready, stopped, failed, and destroy events before it fetches the Actor (engine/packages/guard/src/routing/pegboard_gateway/mod.rs:364-405). It fetches the Actor record with get_for_gateway (engine/packages/guard/src/routing/pegboard_gateway/mod.rs:407-428). A None result means no Actor record exists. Guard returns Actor::NotFound (engine/packages/guard/src/routing/pegboard_gateway/mod.rs:426-428).

If the Actor exists but is not connectable, Guard waits. A stopped event causes a rewake signal. Guard allows at most eight rewake attempts (engine/packages/guard/src/routing/pegboard_gateway/mod.rs:623-683). A failure event returns the Actor error. A destroy event returns ActorDestroyedWhileWaitingForReady. The wait also has a ready timeout (engine/packages/guard/src/routing/pegboard_gateway/mod.rs:685-710). The client sees one of these errors, or it sees the first reply after the Actor becomes ready. The request is not rejected during a normal start. It waits within those limits.

A getOrCreate query is different. Guard resolves the key first. If no Actor exists, it calls the create operation (engine/packages/guard/src/routing/pegboard_gateway/resolve_actor_query.rs:119-180). That operation dispatches the version 2 workflow, which allocates the Actor (engine/packages/pegboard/src/ops/actor/create.rs:105-124).

8.2 The write proof

The celld write proof is the most important difference. celld has two modes. The operator selects one with CELLD_DURABILITY. The values are bucket and fleet. The default is fleet (../../src.celld/markdown/05-cell-storage-and-durability.md:595-596).

A level 0 segment holds captured transactions before compaction. Compaction combines level 0 segments into a level 1 segment (../../src.celld/markdown/05-cell-storage-and-durability.md:69). The capture loop reads committed Write-Ahead Log (WAL) frames. It writes them as a level 0 segment. A write becomes an LTX segment at that point (../../src.celld/markdown/05-cell-storage-and-durability.md:44, ../../src.celld/markdown/05-cell-storage-and-durability.md:347). A write that is not yet in a segment has a durability ticket. The output gate is the code that holds the reply. It waits until a proof covers that ticket (../../src.celld/markdown/05-cell-storage-and-durability.md:192-232). The position that the gate compares is the committed-write position. It is the sum of total_changes, data_version, and schema_cookie. It is a local counter. It is not the LTX transaction identifier (../../src.celld/markdown/05-cell-storage-and-durability.md:205-216).

In fleet mode, the owner sends each write to one or two followers. A follower writes the bytes to its own disk and calls fsync. Only then does it acknowledge. The owner releases the reply when every follower in its current set has acknowledged (../../src.celld/markdown/05-cell-storage-and-durability.md:644-655). The bucket upload happens later, outside the acknowledgement path. The acknowledged write can exist only on the owner and its followers until the upload catches up (../../src.celld/markdown/05-cell-storage-and-durability.md:685-687).

In bucket mode, the owner uploads the segment to the bucket and reads the ownership record once. The upload is the durability point. The read is not optional. A node that was fenced before the upload can write into an old prefix that a new owner will not read. The read confirms that own.json still names this node at this epoch. Otherwise the node refuses the reply (../../src.celld/markdown/05-cell-storage-and-durability.md:629-639).

The timeline is short. Bucket mode: commit, capture and upload the segment, read own.json, release the reply. Fleet mode: commit, send the write to the followers, each follower fsyncs and acknowledges, release the reply. The source is ../../src.celld/markdown/README.md:27-49.

Rivet acknowledges a write after the control plane has copied it to several instance disks (README.md:68). The benchmark setup used two of three instances (README.md:155). UniversalDB is the transactional store, and the architecture page says the control plane writes to replicated disks (docs/general/content/architecture.mdx:48). This document does not identify the replication protocol for general UniversalDB keys.

Epoxy is a separate consensus layer in the same repository. It is a geo-distributed key-value store for its own keys. Its consensus records commit in UniversalDB (engine/packages/epoxy/README.md:51). Its consensus protocol is single-decree Fast Paxos, run independently per key (engine/packages/epoxy/README.md:3). Paxos is a family of protocols that make replicas agree on one value (General knowledge). Fast Paxos is a variant that can commit in fewer message delays (General knowledge). Single-decree means the replicas agree on one value, not on a shared log. A fresh key commits in one round trip; a key with in-flight state uses two (engine/packages/epoxy/README.md:3, engine/packages/epoxy/README.md:19-23). Epoxy is not EPaxos. The code inherited the PreAccept name from EPaxos ancestry, but that phase was always standard Paxos Phase 2a (engine/packages/epoxy/README.md:27). Phase 2a is the accept phase, in which a leader sends a value to the acceptors (General knowledge). EPaxos is a different protocol that orders commands across keys (General knowledge). It is only a reference for cross-key ordering (engine/packages/epoxy/README.md:42). In this snapshot Epoxy serves Actor key reservation only (engine/packages/epoxy/README.md:37-42). It is not the general write path.

A UniversalDB transaction can name several keys. The store applies all named keys in one transaction as one atomic unit on the replica that runs it. This document does not establish how that multi-key transaction becomes visible on other replicas. The source describes per-key consensus for Epoxy, and Epoxy serves key reservation only. This comparison therefore claims per-key durability, not cross-key atomicity on the replicated layer.

The bucket is not on the write path. A background process moves pages to the bucket. The source is README.md:68.

The trade is clear. celld pays a bucket round trip in the bucket proof, or a follower fsync in the fleet proof. Rivet pays a replicated write across control plane disks. The benchmark setup uses two of three instances (README.md:155). celld gets a proof that a specific bucket object holds the write. Rivet avoids a bucket round trip on the write path. A slow or unavailable bucket does not block an acknowledged Rivet write. This document labels the trade as analysis. Neither source publishes a matched write-latency benchmark.

8.3 Where celld is stronger

celld is stronger on three axes.

These are Sibling source claims. Each item cites its source file.

  1. Workers compatibility. celld runs Worker modules and the Durable Object

API. A user can move a Cloudflare Worker to celld with a subset of the API. The exploration documents the gaps in ../../src.celld/markdown/10-limitations-and-compatibility.md. Rivet does not implement the Workers API. RivetKit is the Rivet client and Actor library (README.md:326).

  1. Durability proof. In bucket mode, the bucket is the proof of every

The source is ../../src.celld/markdown/README.md:57-84 and ../../src.celld/markdown/05-cell-storage-and-durability.md:685-687. Rivet's proof is a quorum of control plane disks, and the bucket catches up later.

  1. Ownership record. celld puts the owner in a conditional write to the

8.4 Where Rivet is stronger

Rivet is stronger on three axes.

  1. Language runtime freedom. Rivet runs on native Node.js, Bun, or Rust.

celld runs JavaScript in V8 with the Workers API. A Rust Actor, a native package, or a Node.js addon works in Rivet and does not work in celld.

  1. Density and scheduling. Rivet publishes 72.4 KB per Actor and a 4.37 ms

wake. It schedules Actors with Pegboard, pool selectors, data center inputs, drain, and cron. celld places a cell by ownership and lease. It does not have a general scheduler for user code.

  1. Write-path independence. The Rivet bucket is not on the write path

(README.md:68). A slow bucket does not block an acknowledged write. celld's bucket proof does block the acknowledgement on the upload. The fleet proof removes the bucket from the ack, but it needs a live follower. In fleet mode, the upload is asynchronous after the acknowledgement.

The weaker celld points are the V8-only runtime, the compatibility gaps, and the operational complexity of ownership and fencing. The weaker Rivet points are the shared-process isolation, the younger code, and the control plane protocol. Both systems are young. Neither is a mature platform in the way that Kubernetes or Cloudflare is. That maturity statement is General knowledge and a judgment. This document did not measure it.

9.1 When to choose each

Choose Rivet when the workload is a large number of keyed, stateful processes. Examples are one agent per user, one session per conversation, one room per document, or one tenant per customer. Choose it when the team wants standard Node.js, Bun, or Rust, wants self-hosting, and wants SQLite per key. Do not choose it when the workload needs a hard container boundary or a GPU per unit.

Choose Cloudflare Durable Objects when the application already runs on Cloudflare, the keyed unit fits the platform limits, and the team does not want to operate infrastructure. Do not choose it when the data per key is larger than the stated limit, when the code needs native packages, or when the deployment must be self-hosted.

Choose Kubernetes when the workload is a general container workload. Examples are databases, brokers, batch jobs, machine-learning services, and mixed services with sidecars. Choose it when the team needs isolation, GPU scheduling, network policy, or a mature ecosystem. Do not choose it when the unit is a millions-of-keys stateful process and the container overhead dominates the work.

Choose Temporal when the problem is a long-running workflow across many services. Examples are order fulfillment, payment authorization, and human-in-the-loop approval. Choose it when the team needs many language SDKs and a mature visibility tool. Do not choose it when a single binary and a bucket are a hard requirement.

Choose Resonate when the problem is durable promises across services and the team wants an executable formal model or a choice of storage backends. Choose it when a worker fleet already exists. Do not choose it when the application needs a per-key SQLite database or automatic placement of user code.

Choose Electric Durable Streams when the problem is data distribution, sync, fan-out, audit, or replay. Choose it when many readers need the same ordered history. Do not choose it when the problem is command execution with per-key transactions. Use it with an Actor when both are needed.

Choose celld when the application targets the Cloudflare Workers API and the team wants to self-host that platform. Choose it when the bucket proof matters more than write-path independence. Do not choose it when the code needs native packages or a language other than JavaScript.

10. Where Rivet is weaker

This section states the weaknesses plainly. A comparison that only lists strengths is not a comparison.

10.1 Rivet is young

The source is at version 2.3.31, commit 4a58441c. The version and the commit metadata are in ../spec.md:20-22. The maturity statements in this paragraph are general knowledge, not verified here. Kubernetes has a longer public history. Cloudflare Durable Objects is a managed service. Resonate publishes an executable formal model. Temporal publishes many SDKs. Rivet has a large codebase and a test suite, but it has less production history. A young system has more unknown failure modes. The source does not state a stability guarantee for the version 2 Actor path.

10.2 Rivet has fewer isolation guarantees than a container

An Actor is a task inside a node process. It is not a container, a micro Virtual Machine, or a sandbox. The README says a generated, untrusted code Actor gets its own database and filesystem. The source is README.md:70. That is a product claim. It is not a kernel boundary. Two Actors in one process share the process address space if the runtime or a native module breaks isolation. A container has cgroups, namespaces, seccomp, and often a separate kernel or micro Virtual Machine. A user who runs untrusted code must use a sandbox. The agentOS product is the Rivet answer, but it is a separate product. See 17 The product family.

10.3 The bucket is a single dependency

The README says the bucket is the only external durable store. The source is README.md:262. That is a strength in normal operation and a weakness in failure. If the bucket is unavailable, the control plane cannot read cold Actor pages. The write path does not wait for the bucket, but recovery does. A bucket outage is a single dependency for cold data. This snapshot does not establish whether a new Actor needs a bucket read at create. Depot resolves its bucket pointer lazily on first use (engine/packages/depot/README.md:31-34). The README does not state a degraded mode for a bucket outage.

The bucket is also a cost and a security boundary. The operator must choose Amazon Simple Storage Service (S3), Google Cloud Storage (GCS), Azure Blob Storage, or an S3-compatible store. The operator must manage credentials, versioning, lifecycle, and access policy. The source is README.md:262. A self-hosted deployment needs this skill.

10.4 The protocol is complex

Rivet has a runner protocol, an envoy protocol, a public API, and a workflow history format. The envoy protocol has versioned message types. The repository has a versioned.rs file with conversions between versions. The source is engine/packages/runner-protocol/src/versioned.rs. A reader who debugs a start failure must follow Guard, Pegboard, the Actor workflow, the envoy, and the Actor runtime. A simpler system with one process and one database has a shorter failure path. The complexity buys density and self-hosting. It also raises the cost of an integration and a debug session.

10.5 Self-hosting needs operational skill

The README says self-hosting means four things: identical control plane instances, a persistent disk per instance, one bucket, and the nodes. The source is README.md:218. The benchmark page says three control plane instances on raw NVMe in three zones. The source is docs/general/content/benchmarking.mdx:13-18. The benchmark page also says Kubernetes does not give pods raw NVMe, so it cannot reproduce the numbers. The source is docs/general/content/benchmarking.mdx:39. A team that runs Rivet on a managed Kubernetes cluster may not get the published latency. The operator must understand disks, zones, quorum, bucket latency, and node pools. Rivet Cloud and Bring Your Own Cloud (BYOC) remove some of this work. They do not remove the need to understand the model.

10.6 The storage claim has a path-dependent limit

The README says storage is bottomless. The source is README.md:68. The limits document has a narrower rule. Remote SQL is the mode in which the SQLite queries run on the control plane, not inside the Actor runtime. The maximum database size for remote SQL is 256 MiB (65,536 pages). The page size is 4 kibibytes (KiB), so 65,536 pages give 256 MiB. That limit applies when queries run on the control plane. It always applies on the WebAssembly runtime. It applies on a native runtime when sqlite.backend is set to "remote". The source is docs/actors/content/docs/limits.mdx:87. The same document limits one transaction to 32,768 changed pages, or 128 MiB. The source is docs/actors/content/docs/limits.mdx:84.

The WebAssembly runtime is the RivetKit build for runtimes that cannot load native binaries. A user selects it with runtime: "wasm" (docs/actors/content/docs/wasm-vs-native-sdk.mdx:7-12). The limits document does not state why the remote limit always applies on that runtime. This document infers that the WebAssembly build cannot load the native SQLite binding.

A fair statement is this. The native SQLite path moves pages to the bucket and has no fixed 10 GB limit in the README. The WebAssembly and remote SQL path has a 256 MiB database limit. A user who needs a very large database must use the native path. The README does not make this distinction. The limits document does. This document follows the limits document, which is the detailed source for this rule. This snapshot does not find a code constant for the 256 MiB database limit.

The diagram does not show latency. It shows the dependency. A Rivet write depends on a replicated commit across control plane instances. The benchmark setup uses two of three instances (README.md:155). A Durable Object write depends on the Cloudflare storage service. A pod write depends on the CSI driver. A Temporal write depends on its database. A Resonate write depends on its storage engine. An Electric append depends on the deployment. The Node.js server uses a .log file and an LMDB store. The Cloudflare server uses Durable Object SQLite. The Caddy plugin uses a segment file and bbolt. These are three deployments, not one deployment. A celld write depends on a follower fsync in fleet mode or a bucket upload in bucket mode. The fleet mode upload is asynchronous after the acknowledgement.

Aha: The bucket appears in both Rivet and celld, but it plays a different role. In Rivet, the bucket is the cold tier. It is not on the write path. In celld, the bucket is the eventual home of every byte. It is also the proof of an acknowledged write in bucket mode. In fleet mode the proof is a follower fsync, and the upload catches up later. The same component lets one system avoid a bucket round trip on the write path and gives the other a stronger durable proof. The design choice, not the component, decides the guarantee.
