15 Deployment and self-hosting

In the documented model, a Rivet cluster is a set of identical rivet-engine processes, one persistent disk for each process, one object storage bucket for the cluster, and the node processes that run Actors. The documented model has no separate database and no message bus. The open-source build in this commit is different: UniversalDB runs on RocksDB for one instance, or PostgreSQL plus NATS for several instances. This document shows the documented model and the open-source requirement as separate things. It covers the minimum production topology, the node side, the three delivery shapes, the upgrade order, and the recovery procedure for each part.

The source of truth is the core repository at commit 4a58441c50d1ce20d8803cfb1ab7c3285a5141d6, version 2.3.31. A citation has the form path:line or path:line-line. All paths are relative to /Users/darkvoid/GitSources/src.Rivet/rivet.

1. The deployment model

1.1 The four parts

The project README states the model in one paragraph. It names four parts.

# README.md:218
**Every option runs the same binary. The only difference is who operates it.** Self-hosting means running four things: identical control plane instances (one to try it, three or more in production), a persistent disk per instance that holds recent writes and the instance's identity, one bucket per cluster on S3, Google Cloud Storage, Azure Blob Storage, or any S3-compatible store, and the nodes that run your Actors. There is no database to run and no message bus. Local dev matches production: the same binary, APIs, and control-plane behavior from laptop to production.

The word "database" has two senses in this document. In the README quote it means a separate database server that the operator must run. Rivet does not need one in the documented model. In the open-source build, the engine still writes its own rows to a local database file, which is RocksDB by default (engine/packages/config/src/config/db/mod.rs:17-20). That local file lives on the instance disk. Section 12.4 treats the disk as a failure point for this reason.

A client can reach any instance through the load balancer. The Actor may be connected to a different instance. For Actor traffic, Guard does not forward the request to the instance that owns the node. It publishes the request to the Universal Pub/Sub topic pegboard.envoy.{namespace_id}.{envoy_key}, and the instance that holds the node WebSocket consumes it (engine/packages/pegboard/src/pubsub_subjects.rs:113-138). The reply returns on pegboard.gateway.{gateway_id} (engine/packages/pegboard/src/pubsub_subjects.rs:86-111). This is why a multi-instance cluster needs a pub/sub service, and why the open-source Kubernetes guide deploys NATS. The dashed peer_url edges carry Epoxy and namespace calls between datacenters. They do not carry Actor traffic.

This is the minimum production topology in the project benchmark: three instances, one per zone, and one bucket in the same region (README.md:155, docs/general/content/benchmarking.mdx:13-18). The bucket is the shared store in the documented model. In this open-source commit, the same three-instance shape needs PostgreSQL and NATS instead (section 1.3).

Every instance runs every service. Three of them need a note.

bootstrap is an Oneshot service, so it runs once per process at start and again only if it fails (engine/packages/service-manager/src/lib.rs:207-238). It is safe on all three instances. The setup steps create records only when they are absent, and the coordinator step returns early when the current datacenter is not the leader (engine/packages/bootstrap/src/lib.rs:17-66).

workflow_worker runs on every instance. Each worker pulls tasks from the shared workflow store (engine/packages/workflow-worker/src/lib.rs:4-13). pegboard_outbound runs on every instance and serves serverless pools that have an external endpoint.

1.2 What replaces the database and the message bus

The documented model does not run PostgreSQL or NATS. The README says that UniversalDB replaces the database, that the write path plus the bucket replaces the message bus, and that instances find each other through the bucket (README.md:218, README.md:262).

Removed systemReplacement in the documented modelCode evidence

Message busUniversalDB transactions and a durable write logREADME.md:262
Service discoveryThe bucket: instances find each other through itREADME.md:262

The topology configuration is a separate thing. It does not discover instances. It lists the datacenters, their labels, their public and peer addresses, and which one is the leader (engine/packages/config/src/config/topology.rs:155-179). An operator writes it by hand. Epoxy uses it to address replicas. It is not a service registry.

The open-source tree also has two optional systems. PostgreSQL can replace the local file system database. NATS can carry UniversalDB commit traffic between instances. Both are selectable in the configuration.

Aha: The documented model moves the durable database into the bucket, so the bucket is not a backup. It is the database. The local disk is a cache and a write buffer. An operator who treats the bucket as an optional archive will build a cluster that loses data when an instance disk fails. The obvious alternative is a conventional database cluster. 2.3 Consistency and permissions

The source does not state a consistency requirement for the bucket. The source does not state an Identity and Access Management (IAM) policy for the bucket. The internal document states only that Enterprise reads and writes cold rows and that open source keeps the schema (docs-internal/engine/oss-to-ee-upgrade.md:9-19).

The compaction constants show two bucket operations: upload an object and delete an object. The grace constant also names an "unpublish" step, but the source does not show that step as a bucket call. A bucket policy must permit the upload and the delete. The repository does not give a policy document and does not state whether a list permission is needed.

Unverified: the repository does not state the required bucket consistency model. Do not assume read-after-write, list-after-write, or cross-region replication from this source. The benchmark uses a bucket in the same region as the control plane (docs/general/content/benchmarking.mdx:18). That is a performance choice, not a consistency statement.

3. The instance disk

3.1 What is stored locally

The local database is a RocksDB store. The driver opens it at the configured path. The default path is the user data directory plus rivet-engine/db, or ./data/db when the user data directory is unavailable (engine/packages/config/src/config/db/mod.rs:29-36).

// engine/packages/pools/src/db/udb.rs:19-68
#[tracing::instrument(skip(config))]
pub async fn setup(config: &Config) -> Result<Option<UdbPool>> {
	let db_driver = match config.database() {
		config::Database::Postgres(pg) => {
			// A NATS config (set directly or inherited from the UPS config in
			// `validate_and_set_defaults`) selects UniversalDB multi-node mode.
			let nats = pg
				.nats
				.as_ref()
				.map(|nats| universaldb::driver::postgres::NatsConfig {
					addresses: nats.addresses.clone(),
					username: nats.username.clone(),
					password: nats.password.as_ref().map(|p| p.read().clone()),
					client_capacity: nats.client_capacity,
					subscription_capacity: nats.subscription_capacity,
				});

			let postgres_config = universaldb::driver::postgres::PostgresConfig {
				connection_string: pg.url.read().clone(),
				ssl_config: pg.ssl.as_ref().map(|ssl| {
					universaldb::driver::postgres::PostgresSslConfig {
						ssl_root_cert_path: ssl.root_cert_path.clone(),
						ssl_client_cert_path: ssl.client_cert_path.clone(),
						ssl_client_key_path: ssl.client_key_path.clone(),
					}
				}),
				nats,
				pool_max_size: None,
			};

			Arc::new(
				universaldb::driver::PostgresDatabaseDriver::new_with_config(
					config.clone(),
					postgres_config,
				)
				.await?,
			) as universaldb::DatabaseDriverHandle
		}
		config::Database::FileSystem(fs) => {
			Arc::new(universaldb::driver::RocksDbDatabaseDriver::new(fs.path.clone()).await?)
				as universaldb::DatabaseDriverHandle
		}
	};

	tracing::debug!("udb started");

	let db = universaldb::Database::new(db_driver).with_throttle(throttle_config(config));

	Ok(Some(UdbPool { db }))
}

UniversalDB stores every durable row that the control plane owns. This includes Actor metadata, runner records, workflow state, and the version keys in section 8. The user-facing Actor Structured Query Language (SQLite) pages go through Depot, which also uses UniversalDB as its key space. Document 07 UniversalDB and buckets covers that layout.

The SQLite page cache and the Depot rows live in the same UniversalDB store. On the FileSystem backend, that store is the local disk. Depot reads and writes pages through UniversalDB. The compaction code moves hot pages toward the cold tier when that tier exists.

3.2 Why it must persist

A restart with the same disk continues the same cluster state. A restart with an empty disk starts a new database. For the FileSystem backend, the disk is the only copy of the cluster key space. Loss of that disk is loss of the cluster, unless an earlier copy exists.

This is why the deployment guides mount a volume. The Virtual Machine guide uses a named Docker volume and points the file system path at it.

The datacenter label is not disk state. It is configuration: the operator sets topology.datacenter_label, and epoxy_replica_id() returns that value (engine/packages/config/src/config/mod.rs:345-353). A replacement instance must receive the same label.

The cluster-wide version floor is different. It is EngineVersionKey in UniversalDB (engine/packages/version-management/src/keys.rs:4-33). On the FileSystem backend, the disk holds that row. If the disk is lost, the floor is lost unless the disk is restored.

For an operator, the practical rule is the same for both values. Keep the disk, and keep the configuration in source control. If the disk is lost, recover from the shared database or a backup. If the label is lost, read it from the configuration you saved.

4. The node and the runner

4.1 What a node is

The documentation defines a node as “a long-running process running your app with the Rivet Software Development Kit (SDK)”, started with registry.start() (docs/general/content/nodes.mdx:7). The node opens an outbound connection to the control plane and hosts the Actors that the scheduler assigns to it.

A node needs no public Universal Resource Locator (URL) and no inbound port for Actor traffic (docs/general/content/nodes.mdx:42). The control plane reaches the node over the connection that the node opened. This is why a node can run behind Network Address Translation (NAT) or in a private subnet.

A node joins a node pool. The pool must exist before the node connects. The control plane refuses a node whose pool does not exist (docs/general/content/nodes.mdx:25). The engine has no localhost exception: the connection handler returns WsError::NoRunnerConfig when the pool lookup is empty (engine/packages/pegboard-envoy/src/conn.rs:110-122). The exception is in RivetKit, which creates the pool itself when the endpoint is on localhost (docs/general/content/nodes.mdx:25).

Create the pool before the first production node. A pool name defaults to default (docs/general/content/environment-variables.mdx:24).

4.3 Registration, step by step

The envoy path is the newer path. Its registration sequence is the clearest example of how a node joins a cluster.

The sequence uses names that need a definition. envoy_key is a random identifier that the client generates for one registration. The client keeps it for the life of the connection and replaces it on rotation (engine/sdks/rust/envoy-client/src/context.rs:58-69). runner_key is the same idea on the legacy path: the TypeScript runner makes a random Universally Unique Identifier (UUID) at construction (rivetkit-typescript/packages/engine-runner/src/mod.ts:205). RoutingOutput is the Guard return type. RoutingOutput::CustomServe(PegboardEnvoyWs) means "this request belongs to the envoy service, hand the socket to it" (engine/packages/guard/src/routing/envoy.rs:56-62). init_conn is the server function that validates the URL, resolves the namespace, loads the pool, and claims the registration (engine/packages/pegboard-envoy/src/conn.rs:90-339). Conn is the per-connection struct that the server creates after the claim (engine/packages/pegboard-envoy/src/conn.rs:31).

5.1 Self-host

In the documented self-host model, the operator runs all four parts. The operator provides the instances, the disk, the bucket, and the nodes. The operator also provides the public endpoint and the Transport Layer Security (TLS) certificate.

The open-source self-host procedure in this repository is different. One instance uses a local RocksDB path. More than one instance uses a shared PostgreSQL database and NATS (section 1.3). No guide in this repository uses a bucket as the only durable store.

The README says one instance is enough to try Rivet, and three or more are needed in production (README.md:218). The benchmark uses exactly three instances, one per availability zone, and acknowledges each write at two of the three (README.md:155, docs/general/content/benchmarking.mdx:15).

5.2 Rivet Cloud

In Rivet Cloud, Rivet operates the control plane. The README says there is “nothing to operate” for the application, or the operator can bring their own nodes and let Rivet Cloud provide the control plane and routing layer (README.md:201).

The README does not state where Rivet Cloud stores Actor data. The repository does not contain the cloud deployment configuration. Do not infer a bucket location from this source.

The sample public_url is a placeholder. It is http://localhost:6420 (self-host/control-plane/kubernetes/02-engine-configmap.yaml:22). The NodePort type exposes the api peer on 30421 as well as Guard on 30420. A NodePort opens it on every node. Restrict port 30421 with a network policy, or publish only Guard, before production.

The manifest README says the bundled PostgreSQL is a single-replica StatefulSet and recommends a managed service for production (self-host/control-plane/kubernetes/README.md:31).

The 25-second pod grace period is shorter than the Guard shutdown budget. The Guard budget defaults to 10 minutes (engine/packages/config/src/config/runtime.rs:192-194). The 15-second preStop sleep also comes from the same 25 seconds. Kubernetes sends SIGKILL with about 10 seconds left for Guard. Raise terminationGracePeriodSeconds above the Guard budget, or lower the budget, before production use.

The 10-minute force timer and the 25-second grace period do not conflict in the way they appear to. The force timer is an upper bound inside the process. It fires only if a graceful service does not stop (engine/packages/service-manager/src/lib.rs:369-405). Kubernetes stops the process first, so the force timer never fires under this manifest. The protocol hold-back does not depend on a graceful stop either. If SIGKILL removes the heartbeat, the entry expires after 30 seconds (section 8.3). The grace period therefore changes how long requests have to drain. It does not change the version floor.

7.1 Add an instance

Adding an instance has two different meanings. An instance in an existing datacenter adds request capacity and shares that datacenter's replica identity. An instance in a new datacenter adds an Epoxy voter. The second case needs a new datacenters entry, a new label, and the same updated topology on every instance.

7.2 Add a node

Run more copies of the application with the same namespace and pool. The documentation recommends using the platform autoscaler and keeping spare capacity (docs/general/content/nodes.mdx:95-99).

A new node starts with an empty Actor set. The scheduler fills it with Actors as requests arrive. The cost of a cold start does not depend on the number of instances. It depends on the node that receives the Actor and the state that the Actor must load.

The control plane allocates Actors to envoys with a hash-ring default. The default is EnvoyLoadBalancer::Hash with 8 virtual nodes, 2 samples, a maximum scan of 16 stale entries, and a slot jitter of 4 (engine/packages/config/src/config/pegboard.rs:511-522).

8. Upgrade

8.1 Two kinds of version

A cluster has two unrelated version concepts.

VersionMeaningApplies toSource
Node versionThe application build version. A higher number wins allocation.Node processesdocs/general/content/versions.mdx:9-14
Runtime protocol versionThe wire and storage schema version that the fleet has agreed to speak.rivet-engine processesengine/CLAUDE.md:75-80

The node version is an integer. The operator sets it with RIVET_ENVOY_VERSION. It must come from the build, not from the clock at runtime (docs/general/content/versions.mdx:104). It must increase on every deploy. A rollback to a lower node version is unsafe, because allocation only moves toward higher numbers (docs/general/content/versions.mdx:14).

The runtime protocol version has four kinds: envoy, ups, universaldb_commit, and epoxy (engine/packages/config/src/runtime_protocols.rs:3-9).

8.2 Admission

A new engine process checks admission before it starts any service. The check runs in one serializable transaction.

// engine/packages/version-management/src/lib.rs:56-104
pub async fn check_engine_admission(
	config: &rivet_config::Config,
	pools: &rivet_pools::Pools,
) -> Result<()> {
	let current_version = semver::Version::parse(env!("CARGO_PKG_VERSION"))
		.context("failed to parse cargo pkg version as semver")?;

	tracing::debug!(%current_version, "checking engine admission");

	let protocols = pools
		.udb()?
		.txn("engine_check_admission", |tx|  {
			let config = config.clone();
			let current_version = current_version.clone();
			async move {
				if let Some(existing_version) = tx.read_opt(&keys::EngineVersionKey::new(), Serializable).await? {
					if !config.runtime.allow_version_rollback() {
						if current_version < existing_version {
							bail!(
								"{}",
								formatdoc!(
									"
									Rivet Engine has been rolled back to a previous version:
									- Last Used Version: {existing_version}
									- Current Version:   {current_version}
									Cannot proceed without potential data corruption.
									
									(If you know what you're doing, this error can be disabled in the Rivet config via `allow_version_rollback: true`)
									"
								)
							);
						}
					}
				}

				// NOTE: We serializably read this key and write it in the same txn making all engine
				// connections serial. This is by design
				tx.write(&keys::EngineVersionKey::new(), current_version)?;

				// NOTE: These writes rely on the conflict guarantees of the above `EngineVersionKey`
				update_protocol_versions(&tx).await
			}
		})
		.await?;

	config.set_protocols(protocols);

	Ok(())
}

The transaction is serial on purpose. Every engine process reads and writes the same EngineVersionKey in one transaction. The comment states the reason: the protocol-version writes rely on the conflict guarantee of that key (engine/packages/version-management/src/lib.rs:91-96).

allow_version_rollback defaults to false (engine/packages/config/src/config/runtime.rs:201-203). A lower engine version therefore fails admission unless the operator sets it to true.

The check has an effect before any traffic moves. The transaction writes EngineVersionKey with the running binary's version on every start (engine/packages/version-management/src/lib.rs:91-93). If you start a newer binary and then abandon the upgrade, the old binary is now blocked. The floor rose even though the new version served no request. The only way back is allow_version_rollback: true, and the source warns that this risks data corruption (engine/packages/version-management/src/lib.rs:78-84). Treat the first start of a new binary as a one-way step.

8.3 The hold-back loop

The fleet never jumps to a new protocol version while an older process still heartbeats. A new process pins each protocol to the oldest live version.

// engine/packages/version-management/src/lib.rs:106-171
async fn update_protocol_versions(
	tx: &universaldb::Transaction,
) -> Result<rivet_config::RuntimeProtocols> {
	let now = util::timestamp::now();
	let mut protocols = rivet_build_meta::compiled_runtime_protocols();

	for protocol in &mut protocols {
		let protocol_version_subspace = universaldb::utils::Subspace::all()
			.subspace(&keys::ProtocolVersionKey::subspace(protocol.kind));
		// Read versions in increasing order to get the most out of date version first
		let mut stream = tx.get_ranges_keyvalues(
			universaldb::RangeOption {
				mode: StreamingMode::Small,
				..(&protocol_version_subspace).into()
			},
			Serializable,
		);

		while let Some(entry) = stream.try_next().await? {
			let (existing_key, update_ts) = tx.read_entry::<keys::ProtocolVersionKey>(&entry)?;

			// Check expired and delete
			if update_ts < now - PROTOCOL_VERSION_ENTRY_EXPIRED_THRESHOLD_MS {
				tracing::debug!(
					kind = %protocol.kind,
					version = existing_key.version,
					last_update_ts = update_ts,
					age_ms = now - update_ts,
					"deleting expired protocol version entry"
				);

				tx.delete(&existing_key);
				continue;
			}

			if protocol.compiled_version() < existing_key.version {
				bail!(
					"{}",
					formatdoc!(
						"
						Rivet Engine has been rolled back to a previous version:
						- Last Used `{0}` Protocol Version: {1}
						- Current `{0}` Protocol Version:   {2}
						Cannot proceed without potential data corruption.
						",
						protocol.kind,
						existing_key.version,
						protocol.compiled_version(),
					)
				);
			}

			protocol.set_override_version(existing_key.version);
			break;
		}

		// NOTE: Must write after reading to prevent RYOW
		tx.atomic_op(
			&keys::ProtocolVersionKey::new(protocol.kind, protocol.compiled_version()),
			&now.to_le_bytes(),
			MutationType::Max,
		);
	}

	Ok(protocols)
}

Three constants control the behaviour.

ConstantValueEffect
PROTOCOL_VERSION_ENTRY_EXPIRED_THRESHOLD_MS30,000An entry older than 30 seconds is deleted
PROTOCOL_VERSION_CHECK_INTERVAL15 secondsThe background service rechecks every 15 seconds
Heartbeat writeMutationType::MaxKeeps the newest timestamp for one version

The background service runs every 15 seconds and updates the process config when the agreed set changes (engine/packages/version-management/src/lib.rs:10-51). A call site that can speak more than one version must read the agreed version from config.protocols(), not from the compiled constant (engine/CLAUDE.md:78-80).

8.4 Safe order

The order below follows the code and the project documents. Do not shorten it.

sequenceDiagram participant O as "operator" participant E1 as "old rivet-engine" participant U as "UniversalDB" participant E2 as "new rivet-engine" O->>E2: "start new instance" E2->>U: "check_engine_admission txn" U-->>E2: "EngineVersionKey and oldest ProtocolVersionKey" E2->>E2: "config.set_protocols(oldest live version)" O->>E1: "SIGTERM" E1->>U: "stop protocol heartbeat" Note over U: "entry expired after 30000 ms" E2->>U: "update_protocol_versions every 15000 ms" U-->>E2: "newest live entry is now the compiled version" E2->>E2: "config.set_protocols(compiled version)" O->>O: "repeat for the next instance"
  1. Read the release notes and confirm that the new binary is not older than the

running binary. A downgrade fails admission by default. Remember that the first start raises the version floor (section 8.2).

  1. Deploy one instance. The new instance starts at the oldest live protocol

version, so it speaks the version that the fleet already speaks.

  1. Stop the old instance with SIGTERM. The service manager gives graceful

services time to stop, then stops UniversalDB (engine/packages/service-manager/src/lib.rs:369-405).

  1. Wait at least 30 seconds for the old heartbeat to expire. The hold-back loop

checks every 15 seconds.

  1. Repeat for each instance. The last instance moves the fleet to the compiled

version.

  1. For nodes, give the new node a higher version. To move old Actors to the new

version, set drain_on_version_upgrade on the pool with a PUT request to /pools/{pool}?namespace={namespace} (docs/general/content/versions.mdx:229-235). The default is false, and the two versions then run side by side (docs/general/content/versions.mdx:238-241).

  1. Give each node at least 60 seconds between SIGTERM and SIGKILL

8.5 Cross-datacenter upgrade

Epoxy cannot use the local heartbeat subspace. Its peers are replicas in other datacenters, and each peer writes to its own database. Each replica publishes the version that its own datacenter agreed on over HTTP. A request uses the lower of the local version and the peer version.

// engine/packages/epoxy/src/protocol_version.rs:42-60
/// The version to encode a request to `replica_url` at.
///
/// Returns the lower of our own negotiated version and the peer's most recently discovered version.
/// This performs no I/O.
///
/// A replica the service has not reached yet falls back to our own negotiated version, which
/// reproduces the behavior from before peer discovery existed rather than downgrading whenever a
/// peer is briefly unreachable.
pub async fn negotiate(config: &rivet_config::Config, replica_url: &str) -> u16 {
	let local_version = config.protocols().epoxy.version();

	match PEER_VERSIONS
		.read_async(replica_url, |_, version| *version)
		.await
	{
		Some(peer_version) => local_version.min(peer_version),
		None => local_version,
	}
}

The probe interval is 60 seconds and the probe timeout is 5 seconds (engine/packages/epoxy/src/protocol_version.rs:21-28). A multi-datacenter upgrade therefore moves in steps. Upgrade one datacenter, wait for the peers to discover it, then upgrade the next. The source does not give a maximum wait beyond the 60-second refresh interval.

The fallback has a failure direction. When the peer has not been reached, negotiate returns the local version (engine/packages/epoxy/src/protocol_version.rs:56-59). If the local version is newer than the peer's real version, the local replica encodes the request at the new version. The old peer cannot decode that request. The 5-second probe and the 60-second refresh make this window real during an upgrade. Upgrade a datacenter only after its peers report the new version, or accept that requests can fail while peer discovery is incomplete. The source does not state how a decode failure is retried.

8.6 VBARE compatibility

Persisted and wire data uses versioned Binary Application Record Encoding (BARE) codecs through the vbare crate. The repository rule says to use vbare::OwnedVersionedData for any persisted or wire encoding (CLAUDE.md:25). The runner protocol is a worked example.

// engine/packages/runner-protocol/src/versioned.rs:8-59
pub enum ToClientMk2 {
	V4(v4::ToClient),
	V5(v5::ToClient),
	V7(v7::ToClient),
}

impl OwnedVersionedData for ToClientMk2 {
	type Latest = v7::ToClient;

	fn wrap_latest(latest: v7::ToClient) -> Self {
		ToClientMk2::V7(latest)
	}

	fn unwrap_latest(self) -> Result<Self::Latest> {
		if let ToClientMk2::V7(data) = self {
			Ok(data)
		} else {
			bail!("version not latest");
		}
	}

	fn deserialize_version(payload: &[u8], version: u16) -> Result<Self> {
		match version {
			4 => Ok(ToClientMk2::V4(rivet_util::serde::bare_from_slice!(
				payload
			)?)),
			5 => Ok(ToClientMk2::V5(rivet_util::serde::bare_from_slice!(
				payload
			)?)),
			6 | 7 => Ok(ToClientMk2::V7(rivet_util::serde::bare_from_slice!(
				payload
			)?)),
			_ => bail!("invalid version: {version}"),
		}
	}

	fn serialize_version(self, _version: u16) -> Result<Vec<u8>> {
		match self {
			ToClientMk2::V4(data) => rivet_util::serde::bare_to_vec!(&data).map_err(Into::into),
			ToClientMk2::V5(data) => rivet_util::serde::bare_to_vec!(&data).map_err(Into::into),
			ToClientMk2::V7(data) => rivet_util::serde::bare_to_vec!(&data).map_err(Into::into),
		}
	}

	fn deserialize_converters() -> Vec<impl Fn(Self) -> Result<Self>> {
		vec![Ok, Ok, Ok, Self::v4_to_v5, Self::v5_to_v7, Ok]
	}

	fn serialize_converters() -> Vec<impl Fn(Self) -> Result<Self>> {
		vec![Ok, Self::v7_to_v5, Self::v5_to_v4, Ok, Ok, Ok]
	}
}

The compatibility rule is: a new version adds a converter. It does not change an old converter retroactively. The internal guide states that migration code must never be changed after it is written (.claude/reference/vbare-migrations.md:95). For an operator, the consequence is simple. An upgrade that changes a protocol needs every peer to be on a build that can decode the old version. The hold-back loop enforces that for the fleet. The envoy client also retries a failed decode as the previous version for serverless start payloads (engine/sdks/rust/envoy-client/src/handle.rs:785-796).

8.7 Open source to Enterprise

The internal upgrade document is explicit. Stored rows are compatible in both directions. Compaction workflows are not. Enterprise adds durable steps to the compaction workflows. A workflow that is mid-flight during the binary swap will diverge and raise WorkflowError::HistoryDiverged (docs-internal/engine/oss-to-ee-upgrade.md:22-36).

The required procedure is:

  1. Stop Actor traffic, or at least stop write traffic heavy enough to trigger

compaction.

  1. Let compaction drain, or force the running compaction workflows to

completion.

  1. Confirm that no compaction workflows are running.
  2. Deploy the Enterprise build.
  3. Configure sqlite.workflow_cold_storage if cold storage is wanted.

Source: docs-internal/engine/oss-to-ee-upgrade.md:38-46.

A downgrade from Enterprise to open source is not supported. The internal document says to treat it as a restore from backup. Enterprise-only keys such as kafka, compute_gateway, metadata, and sqlite.workflow_cold_storage are rejected by the open-source deny_unknown_fields (docs-internal/engine/oss-to-ee-upgrade.md:51-62).

10. Backup and restore

10.1 What must be backed up

The backup set follows the storage path.

ItemWhyReproducible?

Bucket objectsThe documented durable copyNo, when the bucket is the primary store
Instance configurationTopology, auth, storage, limitsYes, from source control

UniversalDB rows and Actor Depot data are one item, not two. Depot keeps its pages and key-value rows in UniversalDB (section 3.1). On FileSystem they all live in one RocksDB directory. A backup that copies only the "metadata" and not the pages is incomplete.

For FileSystem, the UniversalDB data is the RocksDB directory. Back it up with a file system snapshot, or use the per-database export in section 10.2.

For Postgres, use the normal PostgreSQL backup tooling. The repository does not include a PostgreSQL backup command.

For the documented bucket model, the bucket is the durable store. The repository does not contain a bucket backup or restore tool. The Enterprise build is not in this snapshot. Unverified: the repository does not state a bucket lifecycle, versioning, or replication policy. Use the provider's own object versioning and replication features, and confirm them against the Enterprise documentation.

		let udb = pools.udb()?;

10.3 How a lost instance rejoins

A lost instance is an instance that stopped and lost its local disk. The recovery depends on the storage path.

Storage pathRecovery
FileSystemRestore the disk snapshot. Without it, the cluster state is gone.
Postgres + NATSStart a new instance with the same PostgreSQL URL, NATS addresses, and topology. It reads the shared state.
Documented bucket modelStart a new identical instance with the same bucket and topology. It reads the bucket.

The rivet-engine start path always runs admission first (engine/packages/engine/src/commands/start.rs:71-76). A new instance with an older binary fails admission. A new instance with the same or a newer binary joins and writes its version.

The source does not contain a command that registers a replacement instance by identifier. The instance is not a named member. It is an identical process with the same configuration.

10.4 What has no tool

The repository has no cluster-level backup command. It has no bucket restore command. It has no command that rebuilds an entire UniversalDB from a bucket. The reason follows from section 10.3. In the documented model, the bucket is the primary store, so a new instance reads it at start and needs no rebuild step. In this open-source build, the bucket is not a store, so no rebuild command exists to write. A cluster that runs the open-source build and needs disaster recovery must protect the database itself, not a bucket.

The depot repair vacuum command repairs one database after writing a verified pre-repair export, but it is a repair tool, not a restore tool (engine/packages/engine/src/commands/depot.rs:444-464).

The database nuke command deletes the entire local RocksDB directory after a --yes flag (engine/packages/engine/src/commands/db/mod.rs:51-66). It is a destructive reset. It is not a cleanup command for old rows.

11. Security posture

11.1 The trust boundary

The cluster has three zones.

ZoneWho can reach itWhat it trusts
Public edgeClients, node processesA bearer token or a JWT
Private instance networkOther instancesThe shared database and the topology configuration
Node connectionOutbound only, from the node to the control planeThe token presented at connect time

A node opens the connection. The control plane does not open a connection to the node. This is the reason a node needs no inbound port (docs/general/content/nodes.mdx:42).

An instance trusts the shared database. An operator who can write to the database can change the cluster. Protect the database with the same care as the admin token.

11.2 Tokens

The engine requires an admin token. Auth::validate rejects an empty value (engine/packages/config/src/config/auth.rs:37-44). The token is a Secret, so the debug output does not print it.

A node presents its token in the WebSocket subprotocol list, not in a header alone. The TypeScript runner builds the list as rivet and rivet_token. (rivetkit-typescript/packages/engine-runner/src/mod.ts:756-759). The envoy client does the same (engine/sdks/rust/envoy-client/src/connection/native.rs:100-106). A proxy must forward the Sec-WebSocket-Protocol header unchanged.

The Guard router calls check_connection_auth before it hands the socket to the runner or envoy service (engine/packages/guard/src/routing/runner.rs:56-61, engine/packages/guard/src/routing/envoy.rs:56-61).

A JWT is namespace-scoped and short-lived. The defaults are in section 9.1. The insecure_allow_unauthenticated flag restores legacy unauthenticated access. Do not enable it in production (engine/packages/config/src/config/auth.rs:28-30).

11.3 TLS

TLS is not active on Guard in this commit. The configuration has four certificate paths for the two traffic classes (engine/packages/config/src/config/guard.rs:361-369). The resolver returns Ok(None) before it reads a path (engine/packages/guard/src/tls.rs:84-87). Terminate TLS at a load balancer or a proxy. The source does not state a minimum TLS version. The source does not state a cipher policy. Set both at the load balancer.

The public URL in each datacenter is the origin that clients use (engine/packages/config/src/config/topology.rs:164-165). The valid_hosts list restricts regional endpoints to known names (engine/packages/config/src/config/topology.rs:171-178). Set it when the topology has more than one datacenter, because validation requires it (engine/packages/config/src/config/mod.rs:292-300).

11.4 Outbound policy

The outbound policy protects the internal network from a caller who can configure a serverless runner URL. The default denies private, link-local, shared, and otherwise non-globally-routable addresses (engine/packages/config/src/config/outbound.rs:4-9). The default allows loopback and plain HTTP.

For production, set allow_loopback to false, set allow_insecure_scheme to false, and leave allow_private_networks false unless a runner must reach a private address. When a private address is required, prefer allow_hosts or allow_cidrs over the whole private range (engine/packages/config/src/config/outbound.rs:26-38).

11.5 Bucket permissions

The repository does not contain a bucket policy. The compaction constants show object upload and object delete calls (engine/packages/depot/src/conveyer/constants.rs:190-203). Grant those two operations on the cluster bucket, and no others that the source does not show. Do not grant access to other buckets. Unverified: the exact action names, the required resource scope, and whether a list permission is needed are not in this source.

12.3 Lost node

ItemDetail
SymptomActors on the node stop answering. Requests to those Actors stall, then retry.
DetectionThe control plane marks the runner or envoy lost after the threshold.
RecoveryThe Actors reschedule to another node in the pool.
Mechanismrunner_lost_threshold defaults to 15,000 ms (engine/packages/config/src/config/pegboard.rs:267-269). envoy_lost_threshold also defaults to 15,000 ms (engine/packages/config/src/config/pegboard.rs:378-380).
Source conflictdocs/general/content/versions.mdx:298 says 40 seconds for envoy_lost_threshold. The code default is 15 seconds. The code wins.

The server sends both thresholds to the node in the init message. The legacy path sends runner_lost_threshold and actor_stop_threshold (engine/packages/pegboard-runner/src/conn.rs:391-397). The envoy path sends envoy_lost_threshold, actor_stop_threshold, and max_response_payload_size (engine/packages/pegboard-envoy/src/conn.rs:152-159).

A graceful node stop is different. The node stops its Actors first. Give the node at least 60 seconds between SIGTERM and SIGKILL (docs/general/content/versions.mdx:283-291). The worker manifest uses 2100 seconds (self-host/workers/kubernetes/rivetkit-app.yaml:15-19).

A full disk also stops compaction, because compaction writes to the same database. The throttle code can slow compaction, but it cannot make room on the disk. The source does not state a minimum free-space rule.

12.5 Clock skew

ItemDetail
SymptomProtocol version entries expire too early or too late. The version floor can stay low after an upgrade.
DetectionCompare host time with a trusted time source.
RecoveryCorrect the clock with Network Time Protocol (NTP).
MechanismA version entry stores now.to_le_bytes() and the write uses MutationType::Max (engine/packages/version-management/src/lib.rs:162-167). The expiry check compares the reader's now with that stored value (engine/packages/version-management/src/lib.rs:109-139).
Source limitThe source does not state a permitted skew.

The comparison uses two clocks. The writer stores its clock value. Each reader compares that value with its own clock. Four cases follow.

Clock faultEffect on the version floor
Writer clock aheadThe stored timestamp is in the future. The entry survives past its real heartbeat and pins the fleet to the old version.
Writer clock behindMax keeps the largest value, so one behind writer is ignored while a healthy writer is present. If all writers are behind, entries expire early.
Reader clock aheadA live entry looks expired, so that instance deletes it and the fleet can advance early.
Reader clock behindThe entry looks live longer, so the floor stays low longer.

The writer-ahead case is the dangerous one. The entry does not expire when the old instance stops, because the timestamp it left is in the future. The fleet stays on the older protocol until the clock catches up. The source does not give a tolerance. Run a time service on every instance.

13. A minimum production checklist

This checklist follows only the source in this document. It does not add steps from the public guides.

  1. Choose the storage path. Use Postgres and NATS for more than one

open-source instance. Use one FileSystem instance only on a single host.

  1. Set auth.admin_token from a secret. Do not leave the development token.
  2. Set topology.datacenter_label and every datacenter entry. Give each entry a

public URL, a peer URL, and valid_hosts.

  1. Set the Guard listener. Terminate TLS at the load balancer, because the

Guard certificate resolver returns Ok(None) in this commit.

  1. Set the outbound policy. Keep private networks denied unless a runner needs

them.

  1. Run three instances in three zones, one per zone (README.md:155). In this

build, give them PostgreSQL and NATS.

  1. Create the node pool before the first node connects

(docs/general/content/nodes.mdx:25).

  1. Give every node a token, a namespace, a pool, and a build version.
  2. Set RIVET_ENVOY_VERSION from the build. Increase it on every deploy.
  3. Keep the instance disk on a volume. In the Enterprise bucket model, keep

the bucket in the same region.

  1. Back up the shared database, or the RocksDB directory, and the

configuration.

  1. Monitor /health on port 6421 and metrics on port 6430. The

SQLITE_S3_REQUEST_FAILURES_TOTAL counter exists, but nothing in this open-source tree increments it, so do not depend on it here.

  1. Upgrade one instance at a time. Wait for the 30-second protocol entry

expiry. Keep the node version monotonic.

Glossary

Actor: A keyed, durable process that Rivet schedules on a node.

>

bucket: An object storage container. It is the only external durable store in the documented model.

>

control plane: The set of rivet-engine processes that schedule Actors and route requests.

>

Envoy: The newer node connection path. The client is in engine/sdks/rust/envoy-client, and the server path is /envoys/connect.

>

Node: An application process that runs the Rivet SDK and hosts Actors.

>

Runner: The older node connection path. The client is the TypeScript engine-runner, and the server path is /runners/connect.

>

UniversalDB: The key-value database under every durable record. Open source uses RocksDB or PostgreSQL. The documented Enterprise model uses a bucket.

>

BYOC: Bring Your Own Cloud. The stack runs in the customer VPC and Rivet operates it over an outbound connection.
