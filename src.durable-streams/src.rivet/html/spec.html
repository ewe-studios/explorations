2. What the Project Is

Rivet is an orchestrator for stateful processes that it calls Actors. An Actor has a key, durable state, a Structured Query Language (SQLite) database, a queue, realtime connections, and a schedule. Many Actors share one node process. An idle Actor writes its state and unloads. A later request starts it again on any node.

The control plane is one Rust binary. It schedules Actors, routes Hypertext Transfer Protocol (HTTP) and WebSocket traffic to them, and stores durable state. The product description says that it has no separate database and no message bus, and that the only external durable store is an object storage bucket. The open-source code in this commit does not match that description in full. UniversalDB has two drivers: RocksDB and PostgreSQL. The cold tier that writes SQLite pages to object storage is Enterprise-only. Instances coordinate through UniversalDB and an optional NATS pub/sub service. The documents state the product claim and the open-source configuration separately, and they mark which is which.

The repository also holds RivetKit, the Software Development Kit (SDK) that a developer uses to define an Actor. RivetKit runs on Node.js, Bun, and Rust. It also holds the dashboard, the documentation, examples, and the internal design documents.

3. Documentation Goal

A reader must be able to:

  1. State what an Actor, a node, a runner, the control plane, and a namespace are,

and how they relate.

  1. Map the repository and name the crate or package that holds each concern.
  2. Trace one request from a client to a running Actor and back, across the

gateway, the control plane, and the runner.

  1. Explain how Pegboard schedules an Actor, how a runner pool holds capacity, and

how the runner protocol carries an Actor start, a request, and a stop.

  1. Explain how Gasoline replays a workflow, how an activity records its result,

and how a code change is versioned.

  1. Explain how an Actor's SQLite database is stored, how a write reaches two of

three control plane instances, and how pages move to the bucket.

  1. Explain UniversalDB, the storage abstraction under every durable record, the

RocksDB and PostgreSQL drivers, and where object storage enters the system.

  1. Explain Epoxy and its per-key Fast Paxos protocol, including replicas, ballots, and

multi-region commit.

  1. Explain how Guard routes HTTP and WebSocket traffic, how it holds a

hibernatable connection, and how it recovers a connection after a wake.

  1. Explain how RivetKit TypeScript and RivetKit Rust define an Actor and how

the client speaks to it.

  1. Explain authentication, namespaces, tokens, and the authorization policy.
  2. Explain telemetry, metrics, logs, profiling, configuration, and the command

line interface.

  1. Explain the deployment shapes: self-host, Rivet Cloud, and bring your own

cloud.

  1. State the benchmark method, the measured limits, and the operational risks.
  2. Name the products in the snapshot and state what each adds to an Actor.
  3. Compare Rivet with Cloudflare Durable Objects, Kubernetes, and the durable

promise systems in this parent directory.

  2. Tables, trees, and diagrams as visual assets.
  3. Generated HTML with consistent navigation.

The engineer can state how an Actor is placed, how its SQLite pages become durable, how a workflow replays after a crash, how Guard finds the Actor, and how RivetKit hides the protocol. The engineer can also state where Rivet is stronger than Cloudflare Durable Objects and Kubernetes, and where it is weaker.
