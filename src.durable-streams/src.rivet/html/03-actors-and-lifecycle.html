03 Actors and lifecycle

An Actor in Rivet is a durable keyed process. It is not a container and not a virtual machine. It is a task inside a node process that the operator already runs. The control plane (the Rivet engine) keeps the Actor record and the key reservation (the record that fixes a key to one datacenter). The live task runs on a host process. The newer host process is an envoy. The older host process is a runner. The Actor record stays in the control plane while the live task moves between host processes. A state machine in the control plane owns that movement. This document explains the identity of an Actor, the Application Programming Interface (API) operations that create and delete it, every state in the Actor workflow, and the sleep, wake, reschedule, and destroy paths. It uses the envoy version 2 path as the main path. It names the legacy runner version 1 path where the two differ. Placement is in 04 Pegboard. The SQLite database storage is in 06 Actor SQLite and Depot.

1. What an Actor is

An Actor has a name, an optional key, a namespace, and durable state. The source represents it with one record. The record is not the live task. The record holds identity and timestamps. The live task is a separate task that the host process starts. The namespace is the isolation boundary for Actor names and keys. It is identified by namespace_id. 13 Auth covers the namespace record.

An Actor is durable in three classes of storage and one live task. The control plane owns the Actor workflow state. It owns the key reservation. It owns the per-Actor UniversalDB (UDB) records, which include the Actor database pages. The host process owns the live task. The control plane can send a stop command to the host and keep all three storage classes. That is the basis of sleep and wake. Section 11 splits the same picture by owner.

2. Identity: the Actor identifier (ID), namespace, name, and key

The Actor ID is a value of type Id. In this commit Id has one version. A version 1 Id is 18 bytes. The first 16 bytes are a Universally Unique Identifier (UUID). The last two bytes are a big-endian u16 label. The source uses the label for the datacenter that created the value.

// engine/packages/util-id/src/lib.rs:35-46

	V1([u8; 18]),
}

impl Id {
	pub fn new_v1(label: u16) -> Self {
		let mut data = [0u8; 18];
		data[..16].copy_from_slice(Uuid::new_v4().as_bytes());
		data[16..].copy_from_slice(&label.to_be_bytes());
		Id::V1(data)
	}

2.1 The key reservation is separate from the Actor

A key needs one home in a multi-datacenter system. Rivet stores the home in Epoxy, its per-key consensus layer. The value is a reservation ID, not the Actor ID. The reservation ID is also an Id. Its label is the datacenter that owns the key.

Epoxy is the replicated key-value layer in 08 Epoxy. It orders writes to each key through consensus. A read with CachingBehavior::Optimistic returns the locally cached value without a consensus round. That read is correct only if the stored value never changes.

An Actor ID can be destroyed and replaced. The value of a key must stay the same. The control plane therefore cannot store an Actor ID and then update it. The document docs-internal/engine/ACTOR_KEY_RESERVATION.md:18-28 states this limitation. The code matches the document. The lookup uses CachingBehavior::Optimistic at engine/packages/pegboard/src/workflows/actor2/keys.rs:179-188.

Aha: The reservation ID is a stable pointer, so the key row never needs an update. The obvious alternative is to store the Actor ID in the key row and rewrite it on every destroy and create. That costs a consensus write on the hot key, and a failed rewrite leaves the key pointing at a dead Actor. The design uses an immutable reservation and a future pointer chain instead. A pointer chain stores a pointer from the old reservation to the new one in the old datacenter, so the Epoxy value never changes (docs-internal/engine/ACTOR_KEY_RESERVATION.md:40-60). The pointer chain is future work, not implemented in this commit.

The current cost is explicit. A key stays tied to its first datacenter. The document says so at docs-internal/engine/ACTOR_KEY_RESERVATION.md:98-100, and the code returns ForwardToDatacenter when the reservation label differs from the local label at engine/packages/pegboard/src/workflows/actor2/keys.rs:122-141. A key cannot move to another datacenter until the reservation chain exists.

Three names describe this condition at three layers. ReserveKeyOutput::ForwardToDatacenter is the workflow result. errors::Actor::KeyReservedInDifferentDatacenter is the API error that the workflow sends at engine/packages/pegboard/src/workflows/actor2/mod.rs:194-202. get_for_key::Output::Forward { dc_label } is the read operation result at engine/packages/pegboard/src/ops/actor/get_for_key.rs:15-20.

3. Creation: POST /actors and get-or-create

Rivet has two create operations. POST /actors creates an Actor. PUT /actors with the get-or-create handler returns the existing Actor for a key, or creates one. The public handlers authenticate and choose the target datacenter. The peer handlers validate and call the control plane.

The create path can still lose a race. Two requests can both see NotFound in Epoxy and both dispatch an Actor workflow. The loser must not create a second live Actor. Before the index scan, reserve_key calls the Propose activity at engine/packages/pegboard/src/workflows/actor2/keys.rs:211-247. Propose sends one CheckAndSetCommand with expect_one_of: vec![None]. The value is written only if the key has no value at consensus. The check happens in the UDB transaction ReserveActorKey. It scans ActorByKeyKey for the namespace, name, and key. It stops at the first entry with is_destroyed == false and returns ExistingActor { existing_actor_id }. Otherwise it writes a new index entry with is_destroyed: false.

// engine/packages/pegboard/src/workflows/actor2/keys.rs:264-322
#[activity(ReserveActorKey)]
pub async fn reserve_actor_key(
	ctx: &ActivityCtx,
	input: &ReserveActorKeyInput,
) -> Result<ReserveActorKeyOutput> {
	let state = ctx.state::<State>()?;

	let create_ts = state.create_ts;
	let res = ctx
		.udb()?
		.txn("pegboard_actor2_reserve_key", |tx| async move {
			let tx = tx.with_subspace(keys::subspace());

			// Check if there are any actors that share the same key that are not destroyed
			let actor_key_subspace = keys::subspace().subspace(&keys::ns::ActorByKeyKey::subspace(
				input.namespace_id,
				input.name.clone(),
				input.key.clone(),
			));

			let mut stream = tx.get_ranges_keyvalues(
				universaldb::RangeOption {
					mode: StreamingMode::Iterator,
					..(&actor_key_subspace).into()
				},
				Serializable,
			);

			while let Some(entry) = stream.try_next().await? {
				let (idx_key, data) = tx.read_entry::<keys::ns::ActorByKeyKey>(&entry)?;
				if !data.is_destroyed {
					return Ok(ReserveActorKeyOutput::ExistingActor {
						existing_actor_id: idx_key.actor_id,
					});
				}
			}

			// Write key
			tx.write(
				&keys::ns::ActorByKeyKey::new(
					input.namespace_id,
					input.name.clone(),
					input.key.clone(),
					create_ts,
					input.actor_id,
				),
				ActorByKeyKeyData {
					workflow_id: ctx.workflow_id(),
					is_destroyed: false,
				},
			)?;

			Ok(ReserveActorKeyOutput::Success)
		})
		.custom_instrument(tracing::info_span!("actor_reserve_key_tx"))
		.await?;

	Ok(res)
}

ActorByKeyKey includes create_ts and actor_id, so two Actors with the same key have different index keys. Only the winner writes a live entry. A destroy later tombstones that entry. A tombstone is an entry whose is_destroyed field is true. The comment in engine/packages/pegboard/src/ops/actor/list_for_ns.rs:9-20 says that every loser writes an index entry before it detects the conflict. The code in this commit does not do that. ReserveActorKey returns ExistingActor before it writes at engine/packages/pegboard/src/workflows/actor2/keys.rs:292-316. The code wins over the comment.

list_for_ns keeps a cap of 4096 entries for one by-key lookup. MAX_ACTOR_BY_KEY_SCAN_ENTRIES is 4096 at engine/packages/pegboard/src/ops/actor/list_for_ns.rs:21. If the scan reaches the cap, list_for_ns returns KeyIndexScanLimitExceeded at engine/packages/pegboard/src/errors.rs:65-74. It does not return an empty list. An empty list would make get-or-create create a replacement and write another entry under the same key.

The loser takes three actions in the Actor workflow. It sends Failed { error: DuplicateKey { key, existing_actor_id } }. It calls destroy(ctx, input). It returns. The branch is at engine/packages/pegboard/src/workflows/actor2/mod.rs:209-224. The error type is at engine/packages/pegboard/src/errors.rs:42-47.

Get-or-create then turns the error into the existing Actor. It checks both the local RivetError form and the remote RawErrorResponse form. It reads the existing_actor_id field from the error metadata. Then it calls pegboard::ops::actor::get and returns created: false. The logic is at engine/packages/api-peer/src/actors/get_or_create.rs:75-107, and the helper is at lines 121-159.

Aha: The duplicate check is in the key index, not only in Epoxy. Epoxy gives one reservation for the key. It does not give one live Actor, because the reservation is immutable and outlives the Actor. The index scan closes that gap. The alternative is to make the reservation carry a live Actor pointer. That alternative breaks the optimistic read rule. The cost of the chosen design is the tombstone history. The 4096-entry cap and the key_index_scan_limit_exceeded error are the price.

A create with a key that already has a live Actor does not return the existing Actor. A live Actor is one whose key-index entry has is_destroyed: false. The create returns the duplicate_key error. Only get-or-create maps that error to a successful response. This is an API semantic difference, not a lifecycle difference. After the previous Actor is destroyed, a create with the same key succeeds: the index scan at engine/packages/pegboard/src/workflows/actor2/keys.rs:292-299 skips destroyed entries and writes a new ActorByKeyKey. The Epoxy reservation itself stays in place, because ReserveActorKey rewrites only the index.

pub async fn reschedule_actor(
	ctx: &mut WorkflowCtx,
	input: &Input,
	state: &mut LifecycleState,
	metrics_workflow_id: Id,
) -> Result<()> {
	let next_gen = state.generation + 1;
	let allocate_res = ctx
		.activity(AllocateInput {
			generation: next_gen,
		})
		.await?;

	if let Some(allocation) = allocate_res.allocation {
		state.generation += 1;

		match &allocation {
			Allocation::Serverless => {
				// Transition to allocating
				state.transition = Transition::Allocating {
					destroy_after_start: false,
					lost_timeout_ts: allocate_res.now
						+ ctx.config().pegboard().actor_allocation_threshold(),
				};
			}
			Allocation::Serverful { .. } => {
				// Transition to starting
				state.transition = Transition::Starting {
					destroy_after_start: false,
					lost_timeout_ts: allocate_res.now
						+ ctx.config().pegboard().actor_start_threshold(),
				};
			}
		}

		ctx.activity(SendOutboundInput {
			generation: state.generation,
			input: input.input.clone(),
			allocation,
		})
		.await?;
	} else {
		// NOTE: Cannot return `StoppedResult::Destroy` if provided `StoppedVariant::FailedAllocation` so we
		// can ignore it
		handle_stopped(
			ctx,
			&input,
			state,
			metrics_workflow_id,
			StoppedVariant::FailedAllocation,
		)
		.await?;
	}

	Ok(())
}

9. Rescheduling and failure

Rescheduling moves an Actor off a host. It is not the same as sleep. Sleep has no host and waits for a request. The code does not treat every rescheduling cause the same way. A draining host starts the Actor on a new host without a client request. A host that stops responding puts the Actor to sleep by default; the next request wakes it. Section 9.3 gives the exact decision.

9.1 The three causes

The internal document lists exactly three causes at docs-internal/engine/actor-rescheduling.md:48-56. The code supports the same three.

  1. A version upgrade with drain_on_version_upgrade enabled. The engine asks

old hosts to drain. The drain operation is at engine/packages/pegboard/src/ops/runner/drain.rs:36-88.

In SleepIntent, StopIntent, or GoingAway, it moves to Destroying and does not send a second command. In Allocating or Starting, it sets destroy_after_start = true. In Sleeping or Reallocating, it breaks the workflow loop. In Destroying, it does nothing. The code is at engine/packages/pegboard/src/workflows/actor2/mod.rs:1098-1152.

destroy is a four-step sequence. It sends DestroyStarted, runs UpdateStateAndDb, runs ClearKv, and sends DestroyComplete. The code is at engine/packages/pegboard/src/workflows/actor2/mod.rs:1191-1206.

10.5 Destroy failure paths

The source defines no separate failure branch for destroy. destroy awaits each activity with ?. If UpdateStateAndDb or ClearKv returns an error, destroy returns that error and the next step does not run. The source does not set a special timeout for DestroyComplete. What the workflow engine does with the error is the Gasoline policy in 05 Gasoline.

DestroyComplete is a message, not a reply. ctx.msg(DestroyComplete {}).send() writes the message to the workflow outbox and returns. The outbox is the durable list of messages that the workflow sends. The workflow does not wait for a listener to acknowledge it. A listener that misses the message has no source-level retry from destroy.

The destroy_after_start flag has a gap. A destroy signal during Allocating or Starting sets the flag at engine/packages/pegboard/src/workflows/actor2/mod.rs:1135-1146. If the start fails first, handle_stopped chooses Decision::Backoff for StoppedVariant::FailedAllocation or Decision::Sleep for StoppedVariant::Stopped { code: StopCode::Error } and StoppedVariant::Lost. Those branches replace the transition at engine/packages/pegboard/src/workflows/actor2/runtime.rs:719-731. The replacement Transition::Reallocating or Transition::Sleeping has no destroy_after_start field. The destroy intent is lost. The Actor can start again or stay asleep. The source gives no guarantee that the destroy completes. The source does not state a reason for the gap.

14. A worked example

This example follows one Actor from create to destroy. The values are concrete and the calls are real.

  1. The client sends POST /actors?namespace=acme with name: "chat",

key: "room-42", runner_name_selector: "default", and crash_policy: "sleep".

  1. The public handler authorizes namespace acme and calls

find_dc_for_actor_creation. The target label is the local datacenter, for example 1.

  1. The peer handler validates the key. "room-42" is 7 bytes, below 1,024. It

creates Actor ID Id::new_v1(1). The UUID part is random. The label is 1.

  1. The create operation reads the pool. The pool has a protocol_version, so

it dispatches actor2. The crash_policy field has no effect on this path. The operation subscribes to the six messages first.

  1. InitStateAndDb writes CreateTsKey, WorkflowIdKey, NamespaceIdKey,

PoolNameKey, NameKey, VersionKey = 2, GenerationKey = 0, and KeyKey = "room-42".

  1. reserve_key looks up the Epoxy key for (acme, chat, room-42). There is

no value. It proposes a new reservation ID with label 1. The proposal commits. ReserveActorKey scans ActorByKeyKey for the same tuple. There is no live entry. It writes the entry with is_destroyed: false.

  1. PopulateIndexes writes ActiveActorKey and AllActorKey. It sets

create_complete_ts. The workflow sends CreateComplete at engine/packages/pegboard/src/workflows/actor2/mod.rs:230-233. The create operation reads the Actor and returns it. The record has create_ts and no sleep_ts. It usually has no start_ts, because the first allocation starts after CreateComplete. A fast start can set start_ts before that read.

  1. The workflow starts the metrics workflow and the lifecycle state. It calls

reschedule_actor with generation 1. Allocate increments the pool slot. The pool is serverful, so it chooses an envoy and returns Allocation::Serverful { envoy_key }. The state becomes Starting with lost_timeout_ts = now + 30_000.

  1. SendOutbound sends CommandStartActor with generation 1 and the decoded

input. The envoy starts the SDK Actor. The SDK runs onCreate on the first start, then onMigrate, then onWake, then run.

  1. The envoy sends ActorStateRunning with generation 1. The workflow moves

Starting to Running. SetConnectable writes ConnectableKey, EnvoyKeyKey, the envoy slot increment, and envoy::ActorKey. The workflow sends Ready { envoy_key }.

  1. The first client request reaches Guard. Guard has already read the Actor

and subscribed to the four messages. It sees sleeping = false and connectable = true, so it uses the envoy key and opens the tunnel. The request succeeds.

  1. The SDK idle timer reaches 30,000 milliseconds with no work that blocks

sleep. The SDK sends ActorIntentSleep. The workflow moves Running to SleepIntent. SetSleeping deletes ConnectableKey and writes SleepTsKey = now. The workflow sends CommandStopActor with reason SleepIntent.

  1. The envoy stops the task and sends ActorStateStopped with

StopCode::Ok. handle_stopped chooses Sleep. Deallocate deletes EnvoyKeyKey and the envoy ActorKey, and decrements both slot counters. The state becomes Sleeping. The Stopped message goes to subscribers.

  1. The client sends another request. Guard reads SleepTsKey, sets

sleeping = true, and signals Wake. The workflow calls reschedule_actor with generation 2. Allocate deletes SleepTsKey, writes GenerationKey = 2, and chooses an envoy. The state becomes Starting with a 30,000 millisecond timeout. SendOutbound sends CommandStartActor with generation 2. The SDK runs onMigrate, then onWake, then run. onCreate does not run again.

  1. The envoy sends ActorStateRunning for generation 2. The workflow calls

SetConnectable and sends Ready. Guard refetches with get_for_gateway. It requires the record to be not destroyed and to name the same envoy key. If either check fails, Guard returns ActorStoppedWhileWaiting with phase route_after_ready at engine/packages/guard/src/routing/pegboard_gateway/mod.rs:716-733. Otherwise it opens the tunnel. The request succeeds.

  1. The client sends DELETE /actors/{id}. The peer subscribes to both

actor::DestroyComplete and actor2::DestroyComplete at engine/packages/api-peer/src/actors/delete.rs:22-25, reads the Actor, and sees no destroy_ts. It signals actor2::Destroy. The workflow moves Running to Destroying and sends CommandStopActor with reason Destroy. The envoy stops the task. The workflow calls handle_stopped, gets Destroy, breaks the loop, signals the metrics workflow to stop, and calls destroy.

  1. UpdateStateAndDb writes DestroyTsKey, deletes ActiveActorKey, and

tombstones ActorByKeyKey for (acme, chat, room-42, create_ts, actor_id). ClearKv clears the Actor KV subspace and the SQLite storage. DestroyComplete reaches the peer, and the API returns success.

  1. The Epoxy reservation for (acme, chat, room-42) still points at

reservation ID with label 1. A new create with the same key in datacenter 1 scans past the tombstone and writes a new index entry. A create in datacenter 2 forwards to datacenter 1.

This example shows the important boundary. The Actor ID is not reused. The key is reusable only in the original datacenter. The live task is replaceable at every start. The durable record is not.

16. Local glossary

Alarm. The host event EventActorSetAlarm { alarm_ts }. It sets state.alarm_ts at engine/packages/pegboard/src/workflows/actor2/mod.rs:841-847. A sleeping Actor wakes at that time. A stop that would sleep reallocates instead when the alarm is due, at engine/packages/pegboard/src/workflows/actor2/runtime.rs:665-673.

>

Allocating. The lifecycle state between a serverless allocation result and the Allocated acknowledgement from the host. reschedule_actor sets it before it sends the start command.

>

Actor ID. An 18-byte Id value. Sixteen bytes are a UUID. Two bytes are the big-endian datacenter label.

>

Control plane. The Rivet engine. It owns the Actor workflow, the key reservation, and the UDB records.

>

Envoy. The newer host process for Actor tasks. The source also calls the older host a runner.

>

Gateway 2. The pegboard_gateway2 service. Guard uses it to send a request to an envoy through the tunnel.

>

Generation. A u32 fencing value. It increases when Allocate returns an allocation. An event with an old generation is ignored. A migration from version 1 resets it to 0.

>

Lifecycle state. One of the Transition variants. Section 5 defines every variant and the fields it holds.

>

Key reservation. The Epoxy value that maps a key to a reservation ID and fixes the key to one datacenter.

>

Ready. The actor2::Ready { envoy_key } message. It tells Guard that the Actor is connectable on that host.

>

SetNotConnectable. The activity that deletes ConnectableKey and clears connectable_ts. It runs before the stop command for StopIntent, GoingAway, and ActorIntentStop, at engine/packages/pegboard/src/workflows/actor2/runtime.rs:939-959.

>

SleepIntent. The state between a sleep intent and the host stop event. A wake that arrives here is deferred with rewake_after_stop.

>

Slot. A concurrency permit for a pool. Two counters exist. Allocate increments the pool counter ActorSlotsKey. SetConnectable increments the envoy counter envoy::SlotsKey at engine/packages/pegboard/src/workflows/actor2/runtime.rs:916-920. Deallocate decrements the counters when acquired_slot is true.

>

Tombstone. An ActorByKeyKey entry with is_destroyed: true. It keeps the history of a destroyed key reservation so a new create scans past it.

>

Transition. The enum that holds the current lifecycle state and its per-state fields.
