00 Overview: the problem and the mental model

Rivet is an orchestrator for many keyed, stateful processes, which it calls Actors. An Actor is not a container and not a virtual machine (VM). An Actor is a task inside a node process that the operator already runs. In this document, operator means the person or team that runs the deployment. Node means one worker process that runs the operator's application with the Rivet Software Development Kit (SDK). Control plane means the rivet-engine service group that schedules Actors and routes requests. An Actor has a key, durable state, a SQLite database, a queue, realtime connections, and a schedule. SQLite is the name of the embedded relational database library, not an abbreviation. When the Actor is idle, it writes its state and unloads. When a request arrives, the control plane starts the Actor again on a node with capacity. This document gives the problem, the vocabulary, the two paths that meet at an Actor, and the map of the exploration. The later documents give the mechanism. Read this document first, then follow one of the two reading paths in section 8.

1. The problem: many small stateful processes

An agentic workload puts one process behind each agent, each session, each user, or each tenant. Each process needs identity, memory, a database, realtime connections, and a schedule. The processes are numerous and small. Most of them are idle at any moment. A request can arrive at any one of them at any time. The operator wants to add capacity by adding machines.

The obvious alternatives are a container for each process or a shared database with stateless functions.

1.1 The container alternative

A container or a pod gives each process its own image, file system, network namespace, and kernel boundary. Kubernetes can schedule it, restart it, and move it. This is a mature and well-understood design.

The cost is the start path. A new pod needs a scheduling decision, an image pull (unless the image is cached), a container start, and a health check. The project states about 6 seconds for a pod cold start on a pre-provisioned node and about 200 megabytes (MB) of memory for an idle Node.js pod. It states about 5,000 nodes for one Kubernetes cluster. A Kubernetes node is one worker machine in that cluster. The project marks these figures as typical published values, not as a matched benchmark (README.md:157). The comparison table is at README.md:141-148.

The second cost is density. A pod owns a fixed memory reservation and a persistent volume. Ten thousand idle agents mean ten thousand idle pods, or a scale-to-zero controller that adds the same start path back. The project states a 72.4 kilobytes (KB) resident set size (RSS) increase for one running Actor (README.md:156). The README states an increase. An increase implies a before-and-after measurement. The README does not state the baseline value. This document describes the baseline as the resident set of the node process before the Actor starts. That description is an inference from the word "increase". That number measures a running Actor inside a shared process. It does not measure a pod.

The third cost is the storage boundary. A pod gets a persistent volume. The volume has a size, and the operator must choose it. An Actor database that grows without a size decision does not fit that model.

1.2 The database alternative

A shared database plus stateless functions gives identity through a row and memory through a query. This design is simple to operate at small scale. It fails on three points.

First, the process does not exist. A function runs for one request and exits. There is no place to hold an open WebSocket, a queue, an in-memory cache, or a timer between requests. Second, every call is a database round trip. A hot Actor that handles many small messages pays a query for each message. Third, the database becomes a shared bottleneck and a shared failure domain. The operator must size one large database for all tenants.

1.3 What Rivet changes

Rivet keeps the process, but makes the process small and movable. The Actor is a task in a node process. Many Actors share one process. The Actor's state lives outside the process, so the Actor can unload and start again elsewhere. The request does not need the Actor's address. The control plane finds the Actor, wakes it, and forwards the request.

The design moves cost from the start path to the storage path. A cold start does not pull an image or boot a kernel. It schedules a task, creates or opens its storage, and runs the first request. The storage path must then carry the durability that the container file system used to carry.

Aha: Rivet makes the unit of scheduling a task, not a machine. The obvious alternative is one container or micro VM for each stateful agent. That alternative buys a hard isolation boundary and a familiar deployment unit. It pays an image pull, a kernel boot, a network namespace, and about 200 MB of memory for each idle agent (README.md:145, README.md:157). Rivet pays a different cost: many Actors share one process and one event loop. The source does not state a per-Actor memory or crash isolation guarantee beyond the separate database and file system. A native crash in the node process can affect every Actor on that node. Document 16 lists this as a risk that the benchmarks do not measure.

2.1 Actor, key, namespace, node, runner, envoy

The words below appear in every later document. The full glossary is document 19. This section gives the minimum needed to read the map.

Actor. A keyed, stateful process that Rivet schedules. The public type is rivet_types::actors::Actor. It holds the Actor identifier, the name, the optional key, the namespace identifier, the datacenter label, the runner name selector, the crash policy, and the lifecycle timestamps (engine/packages/types/src/actors.rs:7-38).

Actor identifier. A generated Id. The create path calls Id::new_v1 with the datacenter label (engine/packages/api-peer/src/actors/create.rs:35). The label is stored inside the 18-byte V1 identifier (engine/packages/util-id/src/lib.rs:35-68). The label is part of the identifier and does not change. The identifier is not the key. A client can create an Actor with no key at all.

Key. An optional string that a client supplies at create time. A reservation key is the lookup tuple that stops two Actors from claiming the same key. It is the tuple of namespace identifier, Actor name, and key (engine/packages/pegboard/src/keys/epoxy/ns.rs:8-21). Epoxy stores this tuple (section 5.5). The reservation key includes the Actor name, so the same key under two names uses two reservation keys. The public create path rejects an empty key and a key longer than 1,024 bytes (engine/packages/api-peer/src/actors/create.rs:6, :15-25).

An absent key and an empty string are different. No key means that the Actor has no key. An empty string is a key of length zero. The create path rejects the empty string (engine/packages/api-peer/src/actors/create.rs:15-18).

Namespace. A separator for Actors, keys, and node pools. The project documentation uses production and staging on one control plane as the example (docs/general/content/architecture.mdx:54). A namespace has a slug. The slug appears in Uniform Resource Locator (URL) and Application Programming Interface (API) requests.

Node. A long-running process that runs the operator's application with the Rivet Software Development Kit (SDK). It starts with registry.start(). It connects outbound to the control plane and hosts the Actors assigned to it (docs/general/content/nodes.mdx:7). A node needs no public address for Actor traffic (docs/general/content/architecture.mdx:38).

Runner. The client-side process that hosts Actors on the legacy version 1 path. The internal terminology file defines "Runner" as "the client-side runner code" (docs-internal/engine/TERMINOLOGY.md:5). The legacy gateway accepts the runner protocol family. The current runner protocol version is 7 (MK2) (engine/packages/runner-protocol/src/lib.rs:8-12). The gateway defaults to version 3 (MK1) when the runner record has no version (engine/packages/pegboard-gateway/src/lib.rs:895-907).

Envoy. The actor-hosting process on the user side on the newer Actor version 2 path. The internal rescheduling document defines the word this way (docs-internal/engine/actor-rescheduling.md:7). The newer path currently uses envoy protocol version 7 or 8. Version 8 is the current compiled version (engine/sdks/rust/envoy-protocol/build.rs:23-30). Both paths exist in this commit. A document must say which path a claim applies to.

Version words. Three different versions appear in this document. The Actor version is 1 or 2 and selects the hosting path. The phrase envoy version 2 is another name for the Actor version 2 path; it is not a process version. The envoy protocol version is the wire message set, from 1 through 8. The runner protocol version is the legacy wire message set, 3 or 7.

Envoy key. A string identifier for one envoy connection. It must have 3 to 128 identifier characters (engine/packages/pegboard-envoy/src/utils.rs:8-90). An identifier character is an ASCII digit, a lowercase letter, a hyphen, an uppercase letter, or an underscore. The first and last character cannot be a hyphen, and two hyphens cannot touch (engine/packages/util/src/check.rs:22-33). The control plane addresses the envoy through the topic pegboard.envoy.{namespace_id}.{envoy_key} (engine/packages/pegboard/src/pubsub_subjects.rs:113-138). That topic is the EnvoyReceiverSubject type. When the envoy connects, the control plane subscribes PegboardEnvoyWs to that subject and forwards each command over the envoy WebSocket (engine/packages/pegboard-envoy/src/lib.rs:109-131). The envoy process receives the command on that WebSocket.

Generation. A counter for one allocation of an Actor. It starts at 0 and increases on each allocation (engine/packages/pegboard/src/workflows/actor2/runtime.rs:15-34, :483-497). The workflow ignores an event from an older generation (engine/packages/pegboard/src/workflows/actor2/mod.rs:643-647). Gateway 3 sends the exact generation. Gateway 2 omits it and uses the highest live generation (section 4.5).

Control plane. The rivet-engine Rust binary. It schedules Actors, routes requests, and stores durable records. Every control plane instance runs the same services. Section 6 shows the service list.

Datacenter. A region with a label, a public URL, a peer URL, and a proxy URL (engine/packages/config/src/config/topology.rs:155-209). The topology lists one leader datacenter and any number of peer datacenters (engine/packages/config/src/config/topology.rs:7-14). The leader is a datacenter, not a process. The leader datacenter runs the Epoxy coordinator workflow (engine/packages/epoxy/README.md:526). The Actor identifier embeds the label of the datacenter that created it.

Bucket. An object storage bucket. The README calls it the only external dependency (README.md:262). Section 5.6 shows an important limit: in this commit, the cold object-storage tier is Enterprise-only, and the open-source software (OSS) build never writes cold rows (docs-internal/engine/oss-to-ee-upgrade.md:9-20).

Six more names appear in the table above. Their one-line definitions follow here. Guard is the routing proxy at the network edge. Pegboard is the scheduling and networking layer for Actors. Depot is the storage engine that stores SQLite pages in UniversalDB. UniversalDB is the transactional key-value store. Epoxy is the per-key consensus store that reserves Actor keys. Gasoline is the workflow engine. Section 9 repeats each one in one line.

2.2 The public Actor record

The public record is small. It carries the identity and the lifecycle timestamps. It does not carry the Actor's user state. The user state lives in the Actor database. The legacy KV snapshot is frozen for downgrade only.

The public record does not carry the workflow identifier, the runner identifier, the envoy_key, the generation, or the Actor version. The Actor version is 1 or 2; it is not a record revision. pegboard_actor_get_for_gateway reads those fields from the internal Output type (engine/packages/pegboard/src/ops/actor/get_for_gateway.rs:11-26). Section 4.4 uses them. Document 03 and 04 give the internal records.

The crash_policy field has three values: Restart, Sleep, and Destroy. Destroy is the default (engine/packages/types/src/actors.rs:40-47). The policy decides what happens after a failed start or a lost host. Document 03 gives the full behavior.

2.3 One concrete example

A client creates an Actor for one agent. The request body names the pool default, the Actor name agent, and the key agent-123. The namespace is production.

{
  "name": "agent",
  "key": "agent-123",
  "runner_name_selector": "default"
}

The words in the steps below have these meanings. A pool is a node pool: a group of nodes by name inside a namespace (docs/general/content/nodes.mdx:9). A serverful pool uses a long-lived envoy process (engine/packages/pegboard/src/workflows/actor2/alloc_serverful/mod.rs:20-29). A serverless pool has no long-lived envoy. The control plane sends a Hypertext Transfer Protocol (HTTP) request to the pool URL, and that host starts the Actor (engine/packages/pegboard/src/workflows/actor2/runtime.rs:401-481). A slot is one unit of the pool concurrency limit. Allocation takes a slot before it places an Actor (runtime.rs:217-243). The configured load balancer is the EnvoyLoadBalancer strategy that selects a serverful envoy (engine/packages/config/src/config/pegboard.rs:456-475). A rate-limit token is one permit from the per-namespace limiter. The create operation takes a permit before it continues (engine/packages/pegboard/src/ops/actor/create.rs:57-81).

3. The four separations

The project README describes four separations (README.md:31-57). Each separation answers one failure. These separations are the mental model. The mechanism behind each one is a later document.

3.1 The Actor is separate from its location

An Actor has an identifier, a key, and durable state. It does not own a machine. Pegboard chooses the runner or envoy that hosts the Actor now. If the host dies, the Actor starts on another host with the same state. The internal rescheduling document states that the newer path is Actor version 2 and envoy version 2, and that the legacy runner version 1 path still exists (docs-internal/engine/actor-rescheduling.md:7).

The failure answered is a dead node. The cost is a placement layer. The placement layer must know which hosts are alive, which hosts have capacity, and which host holds each Actor. Document 04 explains allocation and the envoy protocol. Document 03 explains the Actor lifecycle.

3.2 The request is separate from the process

A client sends an HTTP request or opens a WebSocket connection to Guard. Guard finds the Actor and forwards the request. The client never needs the address of the node. If the Actor is asleep, Guard wakes it and waits for the Ready message before it forwards the request (engine/packages/guard/src/routing/pegboard_gateway/mod.rs:531-561, :615-713).

The failure answered is a moving or sleeping Actor. The cost is a routing hop and a readiness protocol. The routing hop must not become a single bottleneck. The readiness protocol must handle a failed wake and a stop during the wait. Document 09 explains the routing order and the timeouts.

3.3 The database is separate from the disk

Each Actor has its own SQLite database. The SQLite engine runs in the node process. The Depot database object that stores the pages runs in the control plane (section 5.3). The Virtual File System (VFS) is the SQLite interface that replaces local file input and output. depot-client implements this VFS in the node process (engine/packages/depot-client/src/lib.rs:1-32). The VFS sends each page read and write to the control plane over a WebSocket connection. On the control plane, the Guard process hosts depot::Db in the pegboard-envoy crate (engine/packages/pegboard-envoy/src/conn.rs:31-57). Depot stores the pages in UniversalDB. UniversalDB commits the write through its driver. The driver is PostgreSQL or a local RocksDB store in this commit (engine/packages/config/src/config/db/mod.rs:10-21, engine/packages/pools/src/db/udb.rs:20-68). The EE build can add a cold tier that moves compacted shards to a bucket (docs-internal/engine/oss-to-ee-upgrade.md:9-20).

The failure answered is a full disk and a fixed volume size. The cost is a storage engine, a network hop, and a compaction workflow. The Actor's database is not a file on one machine. It is a set of rows that the storage layer can read from another machine. Document 06 explains Depot. Document 07 explains UniversalDB and its drivers.

The README says that "the bucket never sits on the write path" (README.md:68). The statement is true by design in the EE build, where compaction writes cold objects. The statement is vacuous in the OSS build, which has no cold tier and never writes cold rows. Section 5.6 gives the exact source conflict.

3.4 The workflow is separate from one execution

Gasoline runs a workflow as a series of durable steps. It records the result of each step in a history. When the workflow wakes again, it replays the history. A recorded step returns the recorded result and does not run the code again (docs-internal/engine/GASOLINE/OVERVIEW.md:12-30). An activity is one durable step inside a workflow. It wraps a native Rust function, and Gasoline records its result. Each activity can retry with backoff (docs-internal/engine/GASOLINE/OVERVIEW.md:9, :26).

The failure answered is a crash in the middle of a multi-step operation. The cost is a recorded history and a replay rule. A workflow that branches differently on replay raises WorkflowError::HistoryDiverged (docs-internal/engine/oss-to-ee-upgrade.md:22-27). A version check is a recorded history step. It records which branch the workflow took, so a replay can detect a different branch (docs-internal/engine/GASOLINE/OVERVIEW.md:30). This is why a code change that alters a workflow path needs a version check. Document 05 explains the engine.

4. The request path end to end

The request path has two parts. The control path creates and manages Actors. The data path carries the Actor's HTTP and WebSocket traffic. They meet at Guard and at the Pegboard layer, but they are not the same path. A reader who confuses them will expect every Actor request to pass through the public API. It does not.

4.4 The wake and readiness wait

The data path starts with a lookup. pegboard_actor_get_for_gateway reads the Actor's records from UniversalDB in one transaction. The output holds the namespace identifier, the workflow identifier, the key, and the runner name selector. It also holds the sleep, destroyed, and connectable flags, the runner identifier, the envoy key, the envoy protocol version, the generation, and the Actor version (engine/packages/pegboard/src/ops/actor/get_for_gateway.rs:11-26). The operation has a 5 second timeout (:28-33).

The output fields drive the next step. If destroyed is true, Guard returns pegboard::errors::Actor::NotFound (engine/packages/guard/src/routing/pegboard_gateway/mod.rs:465-467). If the Actor is asleep, Guard sends the Wake signal to the Actor workflow and waits for the signal to be accepted (:531-561). An asleep Actor is normally not connectable. The SetSleeping step deletes the connectable key (engine/packages/pegboard/src/workflows/actor2/runtime.rs:961-988). The normal sleep path is therefore wake first, then wait.

Guard then checks the record that it read before the wake. For an Actor version 2 Actor, it skips the wait only when the record has an envoy_key and the record is connectable (engine/packages/guard/src/routing/pegboard_gateway/mod.rs:563-569). The envoy_key is required because Gateway 2 and Gateway 3 address the envoy by that key. An Actor version 1 record has a runner_id instead, so it never takes this skip. handle_actor_v1 applies the same rule with runner_id (:858-862). Otherwise Guard waits for Ready (:570-578). A request with the x-rivet-skip-ready-wait header can also skip the wait (:1040-1050).

The wait is not a simple sleep. Guard creates the subscriptions before the first Actor lookup. It subscribes to four Actor version 2 messages: Ready, Stopped, Failed, and DestroyStarted. It also subscribes to five version 1 messages: Ready, Stopped, Failed, DestroyStarted, and MigratedToV2 (engine/packages/guard/src/routing/pegboard_gateway/mod.rs:364-405). It waits on the version 2 subscriptions with tokio::select! (:615-713). The branches are:

MigratedToV2 is a version 1 message. When it arrives, handle_actor_v1 calls handle_actor_v2 and continues the same request on the envoy path (engine/packages/guard/src/routing/pegboard_gateway/mod.rs:938-953). The version 2 select does not consume it.

A pool error is an active RunnerPoolError record for the Actor's runner pool (engine/packages/types/src/actor/error.rs:8-32). Guard creates a check_runner_pool_error_loop future before the loop (engine/packages/guard/src/routing/pegboard_gateway/mod.rs:607-613). That future waits 1 second, then reads the record every 2 seconds (:32-34, :1060-1100). Guard polls the future as one branch of tokio::select! (:695-700). The 1 second delay lets a flapping pool settle before Guard fails the request.

The 30 second timer is created inside the loop (engine/packages/guard/src/routing/pegboard_gateway/mod.rs:702). A Stopped rewake starts a new loop iteration, so the timer starts again. The timer measures the time since the loop iteration started, not the total wait.

The 30 second value comes from actor_ready_timeout (engine/packages/config/src/config/guard.rs:240-243). The source comment says the value stays high because serverless cold starts can take 10 to 20 seconds (:241-242).

After the wait, Guard reads the Actor record again. If the Actor is destroyed or its envoy_key changed, Guard returns ActorStoppedWhileWaiting (engine/packages/guard/src/routing/pegboard_gateway/mod.rs:716-733). This check closes the race between "the Actor became ready" and "the Actor stopped again".

4.7 What the network edge does not do

Guard does not run the Actor code. An action is one named handler that a client invokes on an Actor (docs/general/content/tracing.mdx:7, :51). Guard does not translate the user's action names. It forwards the HTTP request or the WebSocket frames. The Actor runtime inside the node process reads the request and calls the handler. This is why the project can say that the Actor runs on native Node.js or Bun with no custom runtime (README.md:290). The protocol is a tunnel, not a new application runtime.

The same design has a cost. The gateway must buffer or stream the body, enforce size limits, and handle a response start that never arrives. The 5 minute response start timeout and the 20 mebibytes (MiB) maximum response payload (engine/packages/config/src/config/pegboard.rs:395-398) are the visible budgets. Document 09 lists the rest.

5.2 Layer 1: the Actor SQLite database

The Actor sees a SQLite database. The RivetKit runtime creates the tables that the Actor uses for state, connections, queues, workflow storage, and alarms. The internal Actor KV document states that current RivetKit actors keep this data in internal SQLite tables after the first wake. The first wake is the first start on the migrated runtime. At that start, the runtime imports the legacy store into the SQLite tables. The legacy Actor KV store remains as a frozen downgrade snapshot (docs-internal/engine/ACTOR_KV.md:3-7).

The database is per Actor. It is not a shared table with an Actor identifier column. The isolation boundary is the database, not a query predicate. This is the property that lets one Actor use a normal SQLite schema and normal SQLite transactions.

The frozen downgrade snapshot is the last legacy key-value copy. The current runtime does not write Actor state there. A downgrade to an older build can read the snapshot. The snapshot is not fully frozen. One value is still mirrored: the inspector token is copied there for dashboard compatibility (docs-internal/engine/ACTOR_KV.md:5). The inspector token is the Actor credential that the dashboard inspection view uses (docs-internal/engine/ACTOR_KV.md:5, docs/general/content/mcp.mdx:3).

Document 06 explains the SQLite Virtual File System (VFS), the page format, and the migration behavior. Document 11 explains the tables that RivetKit creates.

5.3 Layer 2: Depot

Depot is the storage engine between the Actor SQLite database and UniversalDB. The Depot README states that Depot stores SQLite pages in UniversalDB and that UniversalDB is the durable source of truth (engine/packages/depot/README.md:3-5, docs-internal/engine/depot.md:7-10).

A commit is one UniversalDB transaction. The transaction appends a DELTA blob, updates the page index rows, writes the COMMITS and VTX rows, updates the head and quota counters, and writes a dirty marker (engine/packages/depot/README.md:131-151). The commit returns durable after the UniversalDB commit (:151).

Compaction is separate. The commit path does not publish SHARD rows and does not delete old history (docs-internal/engine/depot.md:53). A background Gasoline workflow plans the compaction, stages the output, publishes the SHARD rows, and later deletes the old rows. The invariant is stated directly: "commits write deltas directly to UDB; workflow compaction is the only publish/delete authority for compaction output" (docs-internal/engine/depot.md:24).

The PostgreSQL variant selects UniversalDB multi-node mode when a NATS message bus configuration is present (engine/packages/pools/src/db/udb.rs:19-68, engine/packages/universaldb/src/driver/postgres/database.rs:82-85). NATS is a messaging system; the name is not an abbreviation in the source. async-nats is the Rust client library for NATS (engine/packages/universaldb/src/driver/postgres/nats.rs:28, :71-94). NATS is required only when more than one control plane instance must share the transactional store. A single instance uses the in-process commit queue (engine/packages/universaldb/src/driver/postgres/commit.rs:52-60).

In multi-node mode, each control plane instance is both a follower and a leader candidate (engine/packages/universaldb/src/driver/postgres/shared.rs:31-52). The nodes elect one leader with a lease row in udb_lease. The lease has an epoch and a 10 second time to live (engine/packages/universaldb/src/driver/postgres/resolver/lease.rs:6-42). A candidate can take the lease only after it expires, and each acquisition increments the epoch (:15-42). The leader renews the lease (:44-63) and releases it on shutdown (:65-87).

A follower sends each commit to the leader by NATS request/reply (engine/packages/universaldb/src/driver/postgres/commit.rs:97-140). The request carries a deduplication key. The follower resends the same key across a leader failover, so the leader applies the commit at most once (:109-125). The deduplication state is durable. It is the udb_applied table, keyed by (client_node_id, client_seq) (engine/packages/universaldb/src/driver/postgres/database.rs:68-74). The leader writes one row for each applied commit (engine/packages/universaldb/src/driver/postgres/resolver/mod.rs:635). The leader applies the commit to PostgreSQL and publishes a new durable watermark (engine/packages/universaldb/src/driver/postgres/nats.rs:59-62, commit.rs:124-145). A durable watermark is the udb_lease.durable_version value (database.rs:57-63). The leader publishes each advance on the NATS watermark subject, and every node subscribes (nats.rs:59-62). A read-only transaction sends no commit (commit.rs:39-50).

Zone placement is a deployment choice. The code does not require a zone or a quorum. The source contains one elected leader and one PostgreSQL store.

The benchmark page states that two of three instances acknowledge each write, with at least one in another zone (docs/general/content/benchmarking.mdx:15). The code in this commit has one leader and one PostgreSQL store. The source does not show a two-of-three acknowledgement path. A PostgreSQL deployment outside this repository could add synchronous replication, but the page does not say that. This exploration cannot reconcile the statement with the source, and document 16 lists it as unverified.

Document 07 explains the key space, the transaction model, the drivers, and the limits. The overview needs one point: UniversalDB is a transactional store with a PostgreSQL or local RocksDB driver in this commit. It is not an object storage driver.

5.5 Layer 4: Epoxy

Epoxy is a geo-distributed, strongly consistent key-value store. It uses single-decree Fast Paxos for each key. A key is immutable by default (engine/packages/epoxy/README.md:1-3). A key can opt in to mutable overwrite (:3, :15). A committed immutable value never changes, so a replica that holds the value can serve a read locally (:9). A mutable key runs a new versioned round for each overwrite (:52). The README does not state how a replica that has not learned the decree answers a read. A joining replica pages the changelog from one active source while it applies live commits (engine/packages/epoxy/README.md:184-186, :311). Paging means reading the changelog in order from the first unread entry to the current end. Document 08 gives the read rule for a lagging replica and the catch-up protocol.

Epoxy is not the storage layer for SQLite pages. It reserves Actor keys. The Actor version 2 workflow calls the Epoxy propose operation with a check-and-set command on the reservation key (engine/packages/pegboard/src/workflows/actor2/keys.rs:201-235). The reservation key is the tuple of namespace identifier, Actor name, and key (engine/packages/pegboard/src/keys/epoxy/ns.rs:8-21). The value is the reservation identifier. A reservation identifier is a generated identifier that includes the datacenter label. It is not the Actor identifier (docs-internal/engine/ACTOR_KEY_RESERVATION.md:7-9, :20-22).

The reservation lifecycle is: Propose commits the reservation value, then get_reservation_for_key reads it with an optimistic read (engine/packages/pegboard/src/ops/actor/get_reservation_for_key.rs:21-69). An optimistic read reads the cached value without a lock. It assumes that the value does not change after it is set (docs-internal/engine/ACTOR_KEY_RESERVATION.md:18). Document 08 gives the full lifecycle and the conflict cases.

The Epoxy README names two Actor key operations (engine/packages/epoxy/README.md:37-42). The README does not attach those operations to Actor version 1. The actor version 2 code also calls Epoxy (engine/packages/pegboard/src/workflows/actor2/keys.rs:56-65, :211-235). The code wins. The accurate statement is: Epoxy reserves the key tuple on both Actor paths. The README's two-operation list is narrower than the code in this commit. Document 08 explains the protocol and the reservation semantics.

// engine/packages/epoxy/README.md:37-42
Rivet uses Epoxy for two workflows:

- `pegboard::workflows::actor::actor_keys::Propose` reserves an actor key with a single-key set-if-absent write.
- `pegboard::ops::get_reservation_for_key` resolves that reservation with an optimistic read.

Those workloads do not need cross-key ordering or shared global proposal metadata, so Epoxy keeps consensus state per key. For workloads that do need cross-key ordering in high-latency geo-distributed environments, EPaxos (Moraru et al., 2013) is a useful reference.

5.6 Layer 5: the bucket

The bucket is the part that the README describes as the only external durable store (README.md:69, README.md:262). The claim is true by design in the EE build: compaction writes cold objects, and a commit never waits for the bucket. The claim is vacuous in the OSS build: the OSS build has no cold tier and never writes cold rows. The OSS build keeps the cold-storage row schema but writes no cold rows. The internal upgrade document states this directly:

The EE build configures the cold tier with sqlite.workflow_cold_storage (docs-internal/engine/oss-to-ee-upgrade.md:45). The OSS Sqlite struct has no such field, and deny_unknown_fields rejects an EE configuration (engine/packages/config/src/config/sqlite.rs:18-20, docs-internal/engine/oss-to-ee-upgrade.md:60-62). A UniversalDB row is a key-value record. The cold shard reference is a row that points to an object in the bucket. The row can travel between builds. The object cannot. The database block is the two-variant enum in section 5.4. The pubsub block is separate. There is no object-storage configuration in the root in this commit.

These statements do not agree. The code and the self-host artifacts are the source for this exploration. The accurate statement is:

local RocksDB.

  • The cold object-storage tier exists in the EE build. The OSS build keeps its

5.7 The actual commit path and read path

The actual commit path in the OSS build is:

Actor SQLite (node process)
  -> depot-client VFS (SQLite Virtual File System, node process)
  -> envoy WebSocket to /envoys/connect
  -> pegboard-envoy handle_sqlite_commit (control plane)
  -> depot::Db::commit (control plane)
  -> one UniversalDB transaction
       DELTA, PIDX, COMMITS, VTX, META, quota, dirty marker
  -> PostgreSQL or RocksDB driver
  -> durable local or shared disk

depot::Db runs in the control plane, inside the pegboard-envoy crate (engine/packages/pegboard-envoy/src/conn.rs:31-57). The node does not host a Depot database. The node hosts the VFS from depot-client (engine/packages/depot-client/src/lib.rs:1-32). The VFS sends the commit over the envoy WebSocket, and handle_sqlite_commit receives it (engine/packages/pegboard-envoy/src/ws_to_tunnel_task.rs:1668-1707).

The EE build adds this after compaction:

compaction shard
  -> cold object
  -> object storage bucket

The actual read path is:

SQLite read (node process)
  -> depot-client VFS (node process)
  -> envoy WebSocket
  -> pegboard-envoy handle_sqlite_get_pages (control plane)
  -> depot::Db::get_pages (control plane)
  -> one UniversalDB transaction
       head, PIDX, ancestry, DELTA or SHARD
  -> PostgreSQL or RocksDB driver

handle_sqlite_get_pages receives the page request on the control plane (engine/packages/pegboard-envoy/src/ws_to_tunnel_task.rs:1621-1651). The hosting rule above applies to both paths: the node sends a request over its outbound WebSocket, and the control plane answers.

The read path falls back to the newest SHARD when the DELTA is absent or reclaimed (docs-internal/engine/depot.md:26-35). An EE branch can hold a cold shard reference whose object is not reachable in OSS. In that case the read fails with ShardCoverageMissing rather than returning zero-filled bytes (docs-internal/engine/depot.md:36-37). This is a deliberate correctness rule.

5.8 What "durable" means here

A write is durable when the UniversalDB transaction commits. The commit path does not wait for the bucket. That is the design claim that the README makes when it says the bucket is not on the write path (README.md:68). In the OSS build, the durability comes from the PostgreSQL transaction or from the local RocksDB write. In the EE build, the cold tier adds a second copy for old data.

The benchmark table uses a different meaning of "durable" for the SQLite insert: "One 128-byte SQLite row inserted in autocommit mode. Timed around the query on the node, including the write to a majority of disks across zones" (docs/general/content/benchmarking.mdx:30). The timer starts and ends on the node around the query. This exploration infers that the measured interval contains the VFS call, the envoy WebSocket round trip, the depot::Db::commit transaction, the UniversalDB commit, and the disk acknowledgement. The query cannot complete without those steps. The page does not list those layers, so treat the list as an inference. The interval excludes the client request, Guard routing, the Actor wake, and the HTTP response. The page gives no separate client-side timer for this row.

That measurement uses the three-instance control plane and the two-of-three acknowledgement statement. The source in this commit does not show that acknowledgement path (section 5.4). The page does not say how the deployment produced it. The run used three control-plane instances, so it was not the single-instance default configuration. Document 16 states which measurements were reproduced and which were not.

The two backfills here fill the runner name selector and the serverless data (engine/packages/bootstrap/src/backfill.rs:4-29). The Gas pruner is the Gasoline workflow that removes old workflow history (engine/packages/bootstrap/src/lib.rs:136-146).

The service manager starts each service and restarts a crashed service after one second. The Service struct holds the name, the kind, the run function, and a flag for graceful shutdown (engine/packages/service-manager/src/lib.rs:15-28). The ServiceKind enum decides the behavior:

Core carries the comment "Run no matter what". In this commit, Core has no separate code path. It maps to ServiceBehavior::Service like the other indefinite kinds (engine/packages/service-manager/src/lib.rs:50-71). The comment states an intent that the code does not enforce.

The Service flag controls shutdown. A true value means the manager leaves the task running and waits for it to exit. A false value means the manager aborts the task immediately (engine/packages/service-manager/src/lib.rs:383-391).

The runtime wraps the process in a Tokio multi-thread runtime. It initializes OpenTelemetry, starts a metrics sampler, and selects between the main future and a shutdown notification:

// engine/packages/runtime/src/lib.rs:24-51
/// Returns `None` if the runtime was shut down manually.
pub fn run<F: Future>(f: F) -> Option<F::Output> {
	// Build runtime
	let mut rt_builder = build_tokio_runtime_builder();
	let rt = rt_builder.build().expect("failed to build tokio runtime");
	let output = rt.block_on(async move {
		let notify = SHUTDOWN
			.get_or_init(|| std::future::ready(Arc::new(Notify::new())))
			.await
			.clone();

		// Must be called from within a tokio context
		let providers = init_otel_providers();
		traces::init_tracing_subscriber(&providers);

		tokio::spawn(sample_runtime_metrics(tokio::runtime::Handle::current()));

		tokio::select! {
			_ = notify.notified() => {
				tracing::info!("shutting down runtime");
				None
			},
			res = f => Some(res),
		}
	});

	output
}

The runtime builder uses an 8 MiB stack for the worker threads. The source comment says async-nats requires a fat stack (engine/packages/runtime/src/lib.rs:121-122). This is a concrete cost of the message bus dependency in the OSS build.

6.2 Identical instances

The README says control plane instances are identical, run every service, and find each other through the bucket (README.md:69). The first two parts match the code. The start command builds one service list for every instance. There is no per-instance role in run_config.rs.

The third part does not match the OSS source in this document's scope. The services use UniversalDB and the pubsub layer. The PostgreSQL driver can run in multi-node mode when a NATS configuration is present (engine/packages/pools/src/db/udb.rs:22-45). The self-host Kubernetes README names a NATS cluster and PostgreSQL (self-host/control-plane/kubernetes/README.md:5). There is no bucket-based discovery in the files this document opens.

The accurate statement is: every instance runs the same services, and the instances coordinate through the shared storage and pubsub configuration. The README's bucket-discovery sentence is not verified in this commit. Document 02 traces service startup and document 15 covers the deployment artifacts.

A request can reach any control plane instance. The Actor's envoy connects outbound to one instance at /envoys/connect (engine/packages/guard/src/routing/envoy.rs:28-61). That instance runs PegboardEnvoyWs and subscribes to EnvoyReceiverSubject for the envoy key (engine/packages/pegboard-envoy/src/lib.rs:43-131). Every instance shares UniversalPubSub. Any instance can publish to that topic (engine/packages/pegboard/src/pubsub_subjects.rs:113-138). Guard on instance A can therefore reach an Actor whose envoy connected to instance B through the shared pubsub. If the Actor is in another datacenter, Guard uses the peer proxy_url instead (section 4.6).

6.3 Nodes

A node is not a control plane service. It is a process that runs the operator's application with the Rivet SDK. It connects outbound to the control plane and hosts the Actors assigned to it (docs/general/content/nodes.mdx:7). The node has no inbound port for Actor traffic. This is what lets an Actor run inside a private network.

The node pool groups nodes by name inside a namespace. The control plane refuses a node whose pool does not exist (docs/general/content/nodes.mdx:9, :25). The pool name in the create request is runner_name_selector. It selects the pool, not a single machine.

7.2 The method

The benchmark ran on October 25, 2026, in Azure eastus2 across three availability zones (docs/general/content/benchmarking.mdx:7, :13). The control plane had three instances, one per zone. Each was a Standard_L8as_v5 with 8 virtual central processing units (vCPU), 64 gibibytes (GiB) of memory, and about 1.7 terabytes (TB) of local Non-Volatile Memory Express (NVMe) storage (docs/general/content/benchmarking.mdx:14). The page states that every write was acknowledged by two of three instances, and at least one of the two was in another zone (:15). The source code does not contain that quorum (section 5.4).

The node and the client ran on one Standard_D16as_v7 VM with 16 vCPU in the first zone (docs/general/content/benchmarking.mdx:16). The software was Debian 13, Node.js 24, and release builds (:17). The object storage was Azure Blob Storage in the same region with locally redundant storage (:18). Requests used plain HTTP inside the region over reused connections, with one request in flight. Create and wake requests had 20 ms gaps. The table reports every successful sample with nearest-rank percentiles and no trimming (:20). The page does not name the build. The setup lists Azure Blob Storage (:18). The results table has no object-storage row. The OSS configuration in section 5.6 has no bucket block. A reader therefore cannot tell whether the benchmark used the OSS build or the EE build. The page does not say.

The page says to use a new key for each create (:51). It does not state that the benchmark deletes and recreates each Actor. The 1,500 cold-start samples are therefore 1,500 new Actors, not 1,500 restarts of one Actor. The page names one node in the first zone (:16). It does not name which of the three control plane instances that node uses. The 20 ms gaps pace the requests, and they are not part of a reported latency (:20).

Two cold-start scopes are in play. The 6.92 ms figure is an Actor cold start: create, schedule, open storage, and start the Actor (:28). The 10 to 20 second figure is a serverless host cold start. It appears in the Guard comment that justifies the 30 second ready timeout (engine/packages/config/src/config/guard.rs:241-243). The first figure is the Actor task. The second figure is the serverless host. They are not the same measurement.

7.3 What this exploration did not do

This exploration did not run the benchmark. It did not measure cold start, wake, memory, or throughput. Every number in section 7 comes from the project README or the project documentation page. The source confirms the paths that the benchmark measures, but it does not confirm the latency values.

The Kubernetes comparison figures are typical published values, not a matched benchmark. They are about 6 seconds for a pod cold start on a pre-provisioned node and about 200 MB for an idle Node.js pod. The cluster limit is about 5,000 Kubernetes nodes (README.md:157). A Kubernetes node is one worker machine. These figures do not come from the Rivet benchmark run.

The 72.4 KB figure is an RSS increase per running Actor. An increase implies a before-and-after measurement. The README does not state the baseline value. This document describes the baseline as the resident set of the node process before the Actor starts. That description is an inference from the word "increase", not a statement in the README. The figure is not the total memory of a node divided by the number of Actors. It does not include the memory of the shared runtime, the Actor code, or the SQLite cache. The README does not give a confidence interval or a sample count for this figure (README.md:156). Document 16 lists this as an open question.
