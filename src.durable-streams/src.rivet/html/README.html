Rivet: Actors as durable processes

Rivet is an orchestrator for stateful processes that it calls Actors. An Actor is not a container and not a virtual machine. An Actor is a task inside a node process that the operator already runs. It has a key, durable state, a Structured Query Language (SQLite) database, a queue, realtime connections, and a schedule. When the Actor is idle, it writes its state and unloads. When a request arrives, the control plane starts the Actor again on any node that has capacity.

The control plane is one Rust binary. The product description says that it has no separate database and no message bus, and that the only external durable store is an object storage bucket. The open-source code in this commit does not match that description in full. UniversalDB has two drivers: RocksDB on a local disk, and PostgreSQL. The cold tier that moves SQLite pages to object storage is Enterprise-only. Instances coordinate through UniversalDB and an optional NATS pub/sub service. This exploration states the product claim and the open-source configuration, and it marks which is which. The same binary runs on one laptop or on a cluster of identical instances.

The one-page thesis

Rivet is built on four separations.

1. The Actor is separate from its location. An Actor has a key and durable state. It does not own a machine. Pegboard decides which runner hosts the Actor now. If the runner dies, the Actor starts on another runner with the same state. This is the virtual Actor pattern. The source calls the scheduling unit a runner, and the newer path calls its host process an envoy.

2. The request is separate from the process. Guard receives an HTTP request or a WebSocket connection and routes it to the runner that hosts the Actor. The client never needs to know the address of the node. When the Actor is asleep, Guard wakes it and waits for the ready signal before it forwards the request.

3. The database is separate from the disk. Each Actor has its own SQLite database. A write goes to a log and to the durable store under UniversalDB. The product description says that a write is acknowledged after a quorum of control plane instances has it, and that a background process moves pages to the bucket. In the open-source build, UniversalDB writes to RocksDB or PostgreSQL, and the cold tier that writes to object storage is Enterprise-only. The bucket is not on the write path in either build. This is the bottomless storage claim.

4. The workflow is separate from one execution. Gasoline runs a workflow as a sequence of activities. Each activity result is recorded in a history. After a crash, Gasoline replays the history and does not repeat a recorded activity. This gives durable execution without a separate workflow server.

Each separation answers one failure. The first answers a dead node. The second answers a moving Actor. The third answers a full disk. The fourth answers a crash in the middle of a multi-step operation.

What this exploration is not

It is not a user guide. It does not teach a developer to write an Actor. It explains how the implementation works and why it is built that way. The official documentation is at rivet.dev.

It is not a security audit. Document 13 describes the authentication and authorization design. It does not test it.

It does not run the code. Every claim comes from reading the source, the tests, or the project documents. Document 16 states which measurements are reported by the project and which are not reproduced here.
