14 Observability and operations

This document shows how an operator sees and controls a running Rivet cluster. It covers what each process reports, where it reports it, and which command answers which question. It reads the source at commit 4a58441c50d1ce20d8803cfb1ab7c3285a5141d6, version 2.3.31. All paths are relative to /Users/darkvoid/GitSources/src.Rivet/rivet unless the text says otherwise.

The central fact is simple. Each engine process runs every service by default, and every service writes to one Prometheus registry in that process. Logs and Sentry events, OpenTelemetry traces, and Pyroscope profiles leave the process through separate paths. The rivet-engine command line interface (CLI) uses three transports when it contacts a running engine. The first is an HTTP call to one peer Application Programming Interface (API). The second is a direct read or write on UniversalDB (UDB). The third is a publish call on the publish-and-subscribe layer. The separate rivet CLI is a cloud and development tool. Section 7.11 lists the transports for both CLIs and the transport for each rivet-engine command. The operator does not need a separate agent for each subsystem. A cluster can have many engine processes. Each process has its own registry and its own metrics port (engine/packages/engine/src/run_config.rs:4-67).

2. Telemetry, Sentry, and what leaves the process

Rivet sends error telemetry to Sentry unless the operator disables it. The configuration field is telemetry.enabled, and its default is true (engine/packages/config/src/config/telemetry.rs:4-14). The comment in the source says "Telemetry is opt-out". The package README shows the configuration block that turns it off: "telemetry": { "enabled": false } (engine/packages/telemetry/README.md). The flag controls the Sentry client only. It does not stop metrics, OpenTelemetry traces, logs, or Pyroscope profiles. Those paths have their own gates, and the table at the end of this section lists them.

The binary contains one fixed Sentry Data Source Name (DSN). It is a constant at engine/packages/telemetry/src/lib.rs:4. The host in that DSN is o4504307129188352.ingest.us.sentry.io. An operator who does not want any event to reach that host must set the flag to false. There is no environment variable override for the DSN in this file.

rivet_telemetry::init reads the flag first. It returns None and installs nothing when telemetry is disabled. Otherwise it installs the Sentry client with the fixed DSN and the crate release name. It then calls configure_scope and returns a sentry::ClientInitGuard. The guard must stay alive for the life of the process. The engine holds it in main_inner as _guard (engine/packages/engine/src/main.rs:46).

// engine/packages/telemetry/src/lib.rs:7-23
pub fn init(config: &rivet_config::Config) -> Option<sentry::ClientInitGuard> {
	if !config.telemetry.enabled {
		return None;
	}

	let guard = sentry::init((
		SENTRY_URL,
		sentry::ClientOptions {
			release: sentry::release_name!(),
			..Default::default()
		},
	));

	sentry::configure_scope(|scope| configure_scope(scope, config));

	Some(guard)
}

The scope configuration is the privacy-sensitive part. It sets three tags and nothing else. The comment in the source states the reason: configuration serialization preserves secrets, and even ordinary strings such as server URLs can contain credentials. The tags are fixed strings.

// engine/packages/telemetry/src/lib.rs:25-53
fn configure_scope(scope: &mut sentry::Scope, config: &rivet_config::Config) {
	// Only send fixed, allowlisted labels. Config serialization preserves secrets, and
	// even ordinary strings (such as server URLs) can contain credentials.
	scope.set_tag(
		"database",
		match config.database() {
			Database::Postgres(_) => "postgres",
			Database::FileSystem(_) => "file_system",
		},
	);
	scope.set_tag(
		"pubsub",
		match config.pubsub() {
			PubSub::Nats(_) => "nats",
			PubSub::Memory(_) => "memory",
		},
	);
	let cache = config.cache();
	scope.set_tag(
		"cache",
		if cache.enabled {
			match cache.driver() {
				CacheDriver::InMemory => "in_memory",
			}
		} else {
			"disabled"
		},
	);
}

Aha: The author sends an allowlist of class names, not the configuration object. The obvious alternative is to attach the configuration to the Sentry scope for rich debugging. That alternative leaks passwords and tokens, because Secret hides values only from Debug and not from serialization (engine/packages/config/src/secret.rs:28-35, engine/packages/config/src/secret.rs:37-45). The allowlist costs some diagnosis detail and removes a credential leak.

The rest of what leaves the process comes from two places. The first is rivet_telemetry::capture_error, which wraps sentry::integrations::anyhow::capture_anyhow and returns a Sentry event Universally Unique Identifier (UUID) (engine/packages/telemetry/src/lib.rs:55-57). main_inner calls it for a configuration load error and for a command error. The second is the sentry::integrations::tracing::layer() in the tracing subscriber. Rivet does not configure that layer's event filter in this commit. Therefore the sentry crate default decides which tracing events become Sentry events or breadcrumbs. This document did not verify that crate default, because the crate source is not in the checkout. Treat the event selection as unverified.

The tracing subscriber installs the Sentry layer even when telemetry is off (engine/packages/runtime/src/traces.rs:62-63). With telemetry.enabled set to false, rivet_telemetry::init returns None and installs no client. The layer is present, but it has no client to receive an event. The source in this checkout does not show the layer sending anything in that state.

The build enables a fixed set of Sentry features. The workspace entry sets default-features = false and enables anyhow, backtrace, contexts, debug-images, panic, reqwest, rustls, and tracing (Cargo.toml:214-226). The client crate version is 0.45.0 (Cargo.lock:6865-6883). The anyhow integration is active through capture_error. The panic, contexts, backtrace, and debug-images integrations come from the enabled features. The tracing integration is active because the subscriber installs its layer. The source does not attach Actor state, Structured Query Language (SQL) text, or request bodies to the scope.

One caution is necessary. The source proves that the scope tags are an allowlist. It does not prove that every captured event field is free of user data. A tracing event can carry fields that an instrumented function recorded. An operator with a strict data policy should set telemetry.enabled to false and use only local logs, metrics, and traces.

3. OpenTelemetry: one provider, traces only

This commit configures a tracer provider and no other OpenTelemetry provider. The Rust source in engine/packages/metrics-server/src/providers.rs builds an SdkTracerProvider with a batch span exporter. It does not build an SdkMeterProvider or an SdkLoggerProvider. A search for those type names in the metrics server, runtime, and metrics crates finds no match. Metrics stay on the Prometheus registry, and logs stay on the tracing subscriber.

The provider starts only when the environment variable RIVET_OTEL_ENABLED is exactly the string "1" (engine/packages/metrics-server/src/providers.rs:113). The function returns None in every other case. rivet_runtime::run calls it before it installs the tracing subscriber, and it passes the result to the subscriber (engine/packages/runtime/src/lib.rs:35-40).

// engine/packages/metrics-server/src/providers.rs:112-124
pub fn init_otel_providers() -> Option<OtelProviderGuard> {
	let enable_otel = std::env::var("RIVET_OTEL_ENABLED").map_or(false, |x| x == "1");

	if enable_otel {
		opentelemetry::global::set_text_map_propagator(TraceContextPropagator::new());

		let tracer_provider = init_tracer_provider();

		Some(OtelProviderGuard { tracer_provider })
	} else {
		None
	}
}

The exporter is an OTLP gRPC span exporter. It uses the tonic transport and the gRPC protocol. The endpoint comes from RIVET_OTEL_GRPC_ENDPOINT, and the default is http://localhost:4317 (engine/packages/metrics-server/src/providers.rs:81-92). The provider batches spans before export. The source does not set a batch timeout, queue size, or retry policy. The pinned opentelemetry_sdk crate version 0.28 supplies those values (Cargo.toml:335-337). This document does not state the numbers, because the crate source is not in the checkout.

The exporter uses the endpoint exactly as written. The builder sets only the transport, the protocol, and the endpoint (engine/packages/metrics-server/src/providers.rs:86-92). It sets no Transport Layer Security (TLS) option, certificate, header, or authentication token. The workspace build enables trace, metrics, logs, and grpc-tonic, and it enables no TLS feature (Cargo.toml:331-333). Those are features of opentelemetry-otlp. The rustls feature in section 2 belongs to the Sentry build, a different dependency, and it does not enable TLS here. An https:// endpoint therefore does not work in this build. Use a plain http:// collector on a trusted network, or terminate TLS in a local collector process.

// engine/packages/metrics-server/src/providers.rs:86-109
fn init_tracer_provider() -> SdkTracerProvider {
	let exporter = opentelemetry_otlp::SpanExporter::builder()
		.with_tonic()
		.with_protocol(opentelemetry_otlp::Protocol::Grpc)
		.with_endpoint(otel_grpc_endpoint())
		.build()
		.unwrap();

	let initial_ratio = std::env::var("RIVET_OTEL_SAMPLER_RATIO")
		.ok()
		.and_then(|s| s.parse::<f64>().ok())
		.unwrap_or(0.001);

	let dynamic_sampler = DynamicSampler::new(initial_ratio);

	let _ = SAMPLER.set(dynamic_sampler.clone());

	SdkTracerProvider::builder()
		.with_sampler(Sampler::ParentBased(Box::new(dynamic_sampler)))
		.with_id_generator(RandomIdGenerator::default())
		.with_resource(resource())
		.with_batch_exporter(exporter)
		.build()
}

The sampler is a two-layer design. The outer layer is ParentBased. A child span follows the sampling decision of its parent. The inner layer is a custom DynamicSampler that reads a TraceIdRatioBased ratio from an Arc> each time it samples (engine/packages/metrics-server/src/providers.rs:12-54). The initial ratio is RIVET_OTEL_SAMPLER_RATIO, and the default is 0.001. That is one sampled trace for every one thousand trace identifiers. A poisoned lock means a thread panicked while it held the write guard. The read then returns Err, and the sampler uses the hard-coded literal 0.001 (engine/packages/metrics-server/src/providers.rs:42). That literal is not the operator's initial value. A panic during set_sampler_ratio therefore resets the ratio to one in one thousand, not to the value in the configuration.

The dynamic part exists so that an operator can change the ratio without a restart. set_sampler_ratio writes the new value into the same lock (engine/packages/metrics-server/src/providers.rs:58-68). The dynamic configuration service calls it when it receives a tracing configuration message. Section 5 explains that message path.

The resource describes the process. resource() sets the service name from rivet_env::service_name() and adds a service.version attribute with the crate version and the semantic-conventions schema URL (engine/packages/metrics-server/src/providers.rs:70-79). The propagator is TraceContextPropagator, which is the World Wide Web Consortium (W3C) trace context format.

OtelProviderGuard owns the provider. Its Drop implementation calls tracer_provider.shutdown() and logs an error if shutdown fails (engine/packages/metrics-server/src/providers.rs:126-137). The shutdown call flushes the batch exporter. The guard lives in rivet_runtime::run for the duration of the runtime.

What leaves the process is a set of spans. Each span has the resource above, the span name, the span kind, attributes, events, and links that the instrumented code records. Rivet does not add Actor state or SQL text in this file. The #[tracing::instrument] attributes in the codebase decide the span names and the recorded arguments. An operator with a strict data policy should review those attributes before enabling export.

4. Metrics: one registry for every service

Every engine subsystem that records metrics uses one process-wide Prometheus registry. The registry is a lazy_static in rivet_metrics. It uses the namespace "rivet" and an empty set of constant labels:

// engine/packages/metrics/src/registry.rs:1-7
use prometheus::*;

lazy_static::lazy_static! {
	pub static ref REGISTRY: Registry = Registry::new_custom(
		Some("rivet".to_string()),
		Some(labels! { })).unwrap();
}

The namespace changes the exposition name. A metric that a subsystem registers as epoxy_proposals_total appears as rivet_epoxy_proposals_total. This document uses the registered name in tables and says "exposition name" when the prefix matters. The empty constant labels mean that a scrape does not carry a cluster label. An operator who runs several clusters must add that label in the scrape configuration.

The metrics service is a small HTTP server. It binds config.metrics.host() and config.metrics.port(). The defaults are :: and 6430 (engine/packages/config/src/config/metrics.rs:14-21, engine/packages/config/src/defaults.rs:4-13). A bind failure is fatal: the service logs the error and calls std::process::exit(1) (engine/packages/metrics-server/src/server.rs:17-25). A bind failure also skips the OpenTelemetry flush. The call does not run Rust destructors, so OtelProviderGuard::drop never flushes the span batch (engine/packages/metrics-server/src/providers.rs:126-137). The server has no route table. It reads the request, ignores the path, gathers the registry, encodes it with TextEncoder, and returns status 200 with the encoder content type (engine/packages/metrics-server/src/server.rs:38-54). A scrape of /metrics, /, or any other path returns the same body.

// engine/packages/metrics-server/src/server.rs:38-54
async fn serve_req(_req: Request<Body>) -> Result<Response<Body>, hyper::Error> {
	let encoder = TextEncoder::new();

	let metric_families = rivet_metrics::REGISTRY.gather();
	let mut buffer = Vec::new();
	encoder
		.encode(&metric_families, &mut buffer)
		.expect("encode");

	let response = Response::builder()
		.status(200)
		.header(CONTENT_TYPE, encoder.format_type())
		.body(Body::from(buffer))
		.expect("response");

	Ok(response)
}

Aha: The metrics server has no /metrics route and no health route. The obvious design is a router with a metrics path. The author instead answered every request with the full registry. This removes a configuration mismatch between the scrape path and the server path, and it makes the service trivial to probe. The cost is that any request, including one from a scanner, causes a full registry gather and encode.

The engine's own API metrics show the shape of an instrumented subsystem. The middleware records pending requests, total requests, duration, and errors. The labels are router, method, and path, plus status and error on the duration and error metrics (engine/packages/api-builder/src/metrics.rs:5-31).

The runtime metrics are sampled on a five-second interval. The sampler reads the Tokio runtime handle and updates the queue depths, the active task count, and the blocking thread counts. It also updates per-worker overflow, local queue depth, and busy time (engine/packages/runtime/src/lib.rs:157-207). The sampler interval is five seconds, and the sampler always runs.

The task poll histogram is the only runtime metric that needs a poll hook. The gate is env::var("TOKIO_RUNTIME_METRICS").is_ok(), so any value enables it, including an empty value (engine/packages/runtime/src/lib.rs:75). The variable must be present before the runtime starts. A value of "0" or "false" does not disable the metric. The source does not support a runtime toggle.

The labels matter for diagnosis. node_id identifies one process, not one host. The labels below deserve a warning. path on the API metrics is a matched route template, or the string "unknown", so its cardinality follows the route table (engine/packages/api-builder/src/middleware.rs:95-100). namespace_id, node_id, runner_name, workflow_name, and activity_name are unbounded sets from the database. The RivetKit side has one important rule. The engine package comment at engine/CLAUDE.md:82-84 states that RivetKit core records process-wide Prometheus metrics but does not serve them over HTTP. A user renders them with registry.routes.prometheusMetrics() in TypeScript or Registry::prometheus_metrics() in Rust and mounts the response on a user router. The same comment states that there is no per-Actor /gateway//metrics route and no serverless /metrics route. An operator who expects an Actor-level metrics endpoint will not find one in this commit.

fn apply(update: &SetTracingConfigMessage) {
	tracing::debug!(
		filter = ?update.filter,
		sampler_ratio = ?update.sampler_ratio,
		"received tracing config update"
	);

	// An absent field leaves the current value alone, and an explicit null resets it to the default.
	match &update.filter {
		Some(Some(filter)) => {
			if let Err(err) = rivet_runtime::reload_log_filter(filter) {
				tracing::error!(?err, "failed to reload log filter");
			}
		}
		Some(None) => {
			if let Err(err) = rivet_runtime::reload_log_filter("") {
				tracing::error!(?err, "failed to reload log filter to default");
			}
		}
		None => {}
	}

	match update.sampler_ratio {
		Some(Some(ratio)) => {
			if let Err(err) = rivet_metrics_server::set_sampler_ratio(ratio) {
				tracing::error!(?err, "failed to reload sampler ratio");
			}

		Some(None) => {

The publish uses PublishOpts::broadcast() (engine/packages/engine/src/commands/tracing.rs:36-40). A broadcast always uses the configured pubsub driver. The memory optimization is a shortcut that delivers to one in-process subscriber and skips the driver. The driver enables that shortcut only for a OneSubscriber publish with an in-process receiver (engine/packages/universalpubsub/src/pubsub.rs:364-390). A broadcast has no single receiver, so the shortcut does not apply.

The memory driver stores subscribers in a process-local map (engine/packages/universalpubsub/src/driver/memory/mod.rs:25-50). The default driver is memory (engine/packages/config/src/config/pubsub.rs:6-101). A separate rivet-engine config update or rivet-engine tracing config process therefore publishes to a map that no engine process reads. The command prints success because the publish call succeeded. Use the NATS driver for a cluster that accepts these commands from a separate process. The NATS default address is 127.0.0.1:4222, and every engine process and the CLI must use the same addresses.

The subject has no datacenter field. A broadcast reaches every datacenter that shares the NATS deployment. The command does not contact one process at a time. This behavior is why one command can change a whole cluster, and why one command can change more than the operator intended. The --services flag does not change the scope. The dynamic_config service must run in each target process. The listener in engine/packages/dynamic-config/src/lib.rs:1-29 applies the message to its process. The command does not wait for an apply acknowledgement.

reload_log_filter rebuilds an EnvFilter from the new specification and calls handle.reload. The handle is a global OnceLock> that init_tracing_subscriber set at startup (engine/packages/runtime/src/traces.rs:10-12, engine/packages/runtime/src/traces.rs:177-192). A process that did not initialize the subscriber returns the error "reload handle not initialized".

The log file path is optional. logs.redirect_logs_dir is an Option (engine/packages/config/src/config/logs.rs:5-10). When it is set, the start command creates a rivet_logs::Logs with a seven-day retention constant (engine/packages/engine/src/commands/start.rs:7-31). The log writer rotates at the Coordinated Universal Time (UTC) day boundary. It names the file log-%m-%d-%y, calls dup2_stdout and dup2_stderr on the file descriptor, and prunes files older than the retention (engine/packages/logs/src/unix.rs:64-113).

Aha: The log redirect changes the file descriptors of the whole process, not the sink of one layer. That means every service in the process writes to the same daily file. The obvious alternative is a per-service file. The author chose one file so that a node has one log stream to collect and one retention rule. The cost is that a noisy service can dominate the file, and a filter change affects all services at once.

6. Profiling with Pyroscope

Central Processing Unit (CPU) profiling is off by default and can be turned on at runtime. The profiler is a Pyroscope agent with a pprof_backend. It requires a pyroscope configuration block. The block has a required server_url and an optional sample_rate whose default is 100 Hertz (Hz) (engine/packages/config/src/config/pyroscope.rs:4-20). The presence of the block makes profiling available. It does not start the agent.

server_url is a plain string. The configuration comment defines it as the base URL of the Pyroscope server, and Rivet passes it unchanged to the agent builder (engine/packages/config/src/config/pyroscope.rs:7-10, engine/packages/profiling/src/pyroscope.rs:93-102). The configured sample_rate is the fallback. A runtime message that carries a rate overrides it, because the service calls update.sample_rate.unwrap_or(default_sample_rate) (engine/packages/profiling/src/pyroscope.rs:52).

The profiling service is a Core service. When the block is present, it subscribes to the UniversalPubSub subject rivet.debug.profile.config and waits for a message. When a message enables profiling, it builds and starts an agent. When a message disables profiling, it stops and shuts down the agent (engine/packages/profiling/src/pyroscope.rs:18-82).

The builder call passes six positional values (engine/packages/profiling/src/pyroscope.rs:85-105). Value one is server_url. Value two is the string "rivet-engine". Value three is sample_rate. Value four is the same string, "rivet-engine". Value five is the Rivet crate version. Value six is the pprof backend. The call gives no names to values two and four, and the two strings are identical. The pyroscope crate version is 2.0.5 (Cargo.lock:4675-4678), and its source is not in the checkout. This document therefore cannot verify which of the two strings is the application name and which is a second label. Do not use the literal string as a per-process identifier.

The agent pushes a pprof CPU profile to the configured Pyroscope server. The agent version is the Rivet crate version. The operator starts profiling with the CLI. The command sends an HTTP PUT to the peer API endpoint /debug/profile/config. The default endpoint is http://localhost:6421 (engine/packages/engine/src/commands/profile.rs:8-22).   3. The agent pushes profiles to pyroscope.server_url on the crate schedule.

The command prints "Profiler enabled" or "Profiler disabled" when the peer API returns a success status. On a failure it prints the status and the response body and returns an error (engine/packages/engine/src/commands/profile.rs:57-72). A success status means step 2 completed. If the build target is not Linux or macOS on x86-64 or AArch64, the service logs a warning when Pyroscope is configured, then parks (engine/packages/profiling/src/lib.rs:3-30). If the agent fails to start, the service logs the error and stays ready for a later message.

7.3 config

config show prints the configuration that the CLI process loaded, with Rust Debug formatting (engine/packages/engine/src/commands/config.rs:145-147). It reads the files and environment variables of the CLI process. It does not contact an engine process. It does not show a dynamic override that a running engine applied in memory. The output can therefore differ from the values that the engine uses. Secret redacts its value in Debug, but ordinary strings such as server URLs are printed as written (engine/packages/config/src/secret.rs:28-35). Treat the output as sensitive.

config update changes a dynamic limit at runtime. It does not call the engine API. The command first calls apply_dynamic on its own configuration, so an invalid value fails in the CLI process (engine/packages/engine/src/commands/config.rs:333-337). It then publishes a SetDynamicConfigMessage on rivet.config.dynamic, with PublishOpts::broadcast() (engine/packages/engine/src/commands/config.rs:339-345). The CLI exits after the publish, so its local change has no lasting effect. A running engine applies the message only when its dynamic_config service receives it.

The driver rule in section 5 applies here. With the default memory driver, the separate CLI process publishes to a map that no engine process reads. The command prints "Updated" because the publish succeeded. A cluster that accepts this command from a separate process needs the NATS driver.

The variants cover every field in DynamicConfigUpdate (engine/packages/config/src/dynamic.rs:12-142). Section 12.2 maps each command name to its configuration key. An omitted value sends null and reverts the key to the value in the configuration file. A value sends an explicit override.

It then waits until last_emergency_receipt carries the same identifier (engine/packages/engine/src/commands/auth.rs:86-99). That receipt is the proof that the emergency change committed. A timeout is not proof that the change failed.

rotate stages a pending key. It does not replace the active signer at once. The pending key has an activate_after_ts that is at least the current time plus auth.jwt.key_publish_lead (engine/packages/auth-jwt/src/planner.rs:142-196). The planner requires the publish lead to be positive and shorter than the rotation interval (engine/packages/auth-jwt/src/planner.rs:26-28). The default lead is 10 minutes, and the default rotation interval is 7 days (engine/packages/config/src/config/auth.rs:10-21). The rotation workflow wakes at next_wake_ts. While a pending key exists, that value is the pending activate_after_ts (engine/packages/auth-jwt/src/planner.rs:458-468). The workflow stores it as a lifecycle wake (engine/packages/auth-jwt/src/workflows/key_rotation/mod.rs:45-56). At the wake time, reconcile_pending_activation calls activate_pending when activate_after_ts <= now (engine/packages/auth-jwt/src/workflows/key_rotation/reconcile.rs:443-475). The transition makes the pending key active and moves the old key to the retiring list (engine/packages/auth-jwt/src/planner.rs:158-199). The keys command shows both the pending key and the active key, so an operator can see the wait. A retiring key stays valid until its verify_until_ts, which is the maximum token expiry plus clock skew (engine/packages/auth-jwt/src/planner.rs:174-182). The default access token lifetime is 1 hour, and the maximum is 24 hours (engine/packages/config/src/config/auth.rs:10-12, engine/packages/config/src/config/auth.rs:100-106). The fail-closed signing deadline is 14 days (engine/packages/config/src/config/auth.rs:15, engine/packages/config/src/config/auth.rs:119-124). The deadline starts at activation. activate_pending sets sign_until_ts to the activation time plus key_max_signing_lifetime (engine/packages/auth-jwt/src/planner.rs:186-191). A retry or a forced rotation never extends it (engine/packages/auth-jwt/src/planner.rs:189). The retiring key has a separate deadline. Its verify_until_ts is its maximum token expiry plus one clock skew (engine/packages/auth-jwt/src/planner.rs:174-182). That value is a verification deadline, not a signing deadline. At now >= sign_until_ts, active_signer returns an error and issuance fails (engine/packages/auth-jwt/src/key_ring_cache/signing.rs:67-79). Existing tokens keep working until their own expiry. Rotate the key to restore issuance.

keys prints these fields. The first group is the key ring state: generation, JWT enabled, issuance enabled, and the desired issuer. The second group is the issuer state: configured and active issuer generation, active issuer, and issuer configuration valid. The third group is the retiring issuers with an accept-until time. The fourth group is the leader datacenter and the desired datacenter, plus the leader epoch and configuration generation. The fifth group is the active key identifier, the normal rotation due time, and the hard signing deadline. The sixth group is the pending key identifier and activation time. The last group is the retiring key identifiers with a verify through time (engine/packages/engine/src/commands/auth.rs:155-209).

The desired issuer comes from the configuration through derive_issuer. The active issuer and its generation come from the key-ring state. The issuer configuration valid field is a computed boolean. It compares the two issuer values, the two generations, the accepted issuer list, and the leader configuration generation (engine/packages/auth-jwt/src/ops/rotation/status.rs:53-99). The leader epoch and configuration generation are the ring's record of the last leader change (engine/packages/auth-jwt/src/ops/rotation/status.rs:61-64). A false issuer configuration valid means the values disagree; it does not mean that signing is off.

# Inspect the key ring first.
rivet-engine auth jwt keys

# Stage a normal rotation from generation 7.
rivet-engine auth jwt rotate --expected-generation 7 --yes

# Emergency revocation of two key identifiers.
rivet-engine auth jwt revoke-key --kid key-a --kid key-b --expected-generation 8 --yes

7.9 udb

udb opens a UniversalDB (UDB) inspector. -q or --query runs one command and exits. Without -q, the command starts a read-eval-print loop (REPL) with history stored in /tmp/rivet-udb-cli-history (engine/packages/engine/src/commands/udb/mod.rs:12-54). The REPL commands are cd, get, ls, size, move or mv, set, clear, exit, and oneoff (engine/packages/engine/src/commands/udb/cli.rs:20-129). cd keeps the previous key, and cd - swaps to it (engine/packages/engine/src/commands/udb/cli.rs:163-171). get -t sets a type hint, and -t raw prints the bytes. ls takes -d/--max-depth with a default of 1, and -u/--hide-subspaces hides subspace keys past that depth. It takes -s/--style with the values list or tree and a default of tree. The -l/--limit flag sets the maximum entry count, and -o/--open lists entries after the current key as well as under it. --prefer-bytes prints strings as bytes (engine/packages/engine/src/commands/udb/cli.rs:41-68, engine/packages/engine/src/util/udb.rs:11-15). A subspace is a key prefix (engine/packages/universaldb/src/utils/subspace.rs:11-23). At the depth cutoff, ls can show one entry for the whole prefix instead of each child key. -u/--hide-subspaces removes those entries. The oneoff command has two subcommands. reapply-lost-serverless scans the old serverless desired-slot keys and adds their slot counts into the current Pegboard subspace. -f/--flip negates the count, and --dry-run only logs the entries (engine/packages/engine/src/commands/udb/cli.rs:583-639). repair-epoxy-changelog scans one replica's changelog subspace. It tries each entry as the version 2 schema with a byte-identical roundtrip, and it applies the entries that pass through the normal catchup path. --dry-run counts and logs the entries without applying them (engine/packages/engine/src/commands/udb/cli.rs:140-152, engine/packages/engine/src/commands/udb/cli.rs:973-984).

The key syntax is a path of typed segments. The grammar is at the top of engine/packages/engine/src/commands/udb/key_parser.rs:1-18. A leading / is optional. A segment can be u64:, i64:, f64:, uuid:, id:, str:, nested:, bytes: or b: followed by a value. A nested value uses [...]. The path separator is /, .. moves to the parent, and . keeps the current segment. A \ escapes the next character (engine/packages/engine/src/commands/udb/key_parser.rs:6-18). The parser also accepts a symbolic constant name in place of a numeric value (engine/packages/engine/src/commands/udb/key_parser.rs:245-259). The names are lowercase: runner, data, namespace, envoy, and last_ping_ts (engine/packages/universaldb/src/utils/keys.rs:32-143). An uppercase name is not a constant and parses as a string.

# List the top level of the UDB key space with a depth of two.

# Read one typed key and print its value.
rivet-engine udb -q "get /rivet/example/u64:42"

8.1 depot doctor: is this database healthy?

doctor diagnoses one Depot-backed SQLite database. The operator must give exactly one selector. The choices are --bucket-id with --database-id, --actor-id, or --database-branch-id. The command rejects zero selectors and two selectors (engine/packages/engine/src/commands/depot.rs:222-300).

The source exposes four skip flags, so their checks run by default. The flags are --skip-full-integrity-check, --skip-first-bad-txid, --skip-page-provenance, and --skip-resolver-compare. The operator can limit the transaction identifier range with --min-txid and --max-txid. The command also accepts --artifact-dir for diagnostic artifacts (engine/packages/engine/src/commands/depot.rs:222-260). Each skip flag is recorded as a boolean in analysis_scope: full_integrity_check, first_bad_txid_search, page_provenance_collection, and depot_resolver_comparison (engine/packages/depot/src/doctor.rs:2989-3014).

The output is one JSON document. The top-level fields are verdict, generated_at_ms, duration_ms, selected_head_txid, selected_db_size_pages, first_bad_txid, previous_good_txid, identity, analysis_scope, facts, analyses, and artifacts (engine/packages/depot/src/doctor.rs:138-150).

The top-level verdict field is an object, not a string. It has five fields: verdict, corruption_class, unsupported_reason, reason, and message (engine/packages/depot/src/doctor.rs:128-135). The verdict value is healthy, corrupt, inconclusive, or unsupported. The corruption_class value is none, delta_history, depot_reconstruction, hot_compaction_state, sqlite_structure, unknown, or unsupported (engine/packages/depot/src/doctor.rs:107-126). A script that reads report.verdict as a string will fail.

The verdict certifies only the checks that ran. A skipped check leaves a false in analysis_scope, so a healthy verdict does not cover that check (engine/packages/depot/src/doctor.rs:3004-3007). Read analysis_scope together with the verdict when the operator skipped a check.

The exit code is part of the interface: 0 healthy, 1 corrupt, 2 inconclusive, 4 unsupported (engine/packages/depot/src/doctor.rs:423-430). Exit code 3 is not used. A script can gate a repair on the code without parsing the JSON.

8.2 depot execute: what does this SQL return?

execute opens one Actor database or one bucket database and runs one SQL statement. The selector is --actor-id or the pair --bucket-id and --database-id. The query comes from -q or --query (engine/packages/engine/src/commands/depot.rs:319-345).

The command returns JSON with two fields. columns is the column name array. rows is an array of row arrays. A null becomes JSON null. An integer or float becomes a JSON number. Text becomes a JSON string. A blob becomes an object with type "blob" and a base64 string (engine/packages/engine/src/commands/depot.rs:407-429).

execute is not a read-only command. It opens the database with SQLITE_OPEN_READWRITE | SQLITE_OPEN_CREATE (engine/packages/depot-client/src/worker.rs:532-537). It runs one statement through exec and then closes the database (engine/packages/engine/src/commands/depot.rs:346-361). The source sets no explicit transaction and no statement timeout. A write statement can commit.

Four rules make the command safe:

  1. A read statement still opens the database with

SQLITE_OPEN_READWRITE | SQLITE_OPEN_CREATE (engine/packages/depot-client/src/worker.rs:532-537). A mistyped selector can create an empty database. Run reads only where an Actor may write.

  1. A write statement needs an idle database. The Depot contract permits one

writer per database. Pegboard exclusivity is the release fence: the scheduler gives one runner the database, a ping keeps that grant, and the lost timeout releases it (engine/packages/depot/CLAUDE.md:11, engine/packages/depot/CLAUDE.md:23-25). execute takes no such lock.

  1. execute commits through the embedded VFS. The embedded VFS is the SQLite

virtual file system in depot-client that reads and writes pages through UDB instead of a local file (engine/packages/depot-client/src/vfs.rs:117-140). That VFS sets expected_head_txid from the current state.head_txid (engine/packages/depot-client/src/vfs.rs:2163-2166, engine/packages/depot-client/src/vfs.rs:2292-2295). state.head_txid is the commit head that the open connection last saw. A concurrent commit that moves the head makes this write fail with HeadFenceMismatch (engine/packages/depot/src/conveyer/types/pages.rs:105-109). The fence is a commit-time check, not a lock. Run the write while the database is idle.

  1. Treat DROP, VACUUM, and writes to sqlite_schema as destructive. The

command has no dry-run and no confirmation flag.

A real invocation and its output shape:

rivet-engine depot execute --actor-id <actor-id> -q "select 1 as answer"

{
  "columns": ["answer"],
  "rows": [[1]]
}

8.3 The other Depot commands

export --output writes one database to a file. import --input reads it back. Import works only with the local file-system backend, which uses RocksDB. The check is verify_local_import_config (engine/packages/engine/src/commands/depot.rs:133-199). lookup-actor-namespaces prints {actor_id, namespace_id} objects for the identifiers that the operator gives (engine/packages/engine/src/commands/depot.rs:49-70).

scan-corruption partial-hot-shard answers one question: does a current database branch select a hot shard version that covers fewer pages than the branch needs? A hot shard version is one selected shard image at a given txid. A readable version covers every page in its range at that txid (engine/packages/depot/src/recovery.rs:509-516). The source calls the defect "the no-cold multi-slice compaction bug" but does not define the mechanism (engine/packages/depot/src/recovery.rs:243-247). The scan checks the observable result. It looks for a selected image that omits a page whose index owner is at or below the image txid (engine/packages/depot/src/recovery.rs:509-516). The scan reads UDB snapshots only, with Snapshot isolation (engine/packages/depot/src/recovery.rs:12, engine/packages/depot/src/recovery.rs:429). Snapshot is the read isolation level, and the scan performs no writes.

Some comments in the Depot package still say FoundationDB (FDB), but the UDB drivers in this commit are PostgreSQL and RocksDB (section 8). The options and defaults are --transaction-max-ms 2000, --transaction-max-mb 4, --concurrency 4, and an optional --database-limit for a smoke test (engine/packages/engine/src/commands/depot.rs:93-107).

The scan output is one JSON report. The top-level fields are method, read_only, scope, pointer_rows_scanned, ignored_pointer_rows, current_databases, unique_current_branches, prefilter, healthy_candidates, affected, inconclusive, and io (engine/packages/depot/src/recovery.rs:132-146). prefilter has counts for missing_head, never_hot_compacted, cold_history, and candidates (engine/packages/depot/src/recovery.rs:124-130). Each affected entry has the branch, the database identities, the head txid, the page count, and the suspect shards. Each suspect shard lists the shard identifier, the selected version, the selected and expected page counts, and the missing page numbers (engine/packages/depot/src/recovery.rs:98-115). inconclusive lists branches that the scan could not decide (engine/packages/depot/src/recovery.rs:117-122).

The command prints the report and returns success even when affected is not empty (engine/packages/engine/src/commands/depot.rs:117-129). It has no distinct "corrupt" exit code. Read the affected array, not the exit code. Use the scan after a suspected bad compaction, not on a schedule.

repair vacuum rebuilds a database when its vacuum preflight accepts it. It is the only repair strategy (engine/packages/engine/src/commands/depot.rs:202-220). The preflight rejects a database that already passes integrity_check. It rejects a database with unreadable tables unless --allow-unreadable-tables is set (engine/packages/engine/src/commands/depot_vacuum.rs:252-262). It then runs VACUUM INTO on a throwaway copy. It rejects the copy if the copy is still corrupt, has a foreign key violation, has a different schema, or loses rows (engine/packages/engine/src/commands/depot_vacuum.rs:285-398). repair vacuum takes no Pegboard Actor lock. It opens the same embedded VFS handle that an Actor uses and commits through the same path (engine/packages/engine/src/commands/depot_vacuum.rs:102-107). The VFS sets expected_head_txid, so a concurrent commit fails the repair instead of overwriting it (engine/packages/depot-client/src/vfs.rs:2163-2166). Run the repair while the database is idle, because the fence is a commit-time check. A real repair requires an absolute --backup-dir. The command preflights every target first, writes and verifies one pre-repair export per database, applies the repair, and verifies the result (engine/packages/engine/src/commands/depot.rs:466-625). --dry-run proves the rebuild on a throwaway copy and needs no backup directory. --candidate-dir keeps the rebuilt candidate. Positional values are database identifiers with --bucket-id, and actor identifiers otherwise (engine/packages/engine/src/commands/depot.rs:444-464).

The repair output is a JSON array. Each element has database, strategy, dry_run, and backup, and the preflight fields before_integrity, before_row_counts, unreadable_tables, applicable, rejection_reason, candidate_integrity, candidate_row_counts, foreign_key_violations, and recovered_rows (engine/packages/engine/src/commands/depot_vacuum.rs:444-455). A non-applicable target stays unchanged. The command exits 0 on success and nonzero on an error. It has no separate code for "repaired" and "not applicable". Read the applicable field, and run depot doctor again after the repair.

Use this order: doctor, then scan-corruption when the verdict names a hot compaction defect, then repair vacuum --dry-run, then the real repair with a backup directory. Do not repair a database that doctor calls healthy.

8.5 UDB queries

The UDB inspector reads the same key space that the engine writes. The paths use typed segments, so a key can be addressed without a hand-written tuple encoder. The REPL keeps a current key and a previous key. cd .. moves up one segment. get reads one key. ls lists keys under a prefix. size estimates or scans the subspace size. move renames a key or subtree. set writes a value. clear deletes a key or range and asks for confirmation unless --yes is present. exit leaves the loop.

Every read and write runs in a transaction with a five-second timeout (engine/packages/engine/src/commands/udb/cli.rs:170-190). A command that exceeds the timeout returns an error instead of holding the REPL.

get prints a typed value with the caller's type hint, or an inferred type. -t raw prints raw bytes. ls prints a tree by default; --style selects another layout (engine/packages/engine/src/commands/udb/cli.rs:41-70).

8.7 Epoxy debug commands

The Epoxy commands call the peer API. The default endpoint is the local datacenter peer_url from the topology configuration. A key argument uses UDB tuple path syntax. The command tuple-packs the path and Base64-encodes the bytes (engine/packages/engine/src/commands/epoxy.rs:313-340). With --base64, the argument must already be Base64. The encoded string is the last path segment. It is not a plain URL-encoded tuple. The encoding is standard Base64 with padding (base64::engine::general_purpose::STANDARD), not the unpadded Base64URL of the Depot raw routes (section 8.4). get-local and get-optimistic also take -t/--type for the printed value (engine/packages/engine/src/commands/epoxy.rs:60-87).

Epoxy stores per-key Fast Paxos state. Fast Paxos is the consensus variant in which one round trip to a quorum can commit a proposal. The instance log is an ordered record that a classic Paxos replica keeps, one entry for each consensus instance. Epoxy does not keep one; it keeps only the state for each key (engine/packages/api-peer/src/internal.rs:352-355). A proposal carries a ballot. The fast path commits when a fresh ballot reaches the fast quorum. The slow path runs a prepare phase when the key needs a prepare, or when a mutable key already has a committed value. The prepare phase collects the highest accepted ballot from the quorum. A prepare can retry and bump the ballot (engine/packages/epoxy/src/ops/propose.rs:360-518). A committed value has a version and a mutable flag. The changelog keeps the recent committed values for the key (engine/packages/api-peer/src/internal.rs:301-315). A replica is active, learning, or joining. The coordinator is the replica that sends the cluster configuration (engine/packages/api-peer/src/internal.rs:220-286). Document 02 Control plane architecture gives the full protocol.

11.1 A slow Actor

Start with the request path. guard_route_total with the router label shows whether Guard received the request and which routing module it selected. The label has no outcome value.

api_request_duration and api_request_errors_total carry router, method, path, status, and error (engine/packages/api-builder/src/metrics.rs:19-32). The error label is empty on success and is group.code on failure (engine/packages/api-builder/src/middleware.rs:192-206). These metrics come from the api-builder middleware. They cover the api-peer and api-public routers only. Guard's Actor gateway does not use that middleware, so Actor traffic has stage durations and no end-to-end duration metric.

guard_route_pegboard_ready_wait_duration is the time Guard waited for a sleeping Actor to become ready. It has the namespace_id, pool_name, was_sleeping, wake_retries_bucket, and outcome labels (engine/packages/guard/src/metrics.rs:97-106). was_sleeping is true or false. wake_retries_bucket is 0, 1, 2, or 3+. outcome is ready, rewake_not_found, stopped, failed, destroyed, pool_error, or timeout (engine/packages/guard/src/routing/pegboard_gateway/mod.rs:588-605, engine/packages/guard/src/routing/pegboard_gateway/mod.rs:620-709). The was_sleeping label separates a cold start from a slow warm request.

Then check the runtime. tokio_worker_busy_duration_total is a counter of seconds each worker spent polling. It has a worker label, and the counter is per worker. Its rate against wall-clock time is that worker's busy fraction (engine/packages/runtime/src/metrics.rs:52-57). The rate needs no division by the worker count. max by (pod, worker) selects the busiest worker, as step G does. A saturated runtime has a busy fraction near 1. A runtime whose workers are parked has a low fraction even when requests are slow, which points at a dependency. The tokio_worker_local_queue_depth and tokio_worker_overflow_count metrics show whether one worker is overloaded.

gasoline_cpu_usage is a histogram of CPU cores used, not a percentage (engine/packages/gasoline/src/metrics.rs:288-293). A sample value of 2.0 means two cores. The buckets stop at 16. gasoline_cpu_usage_smoothed applies an exponential moving average to the same value (engine/packages/gasoline/src/metrics.rs:294-299). The smoothing constant is worker_load_shedding_beta, and the default is 0.95 (engine/packages/config/src/config/runtime.rs:128-130).

The workflow pull loop divides the smoothed value by the core limit. The core limit comes from worker_cpu_max in millicores, or from the cgroup quota, or from the CPU count (engine/packages/gasoline/src/db/kv/system.rs:57-71). The code converts worker_cpu_max to cores by division by 1000 (engine/packages/gasoline/src/db/kv/system.rs:56-60). A cgroup quota becomes a core count by quota divided by period (engine/packages/gasoline/src/db/kv/system.rs:61-63). The smoothed value is already in cores, as the 1 = 1 core comment states (engine/packages/gasoline/src/db/kv/system.rs:73-74). The result is a ratio from 0 to 1 (engine/packages/gasoline/src/db/kv/system.rs:126-127). The loop maps that ratio through worker_load_shedding_curve, and the default curve is [(700, 1000), (900, 50)] (engine/packages/config/src/config/runtime.rs:123-126). Both curve coordinates are permille. The code multiplies the ratio by 1000 before the interpolation, and it divides the result by 1000 before it records the histogram (engine/packages/gasoline/src/db/kv/mod.rs:1194-1210). Below a ratio of 0.7 the worker pulls 100 percent of eligible workflows. At a ratio of 0.9 the worker pulls 5 percent. The service records each pull ratio in the gasoline_load_shedding_ratio histogram (engine/packages/gasoline/src/metrics.rs:300-305, engine/packages/gasoline/src/db/kv/mod.rs:1194-1210). The ratio decides which workflows the pull keeps (engine/packages/gasoline/src/db/kv/mod.rs:1437-1438). A sample below 1.0 is throttling, not a fault. The worker drops work on purpose to protect the process. Use the average expression in step H of the runbook to read the current fraction.

Then check the Actor start. pegboard_actor_start_duration has namespace_id, pool_name, and kind labels (engine/packages/pegboard/src/metrics.rs:32-38). pegboard_actor_pending_allocation shows the queue of Actors that wait for a runner (engine/packages/pegboard/src/metrics.rs:4-10). A pending count that grows points at capacity or at a runner that cannot register. The companion pegboard_actor_active gauge has no writer in this commit, so use the pending count and the runner registration state, not a pending-to-active ratio (section 11.5).

11.2 A stuck workflow

gasoline_workflow_dead counts dead workflows by name (engine/packages/gasoline/src/metrics.rs:86-91). A rising value is the first signal. gasoline_workflow_errors counts workflow errors, and gasoline_signal_pending counts signals that wait for delivery (engine/packages/gasoline/src/metrics.rs:98-103, engine/packages/gasoline/src/metrics.rs:175-180). A high pending signal count with no activity points at a workflow that is not being leased. gasoline_workflow_concurrency_quota_usage shows whether the cluster-wide concurrency limit is the cause (engine/packages/gasoline/src/metrics.rs:138-143). The value is a ratio from 0 to 1, even though the help text says percent (engine/packages/gasoline/src/db/kv/mod.rs:1542-1544).

Run wf dead with the workflow name and an error substring. Then run wf history to see the event graph. If the workflow died because of a known history defect, wf repair --dry-run prints the diagnosis and the repair that would apply. Do not run a repair without the dry run first. The source says to repair one workflow at a time and confirm that it is healthy before the next one (engine/packages/engine/src/commands/wf/mod.rs:92-96).

11.3 A full bucket or a full database

Three limits are in play. The per-database limit is sqlite.max_storage_bytes, and the default is 10 gibibytes (GiB) (engine/packages/config/src/config/sqlite.rs:207-210). A commit that would exceed it is refused with the quota_exceeded error (engine/packages/depot/src/conveyer/error.rs:61-69). The staged commit cap is MAX_COMMIT_DIRTY_PAGES, which is 32,768 dirty pages (engine/packages/depot-client-types/src/lib.rs:33). The single-shot cap is MAX_SINGLE_SHOT_COMMIT_DIRTY_PAGES, which is 320 dirty pages (engine/packages/depot/src/conveyer/constants.rs:186-188). The client chooses the path from the dirty page count. A commit of 320 pages or fewer takes the single-shot path. A larger commit is staged in segments (engine/packages/depot-client/src/vfs.rs:2631-2648). Both page caps return CommitTooLarge. Only the staged path increments the too_large label (engine/packages/depot/src/conveyer/commit/stage.rs:360-369). sqlite.unstable_disable_commit_size_cap disables only the single-shot check (engine/packages/depot/src/conveyer/commit/apply.rs:496-512). The staged check at engine/packages/depot/src/conveyer/commit/stage.rs:284-289 always applies.

The distance to the storage limit is not a metric in the files this document read. sqlite_conveyer_commit_rejected_total counts only staged too_large refusals (engine/packages/depot/src/conveyer/commit/stage.rs:360-369). It does not show a quota refusal or a single-shot refusal.

Compaction is off by default in this commit. sqlite.unstable_disable_compaction defaults to true (engine/packages/config/src/config/sqlite.rs:216-219). depot::registry registers the compaction workflows only when the key is false (engine/packages/depot/src/lib.rs:23-35). Until an operator sets the key to false and restarts, the compaction and cold-tier series below are absent.

When compaction is on, four workflows can register. Their registered names come from the function name, not the struct name (engine/packages/gasoline-macros/src/lib.rs:112). The names are depot_compaction_backfill, depot_db_hot_compactor3, depot_db_manager3, and depot_db_reclaimer3 (engine/packages/depot/src/lib.rs:28-33). No cold-compactor workflow registers. The runtime concurrency map names depot_db_manager3, depot_db_hot_compactor3, depot_db_cold_compactor3, and depot_db_reclaimer3 (engine/packages/config/src/config/runtime.rs:177-190). The cold name has no workflow. depot_compaction_backfill has no map entry, so no configured concurrency limit applies to it (engine/packages/gasoline/src/db/kv/mod.rs:1153-1163). The cold upload and delete helpers have no production caller. Only a test calls the upload helper (engine/packages/depot/src/metrics.rs:968-985, engine/packages/depot/tests/inline/metrics_compaction.rs:200-201). The delete helpers have no caller (engine/packages/depot/src/metrics.rs:987-1005). The cold upload, cold delete, and S3 series are therefore absent even with compaction on. Do not use them as bucket health signals.

sqlite_compaction_lag_txids is a histogram, not a gauge. Its tier label is hot or cold. Hot install writes a compacted shard image into the live SHARD rows (engine/packages/depot/src/metrics.rs:551-561). Cold publish would copy that image to the cold tier, and no cold publisher runs in this commit. The hot lag is the txid span that waits for hot install. The cold lag is the span that is hot-installed but not yet cold-published (engine/packages/depot/src/metrics.rs:632-638, engine/packages/depot/src/metrics.rs:1008-1018). The database manager records both values at refresh (engine/packages/depot/src/workflows/db_manager.rs:1055). A growing cold lag points at cold publication, not at the Actor.

sqlite_s3_request_failures_total is registered with node_id and op labels (engine/packages/depot/src/metrics.rs:173-178). No code increments it in this checkout, so the series is always absent. Do not use it as a health signal.

The write path also has throttles. udb_throttle_pending_bytes and udb_throttle_decisions_total with throttle, kind, and result labels show whether the engine is holding bytes because a budget is full (engine/packages/universaldb/src/metrics.rs:110-135). The throttle names are depot_compaction and depot_actor (engine/packages/config/src/config/sqlite.rs:8-16).

Run depot doctor --actor-id to separate a logical corruption from a storage limit. A healthy verdict with a quota refusal means the database is valid and the limit is the cause. A corrupt verdict points at the checks that the doctor ran.

Document 07 UniversalDB and buckets explains the key space and the throttles. The Depot commit path, compaction, and cold tier are implemented in engine/packages/depot/src/; the sibling document set does not yet include a Depot document.

11.4 A replica that is down

epoxy_replicas_total has a status label. The values are active, learning, and joining, and there is no healthy value (engine/packages/epoxy/src/metrics.rs:74-79, engine/packages/epoxy/src/metrics.rs:104-115). The gauge is a per-process view, so do not sum it across processes. epoxy_proposals_total with the result label has three values: committed, slow_path, and failed. There is no timeout value (engine/packages/epoxy/src/ops/propose.rs:510-515). epoxy_prepare_total, epoxy_prepare_retry_total, and epoxy_ballot_bump_total show recovery activity. A rising prepare count with a falling fast-path count points at contention or at a missing replica (engine/packages/epoxy/src/metrics.rs:20-48).

11.5 A runner or an envoy that will not register

Pegboard uses two kinds of host process. A runner is a process that registers with the engine over a WebSocket and hosts Actors. A Rivet envoy is a tunnel endpoint. It forwards Actor traffic to a runner that sits behind a network boundary. A Rivet envoy is not the Envoy proxy from the Cloud Native Computing Foundation. The names are unrelated.

pegboard_actor_pending_allocation grows while pegboard_actor_active stays flat. Both have the namespace_id and runner_name labels (engine/packages/pegboard/src/metrics.rs:4-16). The two gauges do not have the same scope. The pegboard_metrics_aggregator workflow is the only writer of the pending gauge. It resets the gauge and scans the whole pending subspace every 15 seconds (engine/packages/pegboard/src/workflows/metrics_aggregator.rs:10, engine/packages/pegboard/src/workflows/metrics_aggregator.rs:42-116). Bootstrap dispatches that workflow once with .unique(), so only the process that holds its lease reports values (engine/packages/bootstrap/src/lib.rs:124-131). The value is a cluster-wide snapshot, not a per-process count. A sum across pods repeats the same count and any stale copy. pegboard_actor_active has no writer in this commit. Its aggregation activity is commented out (engine/packages/pegboard/src/workflows/metrics_aggregator.rs:118-140), so the series is always absent. The pending count is the usable signal. Do not treat a missing active series as zero. pegboard_serverless_outbound_req_total and pegboard_serverless_outbound_req_active show the outbound serverless path (engine/packages/pegboard/src/metrics.rs:55-67). They count HTTP requests that the engine sends to a serverless runner for one Actor request, and the requests in flight (engine/packages/pegboard-outbound/src/lib.rs:275-293). This path starts after allocation. The metric does not count Actors that wait for a runner. For the envoy path, envoy_lb_no_envoy_available_total counts the allocations that found no envoy. envoy_lb_scan_depth and envoy_lb_scan_circuit_breaker_total show the load balancer's search (engine/packages/pegboard/src/metrics.rs:143-207).

The last-ping timestamp is a stored key. For a runner it is LastPingTsKey under (RUNNER, DATA, runner_id, LAST_PING_TS) (engine/packages/pegboard/src/keys/runner.rs:97-140). For an envoy it is LastPingTsKey under (NAMESPACE, ENVOY, DATA, namespace_id, envoy_key, LAST_PING_TS) (engine/packages/pegboard/src/keys/envoy.rs:663-720). The timestamp is part of the allocation index key, so a stale runner moves out of the eligible range (engine/packages/pegboard/src/ops/runner/update_alloc_idx.rs:71-148). The uppercase names in that tuple notation are Rust constants. The udb command uses their lowercase string forms.

The rivet-engine command set has no Pegboard subcommand (engine/packages/engine/src/commands/mod.rs:1-12). Use the udb command to read the stored ping keys. The udb key parser reads the lowercase symbolic constant runner as its integer tuple value, and the type hint id reads a Rivet identifier (engine/packages/engine/src/commands/udb/key_parser.rs:213-260). An uppercase name is not a constant. The value is Unix epoch milliseconds in an i64 (engine/packages/util/src/timestamp.rs:6-13).

rivet-engine udb -q "get runner/data/id:<runner_id>/last_ping_ts -t i64"

# Read the envoy last-ping timestamp in milliseconds.
rivet-engine udb -q "get namespace/envoy/data/id:<namespace_id>/str:<envoy_key>/last_ping_ts -t i64"

The thresholds and the ping timers explain the timing. A runner is eligible while its last ping is no older than pegboard.runner_eligible_threshold, which defaults to 10000 milliseconds (engine/packages/config/src/config/pegboard.rs:263-265). The allocation index uses that cutoff (engine/packages/pegboard/src/ops/runner/update_alloc_idx.rs:49). A liveness monitor marks a runner lost when its last ping is older than pegboard.runner_lost_threshold, which defaults to 15000 milliseconds (engine/packages/config/src/config/pegboard.rs:267-269, engine/packages/pegboard/src/workflows/runner2.rs:639-653). The runner sends a ping every pegboard.runner_update_ping_interval_ms, which defaults to 3000 milliseconds (engine/packages/config/src/config/pegboard.rs:362-363, engine/packages/pegboard-runner/src/ping_task.rs:21-29).

An envoy has four separate timing values. The ping task sends a ping every pegboard.envoy_update_ping_interval, which defaults to 3000 milliseconds, with a random jitter of 0 to 127 milliseconds (engine/packages/config/src/config/pegboard.rs:400-402, engine/packages/pegboard-envoy/src/ping_task.rs:20-34). Allocation uses pegboard.envoy_eligible_threshold, which defaults to 10000 milliseconds. An envoy with an older last ping receives no new allocation (engine/packages/config/src/config/pegboard.rs:404-406, engine/packages/pegboard/src/workflows/actor2/runtime.rs:212). The liveness monitor uses pegboard.envoy_lost_threshold, which defaults to 15000 milliseconds, to mark the envoy lost (engine/packages/config/src/config/pegboard.rs:378-380, engine/packages/pegboard/src/workflows/actor2/mod.rs:445-460). An operator who sees a runner or an envoy disappear compares now - last_ping with these values.

The dynamic update path covers 21 fields. The engine compares a dynamic update against the loaded value and applies a local override. 13. Limits, failure paths, and operational cautions

Several observability paths can themselves fail. This section collects them so that an operator does not confuse a broken signal with a broken system.

The metrics server exits the process on a bind failure (engine/packages/metrics-server/src/server.rs:17-25). A port conflict is therefore fatal, not a degraded mode. Reserve port 6430.

The peer API and the metrics server have no authentication layer, and both bind :: by default. Guard on port 6420 is the authenticated boundary. A network that exposes port 6421 or port 6430 to an untrusted client exposes the read and write routes in section 8.4 and the full metric registry. Bind the services to a loopback address, or put a proxy, a network policy, or both in front of them.

The OpenTelemetry exporter builds with unwrap() (engine/packages/metrics-server/src/providers.rs:92). The source adds no retry or dead-letter path, and it does not document a batch queue limit. An unreachable collector can drop spans after the queue fills. Test the collector path before an incident.

The Sentry path is opt-out, and the DSN is fixed. An air-gapped deployment must set telemetry.enabled to false. A firewall rule is a second control, not a substitute for the flag.

The log redirect is process-wide and daily. A filter change broadcasts to every engine process on the NATS network, so a trace session raises the level on every process that receives it. Reset the filter with rivet-engine tracing config -f "".

Compaction is off by default. sqlite.unstable_disable_compaction defaults to true, so no compaction workflow registers (engine/packages/config/src/config/sqlite.rs:216-219, engine/packages/depot/src/lib.rs:28-33). A dashboard that expects compaction or cold-tier series shows no data until an operator enables compaction and restarts. The S3 failure counter also has no writer, so an alert on rivet_sqlite_s3_request_failures_total never fires (engine/packages/depot/src/metrics.rs:173-178).

The profiler needs a configuration block. Without it, the peer API still returns success because it published the message. Confirm the profile in the Pyroscope UI. The inspector devtools URL carries the token in the query string, so do not copy it into a ticket or a chat.

The config update, tracing config, and profile enable commands report success after a message is published. config update and tracing config publish from the command-line process itself. profile enable sends an HTTP PUT, and the peer API handler publishes inside the engine process that receives the request (engine/packages/api-peer/src/internal.rs:45-75). The success result does not prove that a remote process applied the change. With the memory driver, the broadcast reaches only the publishing process (section 5). A separate command-line process therefore reports success and changes nothing.

The health route is liveness only. A cluster can return {"status":"ok"} while every durable commit fails. The source has no readiness state machine. The runbook in section 11 is an operator procedure, not a readiness probe in the binary.
