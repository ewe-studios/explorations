Durable streams and durable promises

This page is the shared index for three explorations. One explores Electric and its Durable Streams protocol. One explores Resonate and its durable promises. One explores TanStack DB, the reactive client store that consumes synced data. The page also answers the question that joins them: how does each system defer work, which one is better at what, and how can they work together.

The short answer

A durable stream is an ordered log. It stores bytes at offsets. A reader keeps an offset and asks for everything after it. The server does not know what the bytes mean. It does not know which work is waiting. It only knows that offset 100 is before offset 200.

A durable promise is a named record with a lifecycle. It stores a promise, a task, a state, and a deadline. The server knows what is pending. It knows who waits for whom. It can wake a worker when a dependency settles.

The two systems are therefore not competitors. They are two different answers to one question: where does the durable memory of a distributed program live?

Part 1: how Durable Streams works

The full detail is in the Electric exploration. The essential facts follow.

A stream is a URL-addressable, append-only sequence of bytes. The protocol defines seven stream operations:

OperationMethod and pathEffect
CreatePUT /{stream}Creates a stream, or returns the existing one when the configuration matches
AppendPOST /{stream}Adds bytes at the tail
ClosePOST /{stream} with Stream-Closed: trueMoves the stream to its terminal state
ReadGET /{stream}?offset=...Catch-up read, long-poll read, or Server-Sent Events (SSE) read
HeadHEAD /{stream}Returns metadata and the tail offset
DeleteDELETE /{stream}Deletes the stream, or soft-deletes a source that live forks still reference
ForkPUT /{stream} with Stream-Forked-FromCreates a stream that inherits the source prefix up to the fork offset

Source: durable-streams/PROTOCOL.md sections 5.1 to 5.8.

An offset is opaque, persistent, unique, and strictly increasing. Offsets also sort in lexicographic order, so a client can compare two offsets without understanding their structure. Two sentinel values exist: -1 means the start of the stream and now means the current tail.

Source: durable-streams/PROTOCOL.md:1184-1248.

Durable Streams adds two mechanisms that matter for this comparison.

Idempotent producers. An append can carry three headers: Producer-Id, Producer-Epoch, and Producer-Seq. The server keeps the last accepted sequence number for each producer in each epoch. A retry with the same tuple returns the previous result instead of writing a second copy. A new epoch is a new generation of the same producer. The first append in a new epoch must bootstrap the producer state.

Source: durable-streams/PROTOCOL.md:361-498.

Subscriptions. A subscription is a durable cursor over one or more streams. It lives under the reserved path /__ds/subscriptions/{id}. It has a type of webhook or pull-wake. It holds one accepted offset per linked stream. When a linked stream advances past its accepted offset, the subscription produces a wake with a wake_id and a generation. A worker claims the wake, processes the data, and acknowledges the new offset. The lease lasts from 1 second to 10 minutes and defaults to 30 seconds.

Source: durable-streams/PROTOCOL.md:818-1184.

The word "subscription" is important. The stream server does not run code. It does not know what a handler is. It only knows that a cursor moved and that a target must be told. The decision to run an agent, a tool, or a model call belongs to the application.

Electric's agents platform builds that application on top of the primitive. The agents-server creates one stream per entity at /{type}/{id}/main. The agents-runtime opens that stream during a wake, builds an idempotent producer named entity-${entityUrl}, materializes the stream into typed collections, and runs the handler.

Source: packages/agents-server/src/entity-manager.ts:636-858, packages/agents-runtime/src/process-wake.ts:434-558.

Part 2: how Resonate works

Resonate is a server for durable promises and durable functions. A promise is a record with an identifier, a state, a parameter, a value, tags, a deadline, and the times it was created and settled. The five promise states are pending, resolved, rejected, rejected_canceled, and rejected_timedout.

Source: spec/spec/01-protocol/types.lean:18-40.

A task is the executable half of the same object. It has a state, a version, a lease duration, a process identifier, a lease deadline, a retry deadline, and a list of promises that resumed it. Its five states are pending, acquired, suspended, halted, and fulfilled.

Source: spec/spec/01-protocol/types.lean:42-50.

A promise and its task share one row. They are one object with two faces. This is not a database detail. It is the design: every task the machine writes is written at a promise identifier, so a task without its promise cannot exist.

Source: spec/spec/02-abstract/state.lean:13-60.

Tags decide what a promise is for. The tag resonate:target makes a promise a task. The tag resonate:timer makes the deadline resolve the promise instead of rejecting it. resonate:scope and resonate:external decide whether a promise is awaitable. Lineage tags record the call tree.

Source: spec/spec/01-protocol/validation.lean (tag predicates), spec/spec/02-abstract/state.lean:96-120.

The protocol has 21 request kinds: six for promises, eleven for tasks, four for schedules. Each request has an envelope with kind, head, and data. Each response has a status code. The protocol version is 2026-04-01.

Source: spec/spec/01-protocol/types.lean:150-200, impl/server/core/crates/resonate-core/src/types.rs:100-140.

The server is built from plugins. A storage plugin answers protocol requests. A worker plugin delivers messages to worker processes. A gateway plugin accepts requests at an edge. The shipped binary registers six storage plugins, four worker plugins, and three gateway plugins.

Source: impl/server/core/src/main.rs:63-80.

Part 3: how each system defers

This is the heart of the comparison. Both systems defer. They defer in different places, and the difference decides which problems each one solves.

Durable Streams defers by position

A durable stream has no operation called "wait". It defers in three ways, and all three are positional.

1. A reader holds an offset. A catch-up read from offset 42 returns data up to the current tail and stops. A long-poll read from offset 42 waits until new data arrives or a timeout expires. An SSE read from offset 42 keeps the response open and pushes each new message. In every case the durable fact is the offset. The connection is not durable. The reader can disconnect, crash, or move to another machine, and resume from offset 42.

Source: durable-streams/PROTOCOL.md:574-818.

2. A subscription holds an acknowledged offset. A subscription is a cursor that survives the worker. When the worker processes data up to offset 99, it acknowledges 99. If the worker dies before the acknowledgement, the cursor stays at the old offset and the work is delivered again. The wake has a generation number. A late acknowledgement from an old generation receives 409 FENCED and cannot advance the cursor.

Source: durable-streams/PROTOCOL.md:1004-1184.

3. The application arms time outside the stream. A stream has no alarm. In Electric's agents platform, time is a PostgreSQL table named scheduled_tasks and a scheduler loop. A delayed send is a row with a run_at time. A cron schedule is a stream path that encodes an expression. A scheduler instance claims a row with a 30,000 millisecond lease. If it dies, reclaimStaleClaims returns the row to another instance.

Source: packages/agents-server/src/scheduler.ts:285,468-500, packages/agents-server/src/runtime.ts:328-419.

The consequence is simple. Durable Streams can tell you that something new exists. It cannot tell you when to act in the future. The application must build the clock.

Resonate defers by state

Resonate has an operation called task.suspend. It is a durable await.

The sequence has five steps.

  1. A worker acquires a task. The task moves from pending to acquired and its

version increases by one.

  1. The worker runs a function until the function waits on a promise that is not

settled.

  1. The worker sends task.suspend with the list of awaited promise identifiers.

The server checks that none of them is already settled. If one is settled, the server returns status 300 and the worker continues immediately. Otherwise the server registers the task as a callback on each awaited promise, clears the lease, and moves the task to suspended.

  1. When an awaited promise settles, an internal callback step removes the

callback and resumes the task. The task moves to pending with a retry deadline. A retry step then emits an execute message to the task's target.

  1. A worker acquires the task again. The version has increased. The worker

re-executes from the start of the function, but every completed context.run returns its stored value from the durable promise. No side effect runs twice.

Source: spec/spec/02-abstract/external.lean:271-307 for task.suspend, spec/spec/02-abstract/internal.lean:20-40 for processCallback and resumeOne, spec/spec/02-abstract/internal.lean:60-100 for the retry step.

Time is part of the server. Four kinds of deadline exist.

DeadlineWhat it doesDefault
Promise deadlineA pending promise past its deadline becomes resolved (timer) or rejected as timed outSet by the caller per promise
Lease deadlineAn acquired task whose lease expires returns to pendingTask Time to Live (TTL), default 15,000 milliseconds
Retry deadlineA pending task with no claim is offered againServer retry interval, 30,000 milliseconds at the Command-Line Interface (CLI)
Schedule deadlineA cron occurrence creates its promiseSet by the cron expression

Source: impl/server/core/src/serve.rs:150-175 for the CLI defaults, spec/spec/02-abstract/internal.lean:42-105 for the four timeout steps, spec/spec/02-abstract/state.lean:230-245 for the retry default of 5,000 milliseconds in the abstract machine.

Part 4: what is great in each

What is great in Durable Streams

The server is simple and therefore portable. The protocol is six operations over HTTP. The reference repository has clients in TypeScript, Python, Go, Rust, Java, Ruby, PHP, C#, Swift, and Elixir. A stream server can run in Node.js, in Caddy, on Cloudflare Workers, behind a proxy, or inside a test process.

Source: durable-streams/packages/ directory listing.

History is free and exact. Every byte remains. A late reader sees the same sequence as an early reader. Debugging is replay. Auditing is replay. A new projection is a new reader from offset -1.

Fan-out is cheap. One append serves every reader. The server does not track per-consumer state beyond a subscription cursor. A thousand readers cost one write and one thousand reads, and the reads do not change the data.

Forking is constant time. A fork inherits a prefix from a source stream without copying bytes. The headers Stream-Forked-From, Stream-Fork-Offset, and Stream-Fork-Sub-Offset define the branch point. A fork does not inherit producer state, so a writer on the fork starts a new generation.

Source: durable-streams/PROTOCOL.md:151-218.

Idempotency is at the transport. A producer does not need to know the application semantics of a message. It supplies a tuple and the server deduplicates retries.

What is great in Resonate

Waiting is a first-class state. A workflow can wait for a human approval for ten days. No process stays alive. The task is a suspended row and the server holds the callback list. When the approval settles the promise, the server re-offers the task.

Step results are exactly once. context.run stores its result in a durable promise. On recovery the SDK replays the function, but the call returns the stored result. The model call, the payment, or the email does not run twice.

The server owns time. Lease deadlines, retry deadlines, promise deadlines, and cron schedules are server state. The client does not need a timer service.

Version fencing is precise. Every task transition carries a version. A stale worker that lost its lease cannot settle the promise. The server returns 409. This is stronger than a lease alone, because it detects the stale writer at the moment of the write.

The behaviour is specified. The abstract machine is an executable Lean 4 definition. The catalogue has 92 properties. Thirty-one are proved outright. The trace checker takes a recorded run and asks whether the machine can account for it. A second checker uses Porcupine for linearizability.

Source: spec/README.md, spec/valid/README.md, spec/valid/porc/README.md.

The honest limits of each

Durable Streams cannot suspend work. A stream can tell a wake service that data arrived, but the wake service decides everything else. Electric's agents-server therefore contains a hand-built task system: claims, leases, retry deadlines, a scheduler, and idempotent producers. That is a durable execution engine written beside the stream.

Resonate cannot serve a transcript to many readers. A promise record keeps only its current state. It has no operation to read the sequence of past values. Its promise.search and task.search return 501 in the abstract machine. A dashboard that needs history must get it from somewhere else.

Aha: each system contains a partial implementation of the other. Electric's agents-server implements durable execution on top of a log: scheduled_tasks, consumer_claims, wake_registrations, and entityDispatchState are a task lifecycle. Resonate implements a delivery log on top of a record store: the outbox table holds execute and unblock messages, the retry deadline re-emits a message that was not delivered, and the transports deliver it. Each project needed the other's primitive and built a small version of it.

Source: packages/agents-server/src/db/schema.ts:1-400 for the Electric tables, spec/spec/02-abstract/state.lean:130-150 for the Resonate outbox.

Part 6: how both work together

The two systems fit at different layers. Put the stream in the data plane and the promise in the control plane.

flowchart TB subgraph CP["Control plane: Resonate"] RW["workflow function<br/>context.run / context.rpc"] PR["durable promise<br/>state + deadline"] TK["task<br/>lease + version"] RW --> PR PR --> TK end subgraph DP["Data plane: Durable Streams"] ES["entity stream<br/>append-only events"] SUB["subscription<br/>cursor + generation"] RD["readers<br/>UI, audit, replay"] ES --> SUB ES --> RD end TK -->|"execute message"| WK["worker"] WK -->|"append transcript"| ES SUB -->|"wake"| RW PR -->|"settle"| TK

Pattern 1: the stream is the workflow transcript

The durable function is the control flow. The stream is the record of what happened. Each context.run appends its input and output to the entity stream before it settles its promise. The promise gives exactly-once execution. The stream gives replay, audit, and a live view for the user interface.

The division is clean. Resonate answers "what runs next". The stream answers "what happened".

Pattern 2: the stream is the task transport

Resonate's transports are HTTP push, HTTP long-poll, Google Cloud Pub/Sub, and a bash worker. Each is a delivery channel. A Durable Streams pull-wake subscription is also a delivery channel, and it has two properties the others do not have: the consumer holds a durable offset, and the wake stream can be read again after a crash.

A custom worker plugin can watch a durable stream. The server writes an execute message to a wake stream. The worker reads from its last offset, claims the subscription, calls task.acquire, runs the function, and acknowledges the offset. If the worker dies, the offset does not advance and the wake is delivered again.

The loss is the direct call. The gain is replay. A worker that was offline for an hour can read every wake it missed, in order.

Pattern 3: Resonate replaces the hand-built timer and claim system

Electric's agents-server has a scheduler with a 30,000 millisecond claim expiry, a wake registry, consumer claims, and per-entity dispatch state. Resonate already provides all four: task leases, retry deadlines, promise deadlines, and schedules. A deployment can keep Durable Streams for event storage and move the "when does the handler run" decision to Resonate.

The mapping is direct.

Electric agents-server conceptResonate concept
scheduled_tasks row with run_atPromise deadline or cron schedule
Scheduler claim with 30,000 millisecond expiryTask lease with TTL and version
wake_registrations conditionTask suspended on an awaited promise
consumer_claimsTask acquired state
Idempotent cron producerOccurrence identifier from expand
Signal as a stream eventPromise settlement

Pattern 4: fork for speculation, promise for commitment

A durable stream fork gives a cheap branch of a conversation or a plan. A durable promise gives a single settlement point. Use the fork to run two alternative agent paths without copying history. Use one promise per path to record which path completed, and use a parent promise to join them.

A fork costs no bytes. A promise costs one row. The combination gives speculative execution with a durable decision.

Pattern 5: two idempotency layers

Durable Streams deduplicates an append by Producer-Id, Producer-Epoch, and Producer-Seq. Resonate deduplicates a task transition by task version. Use both.

The worker first acquires the task with a version. It runs the step. It appends the result with a producer tuple derived from the promise identifier and the step number. Then it fulfils the promise with the same version. A retry after a crash hits one of three states:

  1. The task was never acquired: acquire it now.
  2. The task was acquired but the append did not land: the producer sequence does

not match, so the append is safe to repeat.

  1. The append landed but the fulfil did not: the promise is still pending, so

the worker reads the stream, finds its own append, and fulfils without running the step again.

The result is end-to-end exactly-once effect, with the stream as the evidence.

Part 8: a combined reference architecture

flowchart LR U["User or agent"] -->|"invoke"| G["Resonate gateway"] G --> S["Resonate server"] S --> P["promise and task store"] S --> O["outbox"] O --> T["transport"] T --> W["worker"] W -->|"context.run"| S W -->|"append event"| D["Durable stream server"] D -->|"subscription wake"| T D -->|"SSE"| UI["User interface"] D -->|"replay"| AU["Audit and rebuild"] S -->|"settle on completion"| P

The rules of the architecture are:

  1. One owner per fact. The promise owns the decision. The stream owns the

record. No fact has two owners.

  1. The stream is append-only. It never mutates. A correction is a new event.
  2. The promise is mutable. It records only the current state. History comes

from the stream.

  1. The worker is stateless. Its durable position is the task version and the

stream offset. Both survive a crash.

  1. Time is server state. No process sleeps. A deadline is a row.
  2. Delivery is at least once. Duplicate delivery is safe because both

layers deduplicate.

Sync engines

Two documents answer how a shape stays current from a database change stream.

DocumentWhy read it
Electric, PostgreSQL, and PGliteThe logical replication slot, the filter index, per-shape evaluation, column projection, the shape log, and PGlite
SQLite, libSQL, and TursoWhy plain SQLite has no committed row-change stream, what libSQL and Turso expose, and the layer each source needs

The short answer: PostgreSQL sends row changes through a logical replication slot. Electric keeps an index of shape filters in memory, finds the candidate shapes, and evaluates each filter on the old row and the new row. It does not re-run the shape query. It projects the row to the selected columns and appends only the changed columns to the shape's log. The log is disk-backed, so memory holds the index and the current window, not the history.
