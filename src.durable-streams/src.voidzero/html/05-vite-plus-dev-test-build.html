05 — Development, test, and build commands

Vite+ does not implement a development server, a bundler, a test runner, a linter, or a formatter. It resolves the real tool for each command and starts that tool with the same Node.js runtime that runs the Command-Line Interface (CLI). The command path has two layers. A Node.js script handles a small set of global commands. Every other command crosses a Native API (NAPI) boundary into a Rust core. The Rust core calls back into TypeScript resolver functions. Each resolver returns a binary path and an environment map. The Rust core then starts node . This document follows that path for vp dev, vp build, vp check, vp test, vp fmt, vp lint, vp pack, and the vpx script runner. It also covers vp preview and the project setup commands vp create, vp migrate, vp config, vp hooks, and vp staged, together with the configuration surface that these commands read.

The name vite-plus has three referents in this file. It names the repository directory at /Users/darkvoid/GitSources/src.voidzero/vite-plus. It names the published package vite-plus. It also appears in the names of the core package and the internal crates. The command itself is vp. A path that starts with vite-plus/ is relative to /Users/darkvoid/GitSources/src.voidzero.

The block above stops after block_on returns, and it is still inside the std::thread::spawn closure (vite-plus/packages/cli/binding/src/lib.rs:224-256). The closure runs on a new native thread. BoxedResolverFn is not Send, so the code creates the resolvers inside that thread (lib.rs:225). Send is the Rust trait that permits a value to move to another thread. The Rust core never guesses a tool path. It asks TypeScript for the path. The anchor of that resolution depends on the resolver. For Vite, Vitest, and the core package, Node.js resolves from the CLI installation (vite-plus/packages/cli/src/resolve-core.ts:60-75). resolveBundled also tries import.meta.dirname before process.cwd(), so the bundled Vitest wins over a project copy (vite-plus/packages/cli/src/utils/constants.ts:89-93). For Oxlint and Oxfmt, the resolve helper tries process.cwd() before import.meta.dirname, so those two tools are project-first (vite-plus/packages/cli/src/utils/constants.ts:69-73). SubcommandResolver::resolve at vite-plus/packages/cli/binding/src/cli/resolver.rs:72-77 maps each subcommand to one resolver. The resolved subcommand has four parts: a program, arguments, a cache configuration, and environment values (vite-plus/packages/cli/binding/src/cli/types.rs:185-191). The program is always cli_options.node_exec_path, the Node.js executable that started vp. Therefore the started process is always node .... vp_command::resolve_bin applies the PATH rules to that program path, including PATHEXT on Windows (vite-plus/crates/vp_command/src/lib.rs:57-72).

2.1 resolve-vite.ts

resolveViteRoot uses cac to find the positional root argument. It registers the Vite boolean options first, so cac does not consume the root as an option value (vite-plus/packages/cli/src/resolve-vite.ts:10-31). The vite function then resolves the core package from that root and constructs the path to the bundled Vite CLI.

// vite-plus/packages/cli/src/resolve-vite.ts:33-53
/** Resolve the bundled CLI for dev, build, and preview from the selected project root. */
export async function vite(
  err: Error | null,
  context: JsCommandContext,
): Promise<JsCommandResolvedResult> {
  if (err) {
    throw err;
  }
  // Start through Vite's bin script, as `vite` does; see packages/core/BUNDLING.md.
  const viteDistDir = dirname(dirname(resolveCore('', resolveViteRoot(context))));
  const binPath = join(viteDistDir, 'bin', 'vite.js');
  if (!existsSync(binPath)) {
    throw new Error(`Could not find the bundled Vite CLI at ${binPath}. Run \`vp install\`.`);
  }

  const envs: Record<string, string> = { ...DEFAULT_ENVS };
  if (process.env.DEBUG_DISABLE_SOURCE_MAP) {
    envs.DEBUG_DISABLE_SOURCE_MAP = process.env.DEBUG_DISABLE_SOURCE_MAP;
  }
  return { binPath, envs };
}

The JavaScript function has two parameters. The first is an error channel. The second is a context object with cwd and args. create_resolver builds that context and invokes the function through call_async (vite-plus/packages/cli/binding/src/lib.rs:127-149). The err parameter is therefore always null on a normal call. ThreadsafeFunction is the NAPI handle that queues a call onto the Node.js event loop. call_async returns a future for the JavaScript Promise. Rust awaits that future and then awaits the promise value (vite-plus/packages/cli/binding/src/lib.rs:139-147). A resolver can therefore return a Promise and still appear synchronous to the Rust caller.

resolveCore('', root) returns the main entry file of the core package, for example dist/vite/node/index.js. Two dirname calls move from node/index.js to dist/vite. The function then adds bin/vite.js. The comment at line 41 states the reason: Vite must start through its bin script, as the vite command does. vite-plus/packages/core/BUNDLING.md explains that the bin script is copied and its CLI import is pointed at ../node/cli.js.

DEFAULT_ENVS is defined at vite-plus/packages/cli/src/utils/constants.ts:107-113. It provides three values: JS_RUNTIME_VERSION from process.versions.node, JS_RUNTIME_NAME from process.release.name, and NODE_PACKAGE_MANAGER=vite-plus. JS_RUNTIME_NAME is usually node. JS_RUNTIME_VERSION is the exact version string. The comment states the purpose: telemetry and compatibility checks in Oxfmt (vite-plus/packages/cli/src/utils/constants.ts:107-113). The last value tells the tool that Vite+ is the package manager. The Vite, Vitest, and pack resolvers copy these values into their child environment (vite-plus/packages/cli/src/resolve-vite.ts:47-52, vite-plus/packages/cli/src/resolve-test.ts:50-62, vite-plus/packages/cli/src/resolve-pack.ts:16-19).

DEBUG_DISABLE_SOURCE_MAP is a pass-through variable. When the parent process sets it, the resolver copies the value into the child environment (vite-plus/packages/cli/src/resolve-vite.ts:48-52, vite-plus/packages/cli/src/resolve-test.ts:52-60). The source does not define what the child does with the value.

2.2 resolve-vite-config.ts

This file is not a tool resolver for a child process. It loads the user configuration inside the CLI process so that Vite+ can read the lint, fmt, check, run, staged, and pack blocks. resolveViteConfig imports the public resolveConfig from ./index.js and calls it with the build command (vite-plus/packages/cli/src/resolve-vite-config.ts:58-76). ./index.js re-exports everything from vite (vite-plus/packages/cli/src/index.ts:9). Therefore resolveConfig is Vite's own configuration resolver, not a Vite+ copy. withConfigMetadataResolution is the Vite+ wrapper that sets the metadata marker (vite-plus/packages/cli/src/define-config.ts:1038-1059).

// vite-plus/packages/cli/src/resolve-vite-config.ts:58-76
export async function resolveViteConfig(cwd: string, options?: ResolveViteConfigOptions) {
  const { resolveConfig } = await import('./index.js');

  // This loads the config purely to read a non-plugin block (lint/fmt/pack/run/
  // staged/create…), so skip the user's plugin factory while it evaluates.
  return withConfigMetadataResolution(async () => {
    if (options?.traverseUp && !hasViteConfig(cwd)) {
      const workspaceRoot = findMonorepoRoot(cwd);
      if (workspaceRoot) {
        const configFile = findViteConfigUp(path.dirname(cwd), workspaceRoot);
        if (configFile) {
          return resolveConfig({ root: cwd, configFile }, 'build');
        }
      }
    }

    return resolveConfig({ root: cwd }, 'build');
  });
}

The traverseUp option is used by vp pack so that a package directory can use the root configuration (vite-plus/packages/cli/src/pack-bin.ts:148-152). resolveUniversalViteConfig serializes a subset of the resolved configuration to JavaScript Object Notation (JSON) at vite-plus/packages/cli/src/resolve-vite-config.ts:78-97. "Universal" means that one filtered result serves every command that needs a configuration block. The function reads the full Vite configuration and then projects six fields into JSON. It does not return the full Vite configuration. It includes configFile, lint, fmt, check, run, and staged. The JSON string crosses the NAPI boundary and becomes ResolvedUniversalViteConfig in Rust (vite-plus/packages/cli/binding/src/cli/resolver.rs:54-69).

resolveBundled prefers the copy inside the CLI package over the copy in the project (vite-plus/packages/cli/src/utils/constants.ts:89-93). The comment at vite-plus/packages/cli/src/utils/constants.ts:75-88 gives the reason. The vite-plus/test shims re-export from vitest. If vp test started a different physical copy of Vitest, the runner and the imported vi, expect, and runner internals would be two modules. That split causes internal-state mismatches and mock-hoisting mismatches. Mock hoisting is the Vitest step that moves vi.mock calls above the imports of a test file. A hoisted mock must register on the same Vitest module instance that the test file later imports. Two copies give two registries, so the mock does not apply to the runner's copy. This is a real constraint, not a preference.

The Rust Test arm at vite-plus/packages/cli/binding/src/cli/resolver.rs:159-191 adds one more rule. It may prepend the argument run before the user arguments. should_prepend_vitest_run returns true when the argument list is empty (vite-plus/packages/cli/binding/src/cli/help.rs:87-90). It returns false when the first argument is a Vitest subcommand: run, watch, dev, related, bench, init, list, doctor, or complete (help.rs:57-64). It also returns false when an argument before -- is -h, --help, -w, --watch, or --run (help.rs:49-55, help.rs:96-101). It returns true in every other case (help.rs:103). Vitest itself starts watch mode when no subcommand is given. The documentation states this contrast (vite-plus/docs/guide/test.md:33-35). The prepended run therefore removes a default that would otherwise apply. The arm also sets a cache input to automatic tracking and excludes node_modules/.vite/vitest/**/results.json. That file is Vitest's results cache. Vitest rewrites it during a run, so file-system tracking would count the run's own write as an input (vite-plus/packages/cli/src/define-config.ts:774-790). Without the exclusion, every vp test task would stay permanently uncacheable. The exclusion glob keeps the file out of the input list (vite-plus/packages/cli/binding/src/cli/resolver.rs:179-185). This cache input matters only when Vitest runs inside the Vite Task engine, which documents 06 and 07 own.

2.6 resolve-core.ts

resolveCore is the single place that validates the vite alias. It reads the installed vite-plus/package.json version at run time, not at build time (vite-plus/packages/cli/src/resolve-core.ts:55-75).

// vite-plus/packages/cli/src/resolve-core.ts:54-76
/** Resolve the same core dependency as the CLI's static `vite` re-exports. */
export function resolveCore(
  subpath = '',
  cwd = process.cwd(),
  modulePath = import.meta.url,
): string {
  const cliRequire = createRequire(modulePath);
  // Read the selected CLI's installed manifest. A static JSON import is inlined
  // during the build, before CI and preview packers can stamp a new version.
  const { version: expectedVersion } = JSON.parse(
    readFileSync(cliRequire.resolve('vite-plus/package.json'), 'utf8'),
  ) as { version: string };
  let corePackageJsonPath: string;
  try {
    corePackageJsonPath = cliRequire.resolve('vite/package.json');
  } catch (cause) {
    throw new Error('Could not resolve the bundled Vite dependency. Run `vp install`.', { cause });
  }
  checkCoreVersion(corePackageJsonPath, expectedVersion);
  checkProjectCoreVersion(cwd, corePackageJsonPath, expectedVersion);

  return cliRequire.resolve(`vite${subpath}`);
}

checkCoreVersion requires both the package name @voidzero-dev/vite-plus-core and the exact expected version (vite-plus/packages/cli/src/resolve-core.ts:9-20). checkProjectCoreVersion validates the project copy only when the nearest package.json declares vite (vite-plus/packages/cli/src/resolve-core.ts:22-52). The comment at lines 27-28 states why: the Node Package Manager (NPM) can hoist an upstream Vite peer even when the project declares only vite-plus.

2.8 The vpx script loaders

Five more files support script execution rather than a build command: script-preload.ts, script-register.ts, script-hooks.ts, script-esm-hooks.ts, and script-watch.ts. They serve vpx, a separate executable in the vite-plus package (vite-plus/packages/cli/package.json:19). vpx is the package executor of Vite+, with the same role that npx has for npm. The bin/vpx launcher imports dist/vpx-bin.js (vite-plus/packages/cli/bin/vpx:1-9). That entry makes three choices (vite-plus/packages/cli/src/vpx-bin.ts:259-334). A path that resolves to a supported script file runs through the loader in this package. A file installed in node_modules/.bin runs directly. A versioned package, a --package flag, or --shell-mode hands off to vp dlx. vp dlx is the download-and-execute command that loads the CLI bundle and the native binding (vpx-bin.ts:11-12). oxc-node is the Oxc-based loader that performs the transform. Oxc is the JavaScript and TypeScript toolchain that parses and transforms the source. oxc-node applies that transform when Node.js loads a module, so a .ts file can run directly. pirates is the library that adds a CommonJS (CJS) require hook. --require and --import are Node.js flags that load a module before the script starts. script-preload.ts is the --require entry (vite-plus/packages/cli/src/script-preload.ts:2). The preload entry stops with exit code 1 when the Node.js version is outside ^22.18.0 || ^24.11.0 || >=26.0.0 (vite-plus/packages/cli/src/script-preload.ts:39-42, vite-plus/packages/cli/src/script-hooks.ts:68). It loads oxc-node, initializes the loader, sets the TypeScript transform dependency, and installs the pirates hook for JavaScript and TypeScript extensions (vite-plus/packages/cli/src/script-preload.ts:67-81).

script-register.ts is the --import entry. When synchronous hooks are not available, it registers the asynchronous ESM hook file through module.register() (vite-plus/packages/cli/src/script-register.ts:19-34). module.register() installs hooks on a separate hooks thread. "Off-thread" means that the hook work runs outside the main JavaScript thread. script-esm-hooks.ts is that off-thread hook file. It resolves and loads each module through oxc-node (vite-plus/packages/cli/src/script-esm-hooks.ts:1-29). The file comment explains that Node.js 22 cannot run this registration from a --require entry (script-register.ts:5-8). script-hooks.ts holds the shared logic (vite-plus/packages/cli/src/script-hooks.ts:37-112). threadScriptConfig captures the tsconfig path from the environment before the first resolve, because a worker can have a different environment (script-hooks.ts:33-50). canRegisterSyncHooks returns true only for Node.js 22.22.3 or later in the 22.x line, 24.11.1 or later in the 24.x line, or 26.0.0 or later (script-hooks.ts:94-103). Each threshold matches the Node.js release that fixed one required hook bug (script-hooks.ts:87-93). The comment also states that tsx switches at the same releases (script-hooks.ts:88-89). Helper-module routing sends only the helper imports that these hooks emit through the name vite-plus:oxc-node (script-hooks.ts:105-112). runtimeHelperSpecifier maps that name to @oxc-project/runtime/helpers/ (script-hooks.ts:121-126). script-watch.ts starts the watch variant with the --require and --import loader arguments (vite-plus/packages/cli/src/script-watch.ts:22-33). Document 04 owns the runtime and environment behaviour that these loaders depend on.

3. packages/core: the single package behind vite

4. vp_static_config: configuration without execution

vp_static_config is a Rust crate that reads a small set of top-level fields from vite.config.* without executing the file. The crate depends on oxc_parser, oxc_ast, and oxc_allocator (vite-plus/crates/vp_static_config/Cargo.toml). It parses the file into an Abstract Syntax Tree (AST) and extracts literal values.

The entry point is resolve_static_config (vite-plus/crates/vp_static_config/src/lib.rs:129-141).

// vite-plus/crates/vp_static_config/src/lib.rs:129-141
pub fn resolve_static_config(dir: &AbsolutePath) -> FieldMap {

        // No config file found — closed empty map; get() returns None for any key.

    };

        return FieldMap::unanalyzable();

The file names and their order match Vite's default list: vite.config.js, .mjs, .ts, .cjs, .mts, .cts (vite-plus/crates/vp_static_config/src/lib.rs:98-105). The parser accepts defineConfig({...}), defineConfig(() => ({...})), and a function body with exactly one return (vite-plus/crates/vp_static_config/src/lib.rs:205-263). It trusts only a defineConfig binding imported from vite-plus or vite (vite-plus/crates/vp_static_config/src/lib.rs:21, vite-plus/crates/vp_static_config/src/lib.rs:337-360).

The result type is FieldMap (vite-plus/crates/vp_static_config/src/lib.rs:49-92). FieldMap has a closed mode and an open mode. A closed map has no spread and no computed key. Every absent key is definitely absent. An open map has at least one spread or computed key. An absent key may still exist at run time. get returns FieldValue::NonStatic for a possible key in an open map. get_declared returns only keys that the file explicitly writes. The difference matters when the file exists but cannot be read as text. no_config() means the field is definitely absent, so get returns None (vite-plus/crates/vp_static_config/src/lib.rs:61-65). unanalyzable() means the field may exist, so get returns Some(NonStatic) (vite-plus/crates/vp_static_config/src/lib.rs:55-59). A caller that must not change behaviour on an unknown value uses get_declared, which returns None in both cases (vite-plus/crates/vp_static_config/src/lib.rs:79-88). app_target.rs uses get_declared for exactly this reason (vite-plus/packages/cli/binding/src/cli/app_target.rs:54-73). The object extractor implements this rule.

// vite-plus/crates/vp_static_config/src/lib.rs:433-461
fn extract_object_fields(obj: &oxc_ast::ast::ObjectExpression<'_>) -> FieldMap {
    let mut map = FxHashMap::default();
    let mut open = false;

    for prop in &obj.properties {
        if prop.is_spread() {
            map.clear();
            open = true;
            continue;
        }
        let ObjectPropertyKind::ObjectProperty(prop) = prop else { continue };
        // A key with a lone surrogate is statically known but not
        // UTF-8-representable, so it cannot key the map — treat it like a
        // computed key and open the map.
        let Some(key) = prop.key.static_name().and_then(StaticPropertyName::into_cow_str) else {
            map.clear();
            open = true;
            continue;
        };

        // Open and closed maps alike record explicit declarations, including
        // NonStatic ones: `get_declared` must distinguish a written
        // `key: expr` from a key that merely might exist behind a spread.
        let value = expr_to_json(&prop.value).map_or(FieldValue::NonStatic, FieldValue::Json);
        map.insert(Box::from(key), value);
    }

    FieldMap { map, open }
}

A spread clears the map, because keys before a spread can be overwritten by it. Keys written after the spread are recorded again. expr_to_json accepts null, booleans, numbers, strings, single-quasi template literals, arrays, and objects (vite-plus/crates/vp_static_config/src/lib.rs:482-540). It returns None for a call, an identifier, a template with expressions, or a spread inside an array or object.

8. vp check

vp check is a composite command. It runs formatting, linting, and optional type checking in one invocation. The general dispatch is a direct call from Rust, not a child process for the whole composite (vite-plus/packages/cli/binding/src/cli/mod.rs:99-123). execute_check receives the flags and the environment map (vite-plus/packages/cli/binding/src/check/mod.rs:21-33).

The command has these phases:

  1. Read the universal Vite configuration (vite-plus/packages/cli/binding/src/check/mod.rs:43).
  2. Decide whether the format step and the lint step are enabled (check/mod.rs:61-78).
  3. Run Oxfmt, unless the step is disabled.
  4. Run Oxlint, with type checking when enabled.
  5. Run Oxfmt again after --fix lint edits (check/mod.rs:281-309).

The format step is skipped when --no-fmt is passed or when check.fmt is false. The lint step is skipped in the same way (check/mod.rs:65-74). The skip note is printed only when the configuration disabled the step, not when a flag did (lines 67-72). This keeps the existing flag output unchanged.

The type-check decision is not a separate option. typeAware enables lint rules that need TypeScript type information (vite-plus/docs/guide/lint.md:45-52). typeCheck enables the full type-check pass. typeCheck depends on the type-aware analysis, so that analysis must be on. It requires both typeAware and typeCheck in the lint.options block (vite-plus/packages/cli/binding/src/check/analysis.rs:84-90).

Inside _, it writes a .gitignore, the shared h script, and one stub for each supported hook name (vite-plus/packages/cli/src/config/hooks.ts:595-617). enable calls install, and install sets core.hooksPath to /_ (hooks.ts:404, hooks.ts:595-621). Git runs only files under core.hooksPath, so the generated stubs are the only entry points that Git sees. The _ directory holds only generated files. Git ignores those files (hooks.ts:610-616). Git then runs a path such as .vite-hooks/_/pre-commit. That stub sources _/h. The h script computes the project hook path by removing the _ segment, so it runs .vite-hooks/pre-commit when that file exists (hooks.ts:60-83). The _ directory stays out of commits because enable writes a .gitignore with * inside it (vite-plus/packages/cli/src/config/hooks.ts:611). disable persists the disable preference in local Git configuration and removes only the generated _ directory (hooks.ts:670-745). status reports the preference, the current core.hooksPath, the dispatcher presence, and project-owned hook scripts (hooks.ts:748-790). The hooks/bin.ts entry dispatches enable, disable, and status (vite-plus/packages/cli/src/hooks/bin.ts:1-31).

vp config is the post-install setup command. It parses its flags, installs the hook dispatcher, and updates existing agent instruction files (vite-plus/packages/cli/src/config/bin.ts:18-80). The agent instruction files are AGENTS.md, CLAUDE.md, GEMINI.md, .github/copilot-instructions.md, .cursor/rules/viteplus.mdc, and .aiassistant/rules/viteplus.md (vite-plus/packages/cli/src/utils/agent.ts:14-69). updateExistingAgentInstructions updates only files that already contain the Vite+ markers, and it never creates a file (vite-plus/packages/cli/src/utils/agent.ts:211-242, config/bin.ts:78-81). It also stops when it finds a stale Vitest alias that points to the removed @voidzero-dev/vite-plus-test package, and it tells the user to run vp migrate (config/bin.ts:28-34). The command treats prepare and postinstall lifecycle events as opting in to hook installation (config/bin.ts:22-24). An explicit hooks directory also opts in, because the interactive question is skipped in that case (config/bin.ts:58-63). This repository calls it from the prepare script (vite-plus/package.json:23).

The installed hooks can be disabled for one process or one machine. VP_GIT_HOOKS=0 makes every hook exit immediately, and HUSKY=0 has the same effect (vite-plus/docs/guide/commit-hooks.md:124-132). Before it reads that variable, each hook sources an init script from $XDG_CONFIG_HOME/vite-plus/hooks-init.sh, with $XDG_CONFIG_HOME/husky/init.sh as a fallback (commit-hooks.md:134-147).

vp staged runs checks on staged files with the lint-staged programmatic API. It reads the staged block from vite.config. and passes it to lint-staged as an explicit configuration object (vite-plus/packages/cli/src/staged/bin.ts:59-82). The documentation states that vp staged bundles lint-staged 17 and requires Node.js 22.22.1 or later in the 22.x line, or 24.11.0 or later (vite-plus/docs/guide/commit-hooks.md:83-90). The default staged configuration is { '': 'vp check --fix' } (commit-hooks.md:108-116).
