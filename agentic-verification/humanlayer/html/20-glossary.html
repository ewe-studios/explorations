Glossary

This glossary defines every term that the exploration uses. Each entry gives the meaning in this codebase, not a general meaning. Where a term names a code element, the entry gives the file. Read the entry, then follow the link to the document that explains the mechanism.

Some term groups follow a plane, and the host machine has a group of its own. Three planes exist. The control plane is the Application Programming Interface (API) and the daemon: processes that accept intent or report state through the API. The sync plane is PostgreSQL, its write-ahead log (WAL), Electric, and the Electric proxy. These components deliver read-only shapes. The client plane is the web user interface, the desktop shells, the command-line interface (CLI), and the plugins. The daemon runs on a user host. The host is an actor (a participant), not a plane. The daemon also appends to the durable stream (the append-only live event log), which is a supporting service. Some terms appear in more than one group, because one word carries different work in different places. The abbreviation table below expands every abbreviation that the documents use.

The diagram places the daemon in the host group by location. By function it belongs to the control plane: it accepts intent and reports state through the API. Here the word actor means a participant, not a software platform. The proxy reads PostgreSQL to run the capability and session checks on shared-artifact and session routes (apps/riptide-electric-proxy/src/lib/queries.ts:139-156, :211-217). The user interface reads the durable stream directly for live session output and Yjs document collaboration (apps/riptide-ui/src/hooks/useStreamDB.ts:1).

The session lifecycle

The status list is declared once, in packages/schemas/src/effect/session/session-status.ts:7-21. The file comment calls the list the single source of truth (:3-6). The transitions are code in the handlers, not a declared table, so the repository does not define a legal-transition map.

StatusMeaning
draftA session that exists but is not prepared for a host.
waiting_for_workspaceThe host has the session, and the daemon has not finished preparing the workspace.
ready_for_launchThe workspace is ready, and the daemon can start the agent process.
launchingThe daemon is starting the agent process.
runningThe agent process is active.
ready_for_inputThe agent is not working, and it waits for a person or a queued message.
needs_approvalThe agent asks for permission to run a tool, and it waits for an answer.
waiting_for_usage_limitThe agent provider's usage limit blocks progress, and the session waits.
interrupt_requestedA person asked to stop, and the daemon has not yet acknowledged.
interruptedThe agent process stopped because of the request.
resumingThe daemon is restoring a session that was ready for input, interrupted, failed, or lost.
failedThe session ended with an error.
lostThe control plane cannot find a live daemon for the session.

The golden document golden/session_state_machine.md describes the intended graph. Document 03 compares the document with the code.

Aha: The status list is the only shared vocabulary between the schema packages, the daemon, and the user interface. The transitions are not part of that vocabulary. The schema file declares 13 values, and the golden document draws a graph with 11 of them. The missing two, waiting_for_workspace and lost, exist only in code. This is why the state machine cannot be generated from a declaration: the declaration names the states, but the edges live in handlers.

Identifiers, in one picture

Four identifiers appear often. They are easy to confuse, so this diagram separates them.

sequenceDiagram participant D as Daemon participant A as API participant P as PostgreSQL participant E as Electric participant X as Electric proxy participant U as User interface Note over D,A: Write one: daemon D->>A: create event with event identifier A->>P: BEGIN and lock session row A->>P: INSERT conversation_events P-->>A: transaction identifier from pg_current_xact_id A-->>D: event identifier and transaction identifier Note over U,A: Write two: user interface U->>U: optimistic row with a temporary identifier U->>A: submit the write with that identifier A->>P: INSERT the row P-->>A: transaction identifier A-->>U: row identifier and transaction identifier E->>P: read the replication stream E-->>X: shape rows past the transaction identifier X-->>U: filtered shape rows U->>U: replace the optimistic row with the confirmed row

The diagram shows two writers: the daemon for conversation events, and the user interface for its own rows. The user interface submits the write with a client-generated identifier. The API inserts the row and returns the transaction identifier. The interface replaces the optimistic row when the shape delivers the confirmed row. The temporary identifier is a client-side placeholder, not one of the four server identifiers in the table below.

IdentifierCreated byUsed for
Session identifieruuidv7() in the database or in the applicationAddresses the session row, the stream path, and the Electric filter
Event identifierThe daemon, or the database when the daemon omits itMakes the insert idempotent
Transaction identifierPostgreSQL, through pg_current_xact_id()Lets the client wait for Electric to pass the write
Share keyThe API, when a person shares an artifactGrants read access with no account
