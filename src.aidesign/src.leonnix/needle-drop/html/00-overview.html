00 Overview: The Film, the Six Shots and the Three Sets

Needle Drop is a 30 second film. Three headless Blender scenes build it. Headless means that Blender runs without a window. Each scene is a Python script that rebuilds one .blend file from an empty factory state. The film has six shots and one visual motif. The record and its parts appear at four scales. A canyon is a record groove. A turntable is the machine that plays it. A desert becomes a 2.4 kilometre record. A mountain-sized tonearm lowers a needle onto that record.

This document gives the film, the shot map, the three set builders, the set-piece structure and one frame traced end to end. It also explains how the production bible and the builder brief relate. It does not repeat the mechanism detail of document 02. It does not repeat the production detail of document 03.

The film in one paragraph

The film opens inside a glossy marbled canyon. The canyon is the groove of a vinyl record. A chrome cantilever and a black diamond stylus appear at the end of the first shot. The camera pulls back to a vermilion turntable in a studio cove. The turntable spins at 200 degrees per second. The camera dives at the record and turns with it until the marbled surface fills the frame. A match cut turns the same marble into a desert seen from 380 metres above. A match cut joins two shots at one shared shape or colour. The desert reorganises into a record on the music drop. A shock wave of sand races outward. The camera cranes up and looks down on a 2.4 kilometre disc with a saffron label and a central crater. A giant tonearm casts a shadow across the rings. The needle lands on the outer groove at 29 seconds. The film cuts to black and loops on the crackle that opened it.

The image is 2560 by 1440 pixels. The frame rate is 24 frames per second (fps). The rendered picture runs from frame 1 to frame 708. Frames 709 to 720 are black. The encoder adds them. The render engine is EEVEE, the Blender real-time render engine, with screen-space raytracing. The view transform is AgX, a Blender tone-mapping transform, with the Punchy look.

The idea: one record motif at four scales

The film uses the record motif at four scales. The first appearance is the groove canyon in Set A. The second is the turntable in Set B, where the tonearm is 0.235 metres long. The third is the desert record in Set C, where the disc radius is 1200 metres and the diameter is 2400 metres. The fourth is the same tonearm in shot S6, scaled 8000 times to 1880 metres. A tonearm is not a record. The motif is the record and its playing parts. The chain is groove, machine, desert and giant needle. The production bible names three scales: microscopic, human and geological. The package specification is spec.md. It counts four appearances, because the giant tonearm is a separate reveal. The film has one typography rule. The turntable label reads SIDE A. The desert label reads SIDE B.

The idea survives the cuts because the marble field is shared. The same node construction paints the vinyl, the groove wall and the pre-drop desert sand. The numbers change with each scale. The shape language does not.

What the package ships

The package is a source checkout at pin 8982f09c1502b5f6c01b1aa7c1eee23e5139677b. It has 100 tracked files. It has no licence file. It has no package manifest and no version field.

The source tree has four source layers: three code trees and one data tree. The scenes tree holds the three set builders and their helper modules. The tools tree holds the shared look library, the safe Blender runner, the frame render tool, and the mastering and encode scripts. The audio/scripts tree holds the music edit, the analysis, the cue build, the delivery master and the checks. The data tree holds the beat grid, the timing events, the handoff values and the Set C layout file. The scripts also name docs/, blend/, renders/, delivery/, stills/ and assets/. The checkout contains docs/ and stills/. The other four directories are absent at the pin.

The build outputs are not in the checkout. The package does not include the rendered frames, the mixed audio, the source music or the downloaded Poly Haven assets. Poly Haven is an external library of three-dimensional models and textures. A rebuild needs Blender 5.2.2, ffmpeg, Node.js and a network connection. Blender builds the scenes and renders the frames. ffmpeg encodes the picture and the sound. Node.js runs the audio helper scripts in audio/scripts. The exploration reads the source and runs nothing.

The three scene builders do not share one file. They share two libraries and one data contract. The libraries are tools/common.py and tools/nd_lib.py. The data contract is the data/ directory. Set A and Set B both write data/handoff.json. Each builder loads the existing file and keeps the blocks that it does not own. Set C reads the file. The audio stage writes data/timing.json, data/beats.json and data/bands.json. Set A reads the timing events through its design module. Set C reads the beat list and the band series. Set B reads no audio data and uses fixed frame constants. The event map is the shared time reference for the production, and the audio stage owns it. The beat list gives the kick times. The band series gives eight frequency band energies for each frame. Set C uses them to light the sand.

The three sets

The three sets are separate Blender files. The sets are never combined into one scene. Each set has its own physical subject size. The unit does not change: one Blender unit is one metre in every set. The subjects differ by about four orders of magnitude: the largest ratio is 2400 / 0.235, which is 10,213, so the numbers differ.

Set B builds a studio cove, a platter, a record, a label, controls and a tonearm. A cove is a curved seamless backdrop. A platter is the round plate that carries the record. The controls are the buttons and switches on the turntable base. The tonearm is built in a local frame with the pivot at the origin. A local frame is the coordinates of the asset before placement. The pivot is the origin of that frame. A collection is a named group of Blender objects. Set B writes the tonearm collection to blend/tonearm_asset.blend. Set C appends that file. Append copies the objects from one Blender file into another. This is the asset handoff that makes one arm serve two scales.

Set A and Set B both write data/handoff.json. Each builder reads the existing file first. It replaces only its own block. Set A owns S1_end, which carries the last three camera frames of Set A. Set B owns S2_start and S2_end, which carry the first and last camera frames of Set B. Set C reads the S2_end block to match its marble to the Set B record. The other two blocks are continuity records for a person. No code reads them.

The set-piece structure

The film is built from six shots. It has four hard transition points. The first is a hidden occluder cut at frame 121. An occluder cut hides the edit behind an object that fills the frame. The camera has climbed onto the cantilever, and the new shot starts on the cantilever at a smaller scale. A cantilever is the tube that carries the stylus. The second is a rotation-locked match cut at frame 289. The camera turns with the record, so the record surface stays still in frame. The marble pattern does not change shape. Only the scale and the camera change. The third is a hard reverse-angle smash cut at frame 433, on the drop. A smash cut is an abrupt cut to a contrasting view. The fourth is a hard cut to black at frame 709. The boundaries at frames 517 and 625 are continuous camera moves inside Set C, not cuts.

The film also has three deliberate holds (docs/bible.md:35). A hold keeps the camera still. The turntable orbit holds from 7.5 to 10.0 seconds, frames 181 to 241. The top-down marble holds from 12.0 to 12.75 seconds, frames 289 to 307. The top-down record holds from 24.5 to 26.75 seconds, frames 589 to 643. The top-down marble hold is the S2 to S3 match cut at frame 289. The top-down record hold is in shot S5. The third hold crosses the S5 to S6 boundary at 26.0 seconds. The camera stays still while the tonearm enters, so shot S6 starts inside the hold. The film also has a visual freeze from 17.5 to 18.0 seconds. The master forces digital zero from 17.500 to 17.998 seconds. The tempo is 120 beats per minute, from data/timing.json, so the 0.5 second freeze is one beat. The sand grains are small mesh particles that the drop front throws outward. The kick rings are expanding sand rings placed on the kick times. The grains and the rings freeze in that interval.

The handoff value record_m_per_desert_m is 0.0001315712. It gives record metres per desert metre. One desert metre equals 0.0001315712 record metres. One record metre therefore equals about 7600 desert metres. The value comes from the Set B frame width divided by the Set C frame width. The Set B camera sensor is 36 millimetres wide, the lens is 28 millimetres and the depth is 0.05 metres. The visible width is 2 0.05 (36 / 2) / 28, which is 0.064286 metres. The Set C width is 488.6 metres. The two cameras see the same marble pattern at two scales. The cut has no visible pattern change. The mesh geometry does change, because Set C shows dunes.

The mapping scale is the Set B marble scale times this ratio: 12.0 * 0.0001315712 equals 0.001578855. The angle aligns the Set B record coordinates with the Set C desert axes. The offset places the record point at the desert camera target. The z offset 0.018 metres sets the field height on the sand surface.

The Set C camera at frame 289 is at desert position (880, 0, 380). It looks straight down. The lens is 28 millimetres and the sensor is 36 millimetres wide. The visible frame width is 2 380 (36 / 2) / 28, which is 488.6 metres. The screen up direction is plus X. The screen right direction is minus Y.

The Set C camera path is a pure NumPy function. NumPy is the Python numerical array library. The function samples the start of each frame, t = (f - 1) / 24. Frame 433 therefore samples 18.0 seconds. At time 12.0 seconds, the S3 branch holds the altitude at 380 metres and the pitch at minus 90 degrees. The branch changes at 12.75 seconds, when the descent starts. The camera is baked as one linear key per frame. Baked means that the path is computed in advance and stored as keyframes. A keyframe stores a value at a frame. Set C also adds two keys at CUT - 0.01 and CUT + 0.01, where CUT is 432.5. The source docstring calls them half-frame keys, but the offset is 0.01 frame, not 0.5 frame. The two keys make the camera change almost instant at the S3 to S4 cut. Linear interpolation does not blend the two camera branches across a full frame.

At frame 289 the record morph is not active. The function front_r gives the radius of the drop front. It returns minus 200 metres for every time below 18.0 seconds. The live node group computes u = (front - radius) / 60 and clamps u to the range 0 to 1. A front at minus 200 metres gives u = 0 for every disc radius above minus 200 metres. The disc therefore shows the dune height, not the record height. The desert is still a desert.

The shader, the material program, does the same. The sand material mixes the pre-drop marble colour with the post-drop record colour by the stored morph attribute. An attribute is a named value stored on each mesh point. At frame 289 the attribute is zero, so the pre-drop colour wins. The same marble field paints the sand and the vinyl. That is the reason the cut works.

The render uses EEVEE with screen-space raytracing. The resolution is 2560 by 1440 at 48 samples. The view transform is AgX Punchy with plus 0.2 exposure. The compositor, the Blender image combine stage, adds mist tint, bloom, streaks, lens dispersion, saturation and a vignette. Bloom is a soft glow around bright areas. Streaks are light lines drawn from bright pixels. Lens dispersion shifts colour channels outward from the centre. A vignette darkens the corners. The frame is written as a 16-bit portable network graphics (PNG) file. The 16-bit value is per channel.

The audio at 12.0 seconds is in the build section of the music edit. A build section is the part of a track that raises energy before a drop. The music segment from 12.0 to 17.5 seconds rises. The event match_cut is a visual event, not a sound hit. A sound hit is a strong sound placed on a cut. The audio stage still snapped its frame to the beat grid if a beat was within 2 frames.

The finishing script is tools/master.sh. A dissolve is a cross-fade between two images. The script dissolves frames 289 to 305 from the colour of frame 288 into the Set C opening. The weight is the old colour weight. It starts at 17/18 for frame 289 and falls to 1/18 for frame 305. The new set therefore supplies 1/18 of the colour at frame 289 and 17/18 at frame 305. The geometry already matches, so the dissolve reads as a slow colour shift and not as a visible cross-fade.

Production bible versus builder brief

The project has three planning documents. The package specification is spec.md in this exploration package. It gives the package inventory, the line counts and the known divergences. The production bible is docs/bible.md. The builder brief is docs/BUILDERS.md. The brief states that it overrides the bible wherever the two disagree.

# docs/BUILDERS.md:3-4
Project root = the current working directory. The film spec is `docs/bible.md` (read it; it is long but it is the
spec). This file OVERRIDES the bible wherever they disagree.

The bible is a design document. It gives the logline, the palette, the shot intent, the lighting, the material recipes, the build order and the render plan. A logline is a one-sentence summary of the film. The builder brief is an engineering document. It gives the real file layout, the shared helper rules, the marble replacement and the machine safety rules. The marble replacement is the rule that every set calls build_marble_field, and no set forks the node group. To fork the node group means to make a separate copy of the shared node group. The machine safety rules keep one Blender process at a time, keep memory below a limit and yield to the user's own Blender work. The code is the final authority.

The difference matters because several bible numbers do not match the code. The bible plans a sample count of 48 for S1, 64 for S2, 48 for S3, 64 for S4, 48 for S5 and 48 for S6. The code uses 32 for Set A, 24 for Set B and 48 for Set C. The bible plans exposures of minus 0.3, 0.0 and plus 0.2 for Set A, Set B and Set C. The code uses plus 0.2, minus 0.5 and plus 0.2. The bible plans a 6 metre crest. The code uses 11 metres. The bible plans a mix at minus 14 loudness units relative to full scale (LUFS). The delivery script targets minus 14.3 LUFS.

The bible also names files that do not exist. It names scripts/safe_launch.ps1, scripts/probe.py, scripts/render_queue.ps1 and scripts/assemble.ps1. A .ps1 file is a PowerShell script. A .sh file is a shell script. The repository uses tools/brun.sh in place of safe_launch.ps1, tools/render_seq.sh in place of render_queue.ps1 and tools/assemble.sh in place of assemble.ps1. probe.py has no single replacement. Each set has its own probe script. The builder brief gives the real layout. Document 04 records each divergence and its evidence.

A reader must use three levels of trust. The bible is the design intent. The builder brief is the working instruction. The code and the data/ files are the final state. A number in the bible is not a measured result.

Who this document is for

This document is for a reader who wants the shape of the film before the mechanism. A graphics engineer can use it to see how one idea maps to three scenes. A Blender user can use it to see the split between a set builder and a shared library. A pipeline engineer can use it to see the data contract between sets. A reviewer can use it to see which numbers are design intent and which are code.

The document assumes no Blender experience. It names each object and each file. It explains the Blender concepts that the argument needs. It expands each abbreviation at first use. The source comments use ND for the module tools/nd_lib.py, GN for Geometry Nodes, and adr1 and adr2 as note labels. It does not assume that the reader has run the project.

The limits of this overview

This document is a static reading. It did not open Blender. It did not build a .blend file. It did not render a frame. It did not play the audio. It did not encode a film. Every statement about appearance is an inference from source. Every timing value is a data value, not a measured frame time.

The package has no licence file. The package has no rendered frame sequence. It has ten release stills, but this reading made no render. The package has no source audio. These limits apply to the whole exploration. Document 04 gives the full list.
