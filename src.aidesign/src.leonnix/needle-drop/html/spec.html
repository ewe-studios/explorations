Needle Drop is a 30 second film. It is built from three Blender scenes and a set of Python scripts. The film has one visual idea: a record appears at four scales. A canyon is a record groove. A turntable is the machine that plays it. A desert becomes a 2.4 kilometre record. A mountain-sized tonearm lowers a needle onto the desert.

The film uses six shots:

ShotNameFramesSetLength
S1The Groove1 to 120A5.0 seconds
S2The Machine121 to 288B7.0 seconds
S3The Desert289 to 432C6.0 seconds
S4The Drop433 to 516C3.5 seconds
S5The Record517 to 624C4.5 seconds
S6The Needle625 to 708C3.5 seconds

The film has no hand keyframes on the camera. Each set script computes a camera path in NumPy. The script then writes one linear key per frame into the .blend file. Set B also writes a second file, blend/tonearm_asset.blend. Set C appends that file and scales the tonearm by 8000, so the same asset is a desk-sized arm in S2 and a mountain-sized arm in S6.

2. Scope

This package covers Needle Drop as a system. It covers these areas:

  • The film idea: one record at four scales, and the six shots that show it.
  • The production plan: the production bible, the builder brief that overrides it, and the

data/ files that hold the numbers of record.

  • The three set builders: their entry points, module boundaries, geometry and materials.
  • The shared look library: the palette, the marble field, the fade group and the shared

material helpers.

  • The camera system: pure NumPy paths, piecewise cubic interpolation, the set A vault, the Set

C cut handling and the Set B rig.

  • The match cut: the S2_end handoff values and how Set C rebuilds the same marble field.
  • The drop: the front wall, the spring-overshoot morph, the kick rings and the record build.
  • The giant tonearm: the asset handoff, the 8000 times scale, the cheat table and the touchdown.
  • The render path: the safe runner, the chunked render script, resolution and sample overrides.
  • The finishing path: the master script, the grain, the frame-count check and the verification.
  • The audio path: analysis, music edit, cue sheet, delivery master and verification.
  • The limits: missing source audio, absent render output, unstated licence and static-only

evidence.

It does not run Needle Drop. It does not start Blender, build a .blend file, render a frame, mix audio or encode a film. Every runtime number comes from source text or from a data file. The exploration marks such numbers as not verified when no output exists.

9. Limits

  • Static reading only. No frame was rendered, no film was viewed and no audio was measured.
  • The film, the stills' source renders and the .blend files are not in the repository.

.gitignore ignores .blend, .mp4, renders/ and logs/.

  • The source audio is not in the repository. The Mixkit licence forbids redistribution.

audio/music_edit_map.json and audio/cues.json hold the edit decisions, not the samples.

  • The downloaded Poly Haven assets are not in the repository. The build scripts fetch them.
  • No Blender was opened. Geometry Node behaviour, shader compilation, EEVEE settings and

timings are not verified.

  • The NumPy paths were read, not executed. Numeric output comes from constants in the source.
  • The audio scripts were read, not executed. Loudness, peak and cue alignment are not verified.
  • The build is not reproducible here. It needs Blender 5.2.2, ffmpeg, Node.js and the network.
  • The released files on GitHub were not downloaded or inspected.

10. Corrections and limits found during research

The inventory matched: pin 8982f09, 100 tracked files, no licence file and no manifest. The following findings qualify the first reading.

  1. The README says "everything is code", but the scenes load external assets. The README

claims "No hand modelling". The Set C builder calls c_props.trees, c_props.boulders and c_props.load_model, and those functions download and place Poly Haven models. Set B loads the studio_small_09 HDRI. The correct claim is that no bespoke model is hand built. The film still depends on CC0 models and textures.

  1. The marble is one field construction, not one fixed mapping. The README says "One

marble, everywhere". tools/nd_lib.py gives one build_marble_field function. Each set maps it differently. Set A calls it with scale=0.05 and warp=1.3 (build.py:277). Set B uses record coordinates at scale 12 and band frequency 4.4. Set C uses the handoff mapping at scale 0.001578855 and frequency 4.4. The shared part is the node construction and the colour stops, not the numbers.

  1. The bible is not the build specification. docs/BUILDERS.md:2 states that it overrides

the bible wherever the two disagree. The bible plans scripts/probe.py, scripts/safe_launch.ps1, scripts/render_queue.ps1 and scripts/assemble.ps1. Those four files do not exist. The real tools are tools/brun.sh, tools/foreign.ps1, tools/render_seq.sh, tools/render_frames.py, tools/master.sh and tools/assemble.sh.

  1. **data/timing.json is the data of record for time, and some events differ from the

bible.** lint_pass is frame 49 at 2.0 seconds; the bible used 1.9 seconds and frame 46. fade_in_end is frame 7; the bible used frame 6. shadow_enters is frame 613; the bible used 615. The note in timing.json says the audio stage snapped events to detected beats. The docs must use the JSON values and state the divergence.

  1. The delivered film is 708 frames, not 720. timing.json gives

"rendered_frames": [1, 708]. docs/BUILDERS.md says frames 709 to 720 are black and are added at encode. The README says "720 frames". Both are correct for different products.

  1. The loudness target is -14.3 LUFS, not -14.0. README.md and the bible state -14 LUFS.

audio/scripts/master_linear.py:89 sets TARGET_I = -14.3 and explains that the margin reduces limiting at the hits.

  1. The delivery mix comes from master_linear.py, not tools/mix.js. build_audio.sh

calls tools/mix.js to write audio/_work/mixjs_reference.wav and marks it "REFERENCE ONLY". The delivery file is audio/mix.wav, written by master_linear.py with a static gain and a latency-compensated peak limiter.

  1. Set C splits the record into three objects. The live RecordDisc with the morph

modifier is visible to frame 516. A RecordStatic copy is visible from frame 517. A RecordPatch sector covers the close view and is visible to frame 541. The split keeps the per-frame Geometry Node cost off 3.6 million vertices after the morph completes.

  1. The giant tonearm is the Set B asset, scaled 8000 times. c_props.tonearm appends

blend/tonearm_asset.blend, renames the collection, rotates it 90 degrees about Z and sets scale to ARM_LEN / 0.235, where ARM_LEN is 1880 metres. A cheat table moves parts to keep the silhouette correct at that scale.

  1. The Set C camera adds half-frame keys at the cut. c_cam.bake_camera keys every

integer frame from 289 to 708. It also keys CUT - 0.01 and CUT + 0.01, where CUT is 432.5. The extra keys stop motion blur from mixing the top-down S3 frame with the low S4 frame.

  1. The safe runner is Windows-specific. tools/brun.sh calls PowerShell through

cygpath, uses taskkill, and reads free memory through a Windows command. The README describes the behaviour but not the platform dependence. The script cannot run on macOS or Linux without changes.

  1. No licence is stated. The container study records needle-drop as not stated. The

README gives credits for assets and music but no licence for the code or the film.

  1. Some source claims are design intent, not code. The bible gives vertex budgets,

sample counts and timings as targets. The builder brief restates some as maxima. The code contains the final values. A reader must not treat a bible number as a measured result.

  1. The film is not reproducible from the checkout alone. The audio, the Poly Haven

assets and the rendered frames are absent. The build needs a network connection, Blender 5.2.2, ffmpeg and Node.js.
