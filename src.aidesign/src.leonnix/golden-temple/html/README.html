Golden Temple

Golden Temple is a 70-second film of a Japanese temple complex that exists only as code.

The package builds a complete site in JavaScript. It lights the site with one low sun and renders it to a fixed set of camera moves. It loads no three-dimensional model, no texture file, no high dynamic range (HDR) environment image and no photograph at run time. The buildings, roofs, bracket sets, statues, trees, lotus, water, terrain, clouds and sky are geometry and shaders. The film is the output of that construction, captured frame by frame in a headless browser.

This README is the map. It gives the thesis, a short summary and the inventory. It lists the six files, four reading orders, the entry points and a glossary. It ends with a clear list of what this exploration does not claim.

The film in one paragraph

The site is a temple precinct at the golden hour. A low sun at 6.8 degrees in the west-south-west rakes the stone court, the vermilion bridge, the gold fittings and the mirror pond. Ten shots of seven seconds each open on one small subject and pull back to the whole complex. The first shot starts inside a stone lantern and ends on the pagoda across the water. The last shot starts on backlit maple leaves and rises over the entire precinct. Every frame is an average of sub-frames. Each sub-frame has a different anti-aliasing offset, shutter time, sun position and ambient occlusion pattern. The average gives clean edges, motion blur, soft shadows and stable detail. A post pipeline adds ambient occlusion, depth of field, bloom, god rays, a tone map and a grade. The picture is encoded with ffmpeg, and a music track is edited onto it.

Entry points

Four short passages show the centre of the package. The first is the site plan header. One plan holds every position, so nine modules agree on where the hall, the pagoda, the pond and the gate stand.

# src/layout.js:1-5
// ---------------------------------------------------------------------------
// SITE PLAN — the single source of truth for where everything is.
// Units: metres. +X = east, +Z = south, +Y = up (north is -Z).
// Courtyard ground level y = 0. The sun is low in the WEST-SOUTH-WEST
// (direction toward sun ~ (-0.94, 0.12, 0.34)), so west faces glow and long

The second is the shot header. The film is ten shots of seven seconds. Each shot is a set of camera keys, and the camera evaluator samples them with an eased spline.

# src/shots.js:5-10
// The film: 10 shots x 7 s. Each shot: camera keyframes (pos/target) sampled
// by a Catmull-Rom spline with eased progress; lens; focus; post overrides;
// shadow focus region.
// ---------------------------------------------------------------------------

export const SHOT_DUR = 7.0;

The third is the sun. It is a direction, not a lamp position. The elevation and the horizontal direction define the whole light mood and the shadow direction.

# src/core/env.js:10-18
// Sun: low golden-hour sun in the west-south-west.
export const SUN_ELEVATION = 6.8 * deg;
export const SUN_AZ_DIR = new THREE.Vector2(-0.94, 0.34).normalize(); // horizontal (x,z) direction TOWARD the sun

export const sunDir = new THREE.Vector3(
  SUN_AZ_DIR.x * Math.cos(SUN_ELEVATION),
  Math.sin(SUN_ELEVATION),
  SUN_AZ_DIR.y * Math.cos(SUN_ELEVATION)
).normalize();

The fourth is the mode switch. One query string selects development, still or render mode. The same switch sets the quality level and the sub-frame count. The module list is the build order.

# src/main.js:28-32
const MODE = Q.get('mode') || (Q.has('shot') || Q.has('cam') ? 'still' : 'dev');
const QUALITY = Q.get('q') || (MODE === 'dev' ? 'preview' : 'final');
const SPP = +Q.get('spp') || (MODE === 'render' ? 8 : MODE === 'still' ? 4 : 1);

export const ALL_MODULES = ['terrain', 'pond', 'hall', 'interior', 'pagoda', 'bridge', 'buildings', 'props', 'vegetation'];

The abbreviation SPP means samples per pixel. The value is the sub-frame count for one film frame. The module list is also the build order, and the order is a dependency rule.

Who this is for

  • A graphics engineer who wants to see a large scene built without assets.
  • A rendering engineer who wants a worked example of sub-frame accumulation and a post chain.
  • A three.js user who wants to see how far a patched physical material can go.
  • A film pipeline engineer who wants a headless capture path with no intermediate frames.
  • An artist or art director who wants to understand what the code controls.
  • A reviewer who needs to separate source claims from render claims.

The package assumes comfort with JavaScript, three.js, shader code and the command line. It does not assume that the reader has run the project. The documents explain the terms they use.

AccumulationThe weighted sum of sub-frames into one high dynamic range image.

What this package does not claim

  • It did not run the project.
  • It did not start the development server or open a browser.
  • It did not build the world or compile a shader.
  • It did not render a still or a frame.
  • It did not encode a film or fetch the music.
  • It did not measure a frame time, a triangle count or a flicker metric.
  • It did not view the film.
  • It does not claim that the film looks correct, clean or complete.
  • It does not claim a fresh-reader review.
  • Runtime numbers are project claims and are marked as such.
  • Sibling package numbers come from their specifications and were not re-verified.
  • The film stills in docs/ are not analysed as evidence for the runtime result.

A reader must treat every statement about appearance as an inference from source. The source is strong evidence for structure. It is weak evidence for the final image.

Source method

The exploration read the source at pin 97fd9ec and modified nothing. It read the entry module, the site plan, the shot list, the engine modules, the world module tree, the shot override files, the tools and the project documents. It did not use the network and did not install a dependency.

Every quoted block carries a header with the source path and the line range. A separate check compared each block with the pinned file, line by line and byte for byte, including indentation and trailing semicolons. The check reported zero mismatches for the six documents. Line numbers refer to the pin, not to a later version.

The counts in the document table come from the same files. A word is a whitespace-separated token. The all-word count includes code blocks. The prose count excludes fenced code. The snippet count counts fenced text blocks with a source header. The Mermaid count counts diagram blocks. The Aha count counts bold Aha: paragraphs.

If a value is not defined in the source, the documents say "not defined" and name the file that would define it. If a claim depends on a render, the documents mark it as a render claim. This method is the reason the package can be trusted as a map and not as a review of the film.
