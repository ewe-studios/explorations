03 Workflow and quality: how one still becomes a film

Golden Temple is not produced by one command. It is produced by a loop. A camera is chosen, a still is captured, the motion is measured, a segment is rendered, the segment is checked for flicker, and only then is the full film encoded. The loop exists because the expensive step is the full film, and a defect found after four hours costs four hours.

This document describes the loop, the Uniform Resource Locator (URL) parameters and the tool flags and defaults. It follows the path of one still and the path of one film frame. It states the runtime claims, the music edit and the four quality metrics. It also explains what each metric can and cannot see.

The loop

The loop has seven stages. Each stage answers a different question.

  1. Build and view. Run the development server and open the page. A developer flies a free camera

and reads the shot player. The status line shows build progress and the head-up display shows the shot and local time.

  1. Capture stills. tools/snap.mjs loads the page once and renders several views from the same

world. A view may be a shot time or an explicit camera.

  1. Tile a contact sheet. tools/sheet.mjs calls snap for every shot at one or more times and

joins the stills into one image. A contact sheet shows the film at a glance.

  1. Check the motion. tools/camcheck.mjs runs on the central processing unit (CPU). It samples

every shot at 60 frames per second and reports speed, acceleration and turn rate.

  1. Render a segment. tools/render.mjs renders a frame range with a low sub-frame count, then a

higher count for the candidate. The render is resumable and frame accurate.

  1. Check the pixels. tools/lumaflicker.mjs, tools/mcflicker.mjs and tools/flickercheck.mjs

measure a finished segment for brightness flicker, motion-compensated shimmer and second difference noise.

  1. Splice and score. tools/splice.mjs replaces a range in a finished film. tools/score.mjs

edits the music and muxes it onto a copy of the video.

flowchart LR A[dev page] --> B[snap stills] B --> C[contact sheet] B --> D[camcheck] D -->|fix keys| A C --> E[segment render] E --> F[flicker checks] F -->|fix world or sampling| A F --> G[full render] G --> H[splice fixes] H --> I[score and mux] I --> J[final checks]

The loop is not a formal pipeline. A person decides when a still is good and when a metric is low enough. The tools supply evidence. They do not supply a pass mark. The source does not define a threshold for any metric.

The defaults are set in the entry module. Width and height default to 1280 by 720. The sub-frame count is eight in render mode, four in still mode and one in development mode. Quality is preview in development mode and final otherwise. The mode is still when the query has a shot or a camera, and dev otherwise. The tools override these defaults with their own values.

The capture tools share a browser locator. tools/lib/chrome.mjs uses the CHROME environment variable first. If it is absent, it searches the usual Chrome, Edge and Chromium paths for the platform. The graphics processing unit (GPU) flags enable the GPU, ignore the block list, enable the Web Graphics Library (WebGL), and disable the GPU watchdog, renderer backgrounding and background timer throttling. On Windows the launcher forces the Direct3D 11 (D3D11) ANGLE backend. The ANGLE environment variable overrides the backend on any platform.

snap and render refuse to start if the development server is not reachable. The error names the expected address and the command that starts the server. This turns a common mistake into a clear message instead of a blank page.

One still from first view to accepted frame

A still starts with a query string. A typical request is shot 3 at local time 3.5 seconds, at 1280 by 720 pixels. snap adds mode=still if the query has no mode. It adds shot=0 if the query has neither a shot nor a camera. If any --view has its own query, it adds skipfirst=1, so the base page load does not render a still that nobody asked for.

snap then takes a lock. The lock is a file in out/.gpu.lock. snap opens it with the exclusive-create flag. If the file exists, the tool waits and retries every 700 milliseconds. A lock older than 15 minutes is treated as stale and removed. The wait has a 60 minute limit.

# tools/snap.mjs:38-48
let lockHeld = false;
async function acquireLock() {
  fs.mkdirSync(path.dirname(LOCK), { recursive: true });
  const start = Date.now();
  for (;;) {
    try { const fd = fs.openSync(LOCK, 'wx'); fs.writeSync(fd, String(process.pid)); fs.closeSync(fd); lockHeld = true; return; } catch {}
    try { const st = fs.statSync(LOCK); if (Date.now() - st.mtimeMs > 15 * 60 * 1000) fs.unlinkSync(LOCK); } catch {}
    if (Date.now() - start > 60 * 60 * 1000) throw new Error('lock wait timeout');
    await new Promise((r) => setTimeout(r, 700));
  }
}

The lock matters because two headless browsers on one GPU compete for memory and can reset the context. The render tool holds the same lock. It refreshes the lock file every 30 seconds, so a long render is not mistaken for a stale lock. A still capture waits behind a full render, and a render waits behind a still.

snap launches the browser with a persistent profile. The profile holds the shader cache, so a second run is faster. A launch can fail if a recently closed Chrome still holds the profile. snap retries the launch 12 times and falls back to a fresh profile after eight attempts. This removes a common transient failure on Windows.

The page loads once. snap waits for window.__READY. It reads window.__ERROR and window.__info. It then renders each view through window.__renderView, which the still mode installs. That function builds a fresh query object, computes the camera and film time, renders one frame, waits one animation frame, and returns a data URL.

# tools/snap.mjs:95-104

The page side is small. __renderView parses the view query, takes the sub-frame count from the view or the page default, and calls renderFrame. The frame index defaults to 1, so the grain and any frame-indexed pattern do not use a random value. The function waits one animation frame before it reads the canvas. That wait lets the browser present the drawing buffer.

The saved file is the decoded base64 data. The tool does not read the canvas through a screenshot call, so the browser window size does not affect the image. The image size is the drawing buffer size, which the page set from w and h.

An accepted still is a human decision. The tool can show a broken frame, a missing module, a wrong focus or a black image. It cannot say whether the composition is good. The contact sheet is the main tool for that decision, because it puts the ten shots side by side at the same local time.

A still run can render many views from one page load. Each view writes its own file, and the name comes from the command line. The world is built once, so the second view pays only the render cost. This is why a contact sheet is cheap: the expensive startup is shared across ten shots. A view without a query reuses the page that is already on screen, and a view with a query builds its own camera and time.

The film frame path

render.mjs starts ffmpeg before it starts the browser. ffmpeg reads raw red, green, blue and alpha (RGBA) frames from standard input. It flips the image vertically and converts to luminance-chrominance (YUV) 4:2:0 with 8 bits per component. It then encodes with the H.264/Advanced Video Coding (AVC) encoder at the requested constant rate factor (CRF).

# tools/render.mjs:32-41
const ff = spawn('ffmpeg', [
  '-hide_banner', '-loglevel', 'warning', '-y',

  '-vf', 'vflip,format=yuv420p',
  '-c:v', 'libx264', '-preset', opt.preset, '-crf', String(opt.crf), '-tune', 'film',
  '-profile:v', 'high', '-color_primaries', 'bt709', '-color_trc', 'bt709', '-colorspace', 'bt709',
  // write the BT.709 primaries/transfer into the H.264 VUI too (ffmpeg 8 drops them otherwise; pixels unchanged)
  '-bsf:v', 'h264_metadata=colour_primaries=1:transfer_characteristics=1:matrix_coefficients=1',
  '-movflags', '+faststart', outPath,
], { stdio: ['pipe', 'inherit', 'inherit'] });

BT.709 is the colour standard for high-definition television. The encoder writes the primaries, the transfer function and the matrix into both the stream filter and the H.264 video usability information. Without that step a player may guess the colour space and show a shifted image. The comment states that ffmpeg 8 drops the tags otherwise.

The sequence below shows the transfer of one frame. The page never writes a file. The encoder is the only consumer of the pixels, and the server is the only writer to the encoder.

sequenceDiagram participant P as Page participant S as Local server participant F as ffmpeg P->>P: renderFrame() P->>P: readRenderTargetPixelsAsync() P->>S: POST /frame?i=N raw RGBA S->>F: write to stdin alt encoder buffer full F-->>S: drain end S-->>P: 200 ok P->>P: copy to canvas and wait cool-down

The tool starts a small Hypertext Transfer Protocol (HTTP) server on port 5190. The page posts each raw frame to /frame?i=N. The direction is page to tool. The tool never reads the canvas or a frame file. The server writes the buffer to the ffmpeg input. If the write returns false, the server waits for the drain event before it answers the page. This backpressure is the reason memory stays bounded. The browser cannot run ahead of the encoder by an unbounded number of frames.

The page does not encode a Portable Network Graphics (PNG) image for each frame. It reads the raw bytes from the post output target with readRenderTargetPixelsAsync and posts the buffer. The encoder flips the rows. A frame at 1920 by 1080 pixels with four channels is 8.3 megabytes. The transfer is one read and one post. The canvas copy that the render loop shows is a separate step and does not affect the posted bytes. A per-frame PNG encode would add processor work and a second copy, and it would not change the output film.

The read is asynchronous. The page awaits the read before it posts. A slow read therefore limits the frame rate, and the encoder waits. The two waits meet at the server, which is the only place where a queue exists. The queue has a natural limit, because the server does not answer the page until the encoder accepts the bytes. The design is a chain of backpressure, not a buffer of frames.

The render tool holds the GPU lock for the whole run. The lock is refreshed every 30 seconds while frames arrive. A still capture that starts during a render sees a fresh lock and waits. The tool polls the page every second. If the page reports an error in window.__ERROR, the tool prints the error, closes the browser, ends the encoder and stops. It does not retry the frame.

function heartbeat() {
  const now = Date.now();
  if (!lockHeld || now - lastBeat < 30000) return;
  lastBeat = now;
  try { fs.utimesSync(LOCK, now / 1000, now / 1000); } catch {}

The page side renders frames in a loop. It computes the film time, the shot, the local time and the fade. It clamps the camera time inside the shot. It calls renderFrame, reads the output target, posts the bytes and copies the frame to the canvas for a live preview. It then waits for the cool-down.

The pauses are 60 milliseconds after every frame and 15 seconds every 250 frames. For 4,200 frames the long rests add 16 rests of 15 seconds, or 240 seconds, plus 4,200 times 60 milliseconds, or 252 seconds. The total pause is about 8.2 minutes. The project README states about 8 minutes. The project also states about 4 hours for the full film on an AMD Radeon 780M. This exploration did not run the film, so these values are project claims, not measured facts.

Aha: The render has no frame files. The page posts raw bytes to a local server, and the server pipes them straight into ffmpeg. The run writes the final MP4, the Chrome profile and the lock, and no image sequence. This removes the disk space and the file naming of an image sequence. It also makes the frame number the only handle. That handle is enough for --from and --to, so a segment is resumable and a splice is frame accurate.

The resumable unit is a frame range. A segment render uses --from A --to B and writes a short MP4. splice.mjs trims the base film into three parts: before A, the segment, and after B. It joins them with a filter graph and re-encodes the result. The filter graph takes to - from frames from the segment. The tool checks only that to is greater than from (tools/splice.mjs:13). It does not compare the segment length with the replaced range. A longer segment has its extra frames dropped. A shorter segment makes the whole film shorter by the difference, and the tail moves earlier. Neither case stops the tool. The video stream is re-encoded; the score must be muxed again afterwards.

The tool assumes 60 frames per second in the output rate. It does not read the base frame rate. A film at another rate would need a matching -r value. The default CRF is 12, which is higher quality than the default 14 of the full render. A spliced range can therefore have a different size and a slightly different quantiser history from its neighbours.

The music edit

The film is silent until score.mjs runs. The tool reads one music file twice and builds a score. Track A starts at 4.46 seconds of the track and is placed at film time zero. Track B starts at 85.96 seconds and is placed at film time 39 seconds. The tool states the reason in a comment. The first koto note lands at film 0.2 seconds. A string crescendo lands on the 28 second cut. The biggest hit lands on the 42 second cut to the Buddha.

# tools/score.mjs:34-34
const A0 = 4.46, FILM = 70.0, B0 = 85.96, B_AT = 39.0;

The filter graph trims, fades and mixes the two sections. Track A fades in over 0.6 seconds and out from 38 seconds for 3 seconds. Track B fades in over 1.5 seconds and is delayed by 39 seconds. The mix uses normalize=0, so the tool does not change the relative level. The result is padded or trimmed to 70 seconds and faded out from 67.5 seconds. It is normalised to minus 16 loudness units relative to full scale (LUFS). The true peak is minus 1.5 decibels true peak (dBTP), and the loudness range is 11.

# tools/score.mjs:42-47
const filter = [

  `[1:a]atrim=start=${B0},asetpts=PTS-STARTPTS,afade=t=in:st=0:d=1.5,adelay=${B_AT * 1000}|${B_AT * 1000}[b]`,
  `[a][b]amix=inputs=2:normalize=0:duration=longest,apad=whole_dur=${FILM},atrim=0:${FILM},afade=t=out:st=${FILM - 2.5}:d=2.5,loudnorm=I=-16:TP=-1.5:LRA=11,aresample=48000[m]`,
].join(';');
ff(['-i', o.music, '-i', o.music, '-filter_complex', filter, '-map', '[m]', '-ac', '2', '-c:a', 'pcm_s24le', o.score]);

The score is written as 24-bit pulse-code modulation (PCM) at 48 kilohertz. The mux step copies the video stream without re-encoding and encodes the audio as AAC at 320 kilobits per second. The comment metadata records the music credit. The tool does not include the music file in the repository. fetch-music.mjs downloads it and checks a SHA-256 (Secure Hash Algorithm 256-bit) digest. The digest belongs to the file against which the edit points were timed. A different file raises a warning, because the cut points may not land on the musical hits.

Three audio measures set the level. Integrated loudness is the average level over the programme, in loudness units relative to full scale (LUFS). True peak is the highest reconstructed analogue peak, in decibels true peak (dBTP). Loudness range is the spread between quiet and loud passages. The target of minus 16 LUFS with a true peak of minus 1.5 dBTP leaves room for lossy encoding and for playback gain. The tool uses a single loudnorm pass, so the result is close to the target but not exact. A two-pass measurement would be more exact and would cost one extra decode.

The mux copies the video stream. A copy does not decode and encode the image again, so the picture keeps the quality of the silent render and the step is fast. The audio is encoded once, at 320 kilobits per second, which is above the usual transparency point for stereo. A splice breaks the copy rule: it re-encodes the whole film, so the audio must be muxed again and the video has one more encode generation. The workflow therefore renders a candidate segment, checks it, and splices only when the fix is worth a new encode.

The tools measure four different things. No single metric covers the whole image.

camcheck is a pure data tool. It imports evalShot, samples every shot at 60 FPS, and computes the first difference of position and direction. The output reports the maximum speed, the maximum turn rate, the maximum acceleration and the maximum turn acceleration. It also reports the time of each acceleration maximum. A large acceleration is a visual jerk even when every frame is sharp.

lumaflicker reads a film at 320 by 180 pixels in grey. It divides the frame into a 4 by 4 grid and computes the mean luma of each cell. It then measures the high-pass value: the absolute difference between the current value and the average of the two neighbours. A smooth exposure change or a slow camera drift changes all three values together, so it cancels. A frame-to-frame brightness jump remains. The tool skips frames within 0.05 seconds of a cut, because a cut is a real jump.

    let e = 0; for (let i = 0; i < G * G; i++) e += Math.abs(L[t][i] - (L[t - 1][i] + L[t + 1][i]) / 2);
    e /= G * G; all += e; n++; if (e > worst) { worst = e; wt = sec; }
    const s = Math.floor(sec / 7); const p = per.get(s) || [0, 0]; p[0] += e; p[1]++; per.set(s, p);
  }
  console.log(file, 'shots:', [...per].map(([s, [a, c]]) => `${s}:${(a / c).toFixed(3)}`).join(' '));
  console.log(`  ALL mean ${(all / n).toFixed(4)} /255   worst ${worst.toFixed(3)} @ ${wt.toFixed(2)}s`);

mcflicker predicts every odd frame from its even neighbours. It decodes the film at 640 by 360 pixels, selects the even frames, and asks ffmpeg to interpolate them back to 60 FPS with motion-compensated interpolation. The residual between the real odd frame and the predicted odd frame is the error. Smooth motion is predicted away; shimmer and sampling noise remain. The tool ignores a 12 percent border, because new content entering the frame cannot be predicted by flow.

# tools/mcflicker.mjs:14-28
const orig = grab(`scale=${W}:${H},format=gray`);
const pred = grab(`scale=${W}:${H},select='not(mod(n\\,2))',minterpolate=fps=60:mi_mode=mci:mc_mode=aobmc:me_mode=bidir:vsbmc=1,format=gray`);
const nf = Math.min(orig.length, pred.length) / N | 0;
let s = 0, n = 0, hi = 0;
for (let f = 1; f < nf - 1; f += 2) {
  const o = orig.subarray(f * N, (f + 1) * N), p = pred.subarray(f * N, (f + 1) * N);
  // ignore a 12% border: content entering the frame cannot be predicted by flow
  let e = 0, big = 0, cnt = 0;
  const mx = Math.round(W * 0.12), my = Math.round(H * 0.12);
  for (let y = my; y < H - my; y++) for (let x = mx; x < W - mx; x++) {
    const i = y * W + x; const d = Math.abs(o[i] - p[i]); e += d; if (d > 12) big++; cnt++;
  }
  s += e / cnt; hi += big / cnt; n++;
}
console.log(`${file} @${start}s: residual ${(s / n).toFixed(3)} /255, pixels >12: ${(100 * hi / n).toFixed(2)}%  (${n} frames)`);

flickercheck is the simplest of the three image metrics. It reads at 480 by 270 pixels and computes the mean absolute second temporal difference. It also reports the first difference for reference. It groups the result by shot. The second difference removes linear motion and linear exposure ramps. It does not remove a shadow that grows or a highlight that shifts colour.

Aha: The three image metrics are not redundant. A brightness flicker shows in lumaflicker but not in mcflicker, because a uniform brightness change is easy for flow to predict. A crawling texture shows in mcflicker but can cancel in the 4 by 4 grid of lumaflicker, because each cell averages many pixels. A per-frame noise pattern shows in flickercheck and in mcflicker, but a slow exposure drift shows in neither. The project uses all three because each one is blind to a different defect.

The quality gates

A candidate shot passes a sequence of gates. The source does not enforce the gates. The workflow comment and the tools define them.

  1. The still renders without a page error and without a missing module. The console shows the

module build lines and no [world] ... FAILED line.

  1. The contact sheet shows the right subject, the right focus and the right exposure at the chosen

local time.

  1. camcheck reports no large acceleration spike near the ends of the shot.
  2. A low-cost segment at reduced size and sub-frame count shows the motion and the cut.
  3. The segment at final size and eight sub-frames passes the three image metrics at a level the

author accepts.

  1. The full render completes. The frame counter matches the requested range.
  2. The music is muxed. The credits file is kept with any copy that contains the music.
  3. The final file is checked for duration, frame count, colour tags and audio level.

The gates have a cost. A still at 1280 by 720 with four sub-frames is cheap. A full segment at 1920 by 1080 with eight sub-frames is expensive. The loop runs the cheap gates first. It spends the expensive gate only on a candidate that already passed the cheap ones.

The gates also have a blind spot. No tool measures whether the subject is in the right third of the frame. No tool knows whether the camera move tells the intended story. No tool checks whether the focus falls on the face of the Buddha rather than the halo. No tool knows the intended colour. The metrics are comparative: the author compares a candidate with the previous candidate, or with a different time, and judges the difference. A number alone does not pass a shot. The source contains no threshold constant for flicker, acceleration or residual. A reader must not infer an official pass mark from the tools. The project supplies evidence for a human decision, and the human owns the decision.
