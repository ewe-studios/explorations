Earshot gives coding agents "ears". An agent can write code that makes a film, a game or a product demo, but it cannot hear the result. Earshot turns sound into evidence that an agent can read: calibrated text-to-audio match scores, the best moment inside a long recording, similarity to real reference recordings, a real-versus-synthesized judgement, a second-by-second listening transcript, an annotated image, and a launch-video scorecard. It also makes sounds from code (earshot forge), translates a recording into code (earshot fit), and renders a bank of sound effects for a film (earshot sfx, earshot kit). It runs on the central processing unit (CPU) and offers a command line interface, a Python application programming interface (API), and a Model Context Protocol (MCP) server.

2. Scope

This package covers earshot as a system. It covers these areas:

  • The core: audio loading and resampling, objective features, video frame and cut access, report

formatting, configuration, and the model wrappers.

  • The listening operations: describe, match, rank, find, compare, ab, realness,

timeline, sheet, critique and profile.

  • The vocabulary and the calibration: 322 descriptions in 16 categories, five prompt templates,

the term-bias removal, the per-sound z score and the verdict bands.

  • The realness detector: its features, its grouped training, its held-out evaluation and its tone

guard.

  • The timeline and the sheet: event detection, tags, sections, loudness, beat grid, sync to cuts

and cue frames, and the annotated image.

  • The launch scorecard: the reference profile from seven professional films, the metric ranges and

the timestamped advice.

  • Forge: physical synthesis in code, the recipe contract, the critic, the model-free tone checks,

the search loop and the bank.

  • Fit: modal, sine and spectral fitters, quality metrics, recipe code generation, takes and the

replication benchmark.

  • The sound bank and kits: 252 sounds rendered by identifier, the sfx aim and audit, and the

kit placement against a music bed and picture cuts.

  • The interfaces: the command line, the Python API, the MCP server, the two agent skills, and the

optional Gemini critique.

  • The quality record: docs/VALIDATION.md, docs/LIMITS.md, the evaluation folders, the

changelog, and the test suite.

It does not run earshot. It does not load the models, analyse audio, render a sound, run an evaluation, call a network service or listen to any file. All runtime numbers come from the project documents and are marked as not verified.

4. Constraints

  • No command, analysis, model load, sound render, fit, evaluation or test is run.
  • No network request is made. No model is downloaded.
  • Prose uses Aerospace and Defence Simplified Technical English, issue 100 (ASD-STE100). One idea

per sentence. Thirty words maximum. Expand every abbreviation at first use in each file.

  • Prose avoids marketing language, em dashes, "simply", "just", and "obviously".
  • A value that the source does not define is recorded as not defined.
  • The pin is 4ac3d2a. Runtime behaviour is marked as not verified.

  1. What problem does an agent have with sound, and how does earshot turn sound into evidence?
  2. How does one file move from bytes to a calibrated verdict: windowing, embedding, vocabulary,

term bias, z score and verdict band?

  1. How do the two models divide the work, and where do objective measurements replace a model?
  2. How does find search a long recording, and how does it avoid a trim that starts after the

attack?

  1. How does the realness detector separate real recordings from code-synthesized sound, and what

do its bands and its tone guard mean?

  1. How does timeline build a listening transcript and measure sync to picture cuts and cue

frames?

  1. How does critique build a reference profile from seven films and turn a measurement into a

timestamped fix?

  1. How does a forge recipe become a waveform, and how does the critic steer the search?
  2. How does fit invert a recording into a recipe, and which properties survive the round trip?
  3. How do the bank, sfx and kit place a sound at a picture moment without a model?
  4. How do the command line, the Python API, the MCP server and the skills share one contract?
  5. Which quality gates exist, what do they prove, and what does the project say they cannot prove?

10. Corrections and limits found during research

The inventory matched: pin 4ac3d2a, 287 tracked files, version 0.4.1, MIT code. The following findings qualify the first reading.

  1. The validation record counts 13 MCP tools, but the pin registers 16.

docs/VALIDATION.md:102 says 13 tools. earshot/mcp_server.py:529-533 lists 13 and earshot/mcp_server.py:607 adds sfx_list, sfx_render and kit_render. The validation record predates the three bank tools.

  1. The held-out library is 125 files in one place and 126 in another.

README.md:389 and docs/VALIDATION.md:5,16 say 125. docs/DESIGN.md and eval/README.md:25 say 126 rejected recordings. The source does not reconcile the two counts.

  1. The bank count is a sum of four files. forge_v2.json holds 183 entries,

forge04.json holds 51, fit.json holds 15 and pluck.json holds 3. The sum is 183 + 51 + 15 + 3 = 252 (README.md:198).

  1. The package version and the launch film tag differ. The package is 0.4.1. The launch

film is a v0.4.0 release asset (README.md:5). A release tag is not a package version.

  1. The vocabulary size is 322 descriptions in 16 categories. The number is the sum of the 16

category lists in earshot/data/vocab.json. Five prompt templates wrap a description (earshot/data/vocab.json, earshot/vocab.py).

  1. The test count is a release record. docs/VALIDATION.md:119 says 128 passed and 14

skipped in the fast run. The test files contain many parametrised cases, so the count is not the number of def test_ functions.

  1. The evaluation data is not in the repository. The scripts read licensed recordings and

third-party films from environment variables or a gitignored eval/local_paths.json (eval/README.md:20-38). Only derived numbers are committed.

  1. The two models cover different bands. CLAP hears up to 14 kHz. The AudioSet tagger hears up

to 8 kHz (docs/LIMITS.md:48).

  1. The bf16 path depends on the CPU. bf16 runs only on CPUs with native bf16 support.

Elsewhere the package runs fp32 (docs/LIMITS.md:58-60).

  1. The optional language model critique was never called live. Every path was tested against

a fake Hypertext Transfer Protocol (HTTP) layer (docs/VALIDATION.md:105-107).

  1. The project describes a multi-agent build process. docs/DESIGN.md:26-38 assigns one owner

per file. The exploration records this as a project statement and does not verify the process.
