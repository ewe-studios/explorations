1. Source

2. Scope

This exploration gives every one of the nineteen projects its own package. Each package lives in its own subdirectory of this exploration, has its own spec.md, its own markdown/ tree, and its own generated HyperText Markup Language (HTML) pages.

The container level supplies only two items:

  • markdown/README.md, the index. It gives the thesis, the four groups, the

nineteen-row table, the reading order, and the shared non-claims.

  • This file, the specification. It gives the pins, the document plan, the order

of work, and the verification rules.

Every project receives the same six-document exploration. Section 3 gives the fixed layout.

The exploration does not run a project. It does not build, render, test, or launch one. It does not evaluate visual quality. Section 8 states the limits.

3. Depth: every project is detailed

Depth does not follow size. Every one of the nineteen projects receives the same full exploration: six documents, and a deep dive for each part of the machine. A twelve-file skill still gets the overview, the architecture, the core mechanism, the workflow and quality, and the limits. The difference between a large project and a small one is how many code paths those documents cover, not whether the documents exist.

5. Per-package workflow

A package is complete only when all seven steps are done.

  1. Read the project: manifest, entry points, scripts, tests, and documents.
  2. Write spec.md in the package directory. It gives the pin, the file count,

the licence, the source map, the research questions, and the task table.

  1. Spawn the writer agent for that one package. The brief names the six-file

layout, the word and snippet minimums, the citation rule, and the source path. The writer is the only agent that writes prose.

  1. Validate mechanically: byte-exact snippet check, sentence length check,

relative link check, and Mermaid and Aha: count.

  1. Spawn the fresh-reader agent. It has no memory of the writing. It reads the

package documents with no tool use and no web access. It reports every place where it loses the thread or finds the depth too thin.

  1. Repair every reported gap. Where the source cannot settle a finding, record

it as unexplained instead of guessing.

  1. Build the HTML, commit with an ADD: prefix and no Artificial Intelligence

(AI) attribution, and push. Update the container README row from "Planned" to a live link.

Only one package is in flight at a time. A new package does not start until the current one is committed and pushed.

6. Constraints

  • The source is read only. No project file is modified.
  • No project build, test, render, or server run is executed.
  • Code snippets are copied byte for byte from the source, with the cited line

range. A reformatted snippet is a defect.

  • Prose uses Aerospace and Defence Simplified Technical English, issue 100

(ASD-STE100). One idea per sentence. Thirty words maximum. Every abbreviation is expanded at first use in each file.

  • Prose avoids marketing language, em dashes, "simply", "just", and "obviously".
  • A document states when its source does not define a value. It does not guess.
  • Each package repeats the non-claims in its own README, because a reader can

open one package without the container index.

7. Research questions

The container answers one question: what connects nineteen projects that look unrelated? Each package answers the same five questions in its own terms.

#Question
1What does the project make, and for which user?
2How does a run start, and which process owns state?
3Where does determinism come from: seed, fixed step, or a measured gate?
4What does the project check before it trusts a model report?
5What does the project say it cannot do?

The two poles add one question each. For tastecode: how does a local server turn design judgement into phases, checks, and an append-only event log? For taste-skill: how does a Stop hook turn a browser measurement into a condition for finishing?

8. Limits of the container study

  • No runtime behaviour was observed. Every runtime claim comes from source text.
  • A licence field is recorded as the files state it. Four projects state no

licence. Two projects have a split licence. Section 10 records both cases.

  • A short commit identifier can collide or move upstream. A later reader must

record a new pin.

  • File counts can include generated, vendored, or fixture files.
  • The container index does not compare visual quality. Quality claims need

output, and no output was produced.

  • The bundled copies of skills inside tastecode are older than the container

checkouts. Section 10 records the versions.

10. Corrections and limits found during research

The inventory was correct at the time of reading. All nineteen pins and all nineteen file counts matched. The following findings correct or qualify other assumptions.

  1. The container is not a package. There is no container manifest, README, or

Git repository. The word "package" in the task means a group of checkouts.

  1. The licence field is unreliable in two projects. first-bloom has no

licence file and its manifest says ISC. Its README names licences for assets. valle-morta has an MIT licence file, but its manifest says ISC. The licence file and the README agree, so the manifest field is stale.

  1. Four projects state no licence. feed-backrooms, first-bloom,

needle-drop, and procedural-alpine-lake have no root licence file. The exploration records them as not stated. It does not infer a licence.

  1. afterglow has a split licence. The MIT licence covers the code. It does

not cover the musical composition, the film, the audio, or the stills. A reader must not treat the whole repository as MIT.

  1. tastecode bundles older skill copies than the container holds. The

default-skill manifest pins taste-skill at version 2.5.0 and cinetic at commit ecfa6605. The container has taste-skill 2.5.1 and cinetic at f4bbfc8. The cook pin is b23cac6, which equals the container checkout.

  1. tastecode main ships three providers. The provider plan states that

main ships Codex, Claude Code, and Grok only. Other adapters exist in the source tree and are described as nightly work. A reader must not assume that every adapter in the tree ships on main.

  1. No runtime claim is verified. I did not run a build, a test, a render, or

a server. Statements about output quality come from project documentation and from source structure, not from observed runs.

  1. Some projects have no package manifest. needle-drop is a Blender Python

project. cook and unlazy are skill folders. Their file counts are small because they contain text and scripts, not application code.

  1. Two projects belong to two groups. halo-above-the-clouds and

room-at-dawn each contain a real-time scene and an offline film. The index marks both groups for these projects.

  1. The earlier plan was too flat. A first draft gave the whole container six

documents and treated the container as one package. That draft did not cover the seventeen smaller projects in detail. The current plan gives each project its own package, as the task requires.
