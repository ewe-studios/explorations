SceneOne cliffside living room, eight camera shots and six outside views

Casa Ocaso is a real-time recreation of a cliffside living room at golden hour. The room has a curved glass wall, a plaster core with two linear fireplaces, a curved boucle sofa, a travertine coffee table, a round wool rug, a lounge chair, a dining terrace, a cliff and Mediterranean planting. The browser draws the room with the WebGPU renderer of three.js and its node material system, Three Shading Language (TSL). The outside is a set of six real high dynamic range (HDR) panoramas. Each panorama is rotated so its sun matches a reference image. The renderer restores the clipped sun with a measured halo. A pre-baked light probe grid supplies the bounce light.

The project states that an artificial intelligence coding tool built the room from five reference renders (README.md:3-5). The exploration records this as a project statement. It does not verify the process and does not repeat the product name.

2. Scope

This package covers casa-ocaso as a system. It covers these areas:

  • The room plan: one config file holds the curved glass, roof, oculus, core, fireplaces, terrace,

seating, dining, decor and cliff positions.

  • The architecture: floor, glass, roof, core, back wall, column and planters.
  • The materials: plaster, boucle, linen, knit, travertine, ceramic, bronze and limestone.
  • The render pipeline: the ultra path with a normal and velocity pre-pass, ground-truth ambient

occlusion (GTAO), temporal resolution anti-aliasing (TRAA) and sharpening; the high path with multi-render-target (MRT) geometry, post ambient occlusion, temporal anti-aliasing upscaling (TAAU) and dynamic resolution.

  • The outside: panorama loading, sun measurement, halo reconstruction, procedural open sea,

islands and fog banks.

  • The light: a directional sun with virtual shadow maps (VSM), a hemisphere fill, a light probe

grid with two bounces, baked atlas files and atlas blending during view changes.

  • The physical scene: signed distance field (SDF) assets built in Python, loaded as GLB, with

baked vertex ambient occlusion and a detail render layer.

  • The views: six panorama sets, per-view grade, sun, exposure, cove and fill; the 2.8 second

crossfade.

  • The cameras and controls: drag, wheel, keyboard, eight shots, a guided tour and a capture

application programming interface (API).

  • The tools: headless capture, GI bake, profiling, colour sampling, tonal tracing, reference

comparison, film render, merge, finish and encode.

  • The film: an offline 4K path defined by scripts; the film and its music are not in the repository.

It does not run casa-ocaso. It does not start Vite, open a browser, render a pixel, bake a probe, build a model or play the film. All runtime numbers come from the project documents and are marked as not verified.

  1. How does the backdrop shader turn six cube faces into a panorama, restore the clipped sun, and

  1. How does the room receive bounce light: probe grid, two bounces, baked atlas, blend and

interior reflection probe?

  1. How do the materials match the reference images: palette, relief, fabric lighting, limestone

and the travertine floor?

  1. How is stone, fabric and furniture geometry built offline as signed distance fields and loaded

with baked ambient occlusion?

  1. How does the furniture assembly isolate a failed module, and how does the detail layer save

probe and reflection cost?

  1. How does a view change blend the panorama, the sun, the grade and the light probe data?
  2. How do the camera, the shots, the tour and the capture API share one scene?
  3. How do the tools measure a render against a reference and produce the film?
  4. What does the project state it cannot do, and where does the static reading stop?

9. Limits

  • Static reading only. No pixel was rendered and no frame was viewed.
  • The reference images are not in the repository. Only docs/shot_ref1.jpg is available; the

other reference images are absent, so no visual match is checked here.

  • The film is absent. The video/ directory in the project README is not tracked.
  • No browser was opened. WebGPU behaviour, shader compilation and timings are not verified.
  • The light probe atlas, cube faces, HDR files, GLB models and texture maps were not decoded.
  • The asset, bake and film tools were not run. Their outputs are not checked.
  • The build process is a project statement. It is not reproducible here.
  • The capture tools select a Windows graphics path and use PowerShell wrappers. The checkout was

read on macOS, so the tools do not match this machine.

10. Corrections and limits found during research

The inventory matched: pin fcc3379, 193 tracked files, version 1.0.0, code MIT. The following findings qualify the first reading.

  1. The film is not in the repository. README.md:73-82 describes a 45 second flythrough in

video/ and four film scripts. git ls-files holds no video/ directory and no .mp4 file. The scripts define the path. The output does not ship.

  1. The reference images are not in the repository. README.md:68-69 tells a reader to put

refs/ref1.png to refs/ref5.png in place. The repository holds only docs/shot_ref1.jpg, docs/hero.jpg and docs/detail_table.jpg. The project states that the originals are not part of the repository (README.md:69).

  1. The capture tools target a Windows graphics path. tools/shoot.mjs and

tools/bake_gi.mjs pass --use-angle=d3d11 to Chrome. tools/gpu.ps1 and tools/render_chunks.ps1 are PowerShell. tools/bake_gi.mjs launches Chrome headless with those arguments. The source does not define a macOS or Metal path.

  1. One diagnostic tool names a page that is not tracked. tools/gpuinfo.mjs navigates to

/tools-blank.html. No such file is tracked. The navigation is wrapped in a catch, so the tool continues and reads the adapter limits from the browser.

  1. The ?q option does not match the default. README.md:24 presents ?q=ultra as the

full-resolution path. src/main.js:53 sets the interactive default to high and the capture default to ultra. The query option can select ultra in a normal session, but it is not the default.

  1. Two tone map defaults exist. src/core/renderer.js:34 sets the renderer tone map to AgX.

src/main.js:56 passes ACES as the pipeline tone map unless ?tm= overrides it, and the pipeline disables the renderer's own output transform (renderer.js:87). The project README says ACES (README.md:49). The effective path is ACES unless the query changes it.

  1. The six panoramas are real, but one view is partly procedural. The beach view keeps the

photograph for sky and horizon and replaces the lower half with open sea rendered in src/world/backdrop.js. The README states this (README.md:24-29). The other five use the photograph.

  1. Each view ships 12 files. The six view folders hold six cube faces, two HDR environments,

one thumbnail, meta.json, gi.bin and gi.json. The view assets are 86 mebibytes of the 147 mebibyte public tree.

  1. The GI atlas depth is not the probe count. public/views/beach-sunrise/gi.json records

dims as [18,6,126], while the grid count in src/world/lighting.js:17 is [18,6,16]. The atlas is a packed GPU layout. The source does not state the packing formula, so this exploration does not derive it.

  1. There is no automated test suite. The quality tools are manual capture and comparison

scripts. The source has no test runner and no assertion set for the image.

  1. The music is not in the repository. README.md:90-91 names "The Great Sea" by Scott

Buckley under CC BY 4.0. The encode tool expects an audio file under .tools/, which is not tracked.

  1. The project records an artificial intelligence build process. README.md:3-4 states it.

The exploration records this as a project statement, not as verified work.
