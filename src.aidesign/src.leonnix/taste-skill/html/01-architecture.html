Architecture: how the skill is packaged

This document maps the package. It covers the folder layout, the SKILL.md contract, the 22 references, the 12 scripts, the asset kit, the library data, the three plugin manifests, and the install paths. Every count and every path comes from the checkout at pin f6b7657.

1. The repository at a glance

The repository has two roles. The folder skills/taste-skill/ is the product. The rest of the repository delivers that folder to an agent. The tracked file count is 1,663. Of these files, 1,631 are inside the skill folder (spec.md).

The skill folder is 39 MB on disk. The assets subfolder is 37 MB of that total. The size comes from binary files: photographs, fonts, and page models. The file count and the disk size measure different things.

2. The skill folder

The skill folder has five parts. Each part has a different load time.

PartLoad timeWhy
SKILL.mdAlways, at skill loadThe contract, the rules, the steps, and the checklist
references/On demand, when a step names oneThe detailed design knowledge
scripts/On demand, as a commandThe measuring and dealing tools
assets/Copied into the projectThe parts the page uses
library/Read by the start scriptThe palette and type data

The split keeps the context small. The model reads SKILL.md first. It reads only the reference that the current step names. For example, step 4 names cards.md and the recipe of each section identifier (skills/taste-skill/SKILL.md:213-215).

Aha: The package has a small always-loaded surface and a large on-demand surface. The design knowledge is large, but the model pays for it only when a step needs it.

The name is kebab-case and has no more than 64 characters. The description is non-empty and has no more than 1,024 characters. The test tests/frontmatter.mjs enforces both limits (tests/frontmatter.mjs:38-40).

This fallback chain matters because the skill supports five install paths (section 9).

The kit is checked by its own test. tests/kit-clean.mjs runs consistency.mjs and the layout check on every page that the kit ships as a model. It checks the hero demos, the starter page, and the in-page moments (tests/kit-clean.mjs:2-8).

# tests/kit-clean.mjs:2-8
// The kit must pass its own checks. scripts/gate.mjs will not let a build end while consistency.mjs reports a FAIL or
// assets/layout/check.mjs reports any finding, so every page the kit ships as a model (the hero demos, the starter and
// the moments in a page) is checked the way the gate checks a builder's page: node
// skills/taste-skill/scripts/consistency.mjs --quick --widths 1440,390 --json, then node
// skills/taste-skill/assets/layout/check.mjs --sizes 1440x900,390x844 --json, one page at a time, each in its own
// headless Chrome (each script starts it with its own profile and stops it by its PID). It prints the FAIL ids of each
// page (a layout finding as "layout <rule>") and exits 1 when any page has one, 2 when a page could not be checked.

This test is the strongest statement of quality in the package. The kit must pass the same gate that a client page must pass.

7. The library data

The library/ folder holds two JavaScript Object Notation (JSON) files. They are the only data that the start script reads.

FileEntriesContent
library/palettes.json64Palette sets, with trade groups
library/type.json39Face, weight, tracking, and size pairings

A palette has a ground, an ink colour, an accent, a surface, and a muted colour. The start script prints a :root block from the chosen palette. A type pairing has a display face and a text face. It also has the weights, the tracking, and the sizes. start.mjs states that type.json is "the one source of every face, weight, tracking and size" (skills/taste-skill/scripts/start.mjs:4).

The photograph library is separate. It lives in assets/photos/photos.json and has 413 entries in 16 trade groups (assets/photos/photos.json). Each entry has a source, a licence, a credit line, and a set of usable slots. The library is data, not code.

The deal history is not in the library. It lives in the project at .taste-skill/history.json (skills/taste-skill/SKILL.md:202). A shared recent file can be set with the environment variable TASTE_SKILL_RECENT (skills/taste-skill/scripts/start.mjs:17-18).

9. The install paths

The skill supports five install paths. The first four are commands. The fifth is a manual copy.

Clone and link./install.shA symlink into ~/.claude/skills

The Skills CLI install is the simplest. The README gives the exact command (README.md:81). It installs under the skill name design-taste-frontend.

The Claude Code plugin install is a marketplace install. The plugin name is taste-skill, and the skill is namespaced under taste-skill: (README.md:91-96). The namespace prevents a collision with another skill.

The Codex install uses the Codex plugin commands (README.md:106-107). A new session is needed after the install.

The clone and link path uses install.sh. The script reads the install name from the front matter of each SKILL.md. It creates a symlink in the target skill directory (install.sh:70-77).

# install.sh:8-13
#   ./install.sh                          # link all skills into Claude Code
#   ./install.sh --codex                  # ... into Codex instead
#   ./install.sh --all-agents             # ... into both
#   ./install.sh design-taste-frontend    # link only these (by install name)
#   ./install.sh --list                   # show install name -> folder
#   ./install.sh --uninstall              # remove links pointing at this repo

The default target is ~/.claude/skills. The --codex flag changes the target to ~/.codex/skills. The --all-agents flag installs into both (install.sh:38-40). The script removes only links that point into this repository. It leaves a copied folder in place and prints a warning (install.sh:106-120).

On Windows, ln -s can copy a folder instead of linking it. The script asks for a real symbolic link first. It falls back to a directory junction when a symbolic link is not allowed (install.sh:19-27, install.sh:85-94).

Aha: The install script does not copy the skill. It links the working tree. A git pull then updates every installed skill in place (install.sh:4-6). This design makes the checkout the single source of truth.

10. The tests and continuous integration

The tests/ folder holds three tests. Each test guards one property of the package.

TestGuards
frontmatter.mjsEvery SKILL.md front matter parses, and the name and description obey the limits
kit-clean.mjsEvery kit page passes the checker and the layout check
text-encoding.mjsText files are clean UTF-8 with no double encoding

The front matter test exists because a strict YAML parser can drop a skill without an error. The header of the test states that an unquoted word: word in a description is enough to fail (tests/frontmatter.mjs:2-4).

# tests/frontmatter.mjs:2-7
// Every skill must load in every agent. Claude Code and Codex read SKILL.md frontmatter with a strict
// YAML parser and silently drop a skill whose frontmatter fails to parse (an unquoted "word: word" in
// a description is enough), so this check parses each one the same way and fails loudly.
//
//   npm install --no-save --no-package-lock yaml@2.6.1   (once; CI does this)
//   node tests/frontmatter.mjs

The workflow .github/workflows/check-skills.yml runs on a push to main and on a pull request. It installs Node.js 22, installs the YAML package without saving it, and runs the front matter test and the text encoding test. It also runs node --check on every .mjs and .js file in scripts/ and assets/ (.github/workflows/check-skills.yml:16-32).

The workflow does not run kit-clean.mjs. That test needs a browser and takes one to three minutes per page (tests/kit-clean.mjs:18-19). It is a local or release-time test, not a continuous integration test.

11. State files and their location

The runtime writes small files into the project under .taste-skill/. They are separate from the skill folder. The skill itself stays read-only. The build.json file is the marker: the gate treats a build as active while that file exists.

The gate writes the checker crops under .taste-skill/gate/consistency/ (skills/taste-skill/scripts/gate.mjs:856). The dealer histories are separate from the gate state. The dealers write history.json, layout-history.json, effects-history.json, bg-history.json, and scenes-history.json under .taste-skill/ (skills/taste-skill/SKILL.md:199-203, skills/taste-skill/references/layout-v4.md:144, skills/taste-skill/references/effects-usage.md:91, skills/taste-skill/references/backgrounds.md:63, skills/taste-skill/references/scenes.md:21).

The file names are fixed. 02-core-mechanism.md explains how the gate state files change the verdict.

12. What the architecture does not define

The source does not define a server, a database, a user account, a build service, or a hosting target. The skill builds a static page or a static export. The checker serves the page on the loopback address and reads it with headless Chrome. There is no cloud component.

The source does not define a version control policy for generated pages. It does define a version for the skill. The version is 2.5.1 in SKILL.md and in the three manifests (skills/taste-skill/SKILL.md:4, .codex-plugin/plugin.json:3).

The source does not define a licence for generated pages. The skill licence is MIT and covers the skill code (LICENSE:1). The photograph library has its own licences per entry (skills/taste-skill/references/photos.md).

The source does not define a limit on the page size. The performance reference defines budgets for transfer, images, scripts, requests, fonts, and rendering (skills/taste-skill/references/perf.md). Those budgets are checks, not hard platform limits.
