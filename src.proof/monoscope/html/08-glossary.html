4. The proof host

TermDefinitionSource
Review hostThe Haskell server process that owns the review state, the proof budget, and the comment.src/Data/Effectful/CodeReview.hs
ExecutorThe component that starts the virtual machine and runs the command. In Monoscope it is the guest session together with the sandbox bridge. Blacksmith does not document its executor.sandbox.mjs; Blacksmith overview
HostThe same Haskell server process when the sentence is about one proof run. The host prepares the workspace, calls the Node adapter, renders the media, and stores the rows.CodeReview.hs:672-691

LeaseA time-limited claim by one review run on one pull request review thread. lease_owner names the run and lease_until names the end time.ImpactReviews.hs:383; 0213_pr_impact_reviews.sql:19-20
Proof keyA name such as proof-1 that identifies one proof across both sides. The number is the count of distinct keys stored in the run plus one, so it is derived from visible rows, not from a separate sequence. A committed key is not reused in the same run because the count includes it. A rolled-back attempt stores no row, so a later attempt can derive the same key again. The host builds media links from the returned key after the transaction commits; this exploration found no path that publishes a media link before the commit. If a link were visible before the commit, the reuse could change the bytes behind it. That is an inference about publish order, not a test.Migration 0269; ImpactReviews.hs:630-631
Proof budgetThree proofs per agent attempt, enforced at two layers. The in-memory proofCount counts proof requests in one agent attempt, including a request that fails, and a resume restores it. The database count taken counts distinct proof keys stored for the attempt and stops a fourth store. A run can hold more than three keys across several attempts; each attempt has its own three.CodeReview.hs:61-63, 425, 462, 665-666; ImpactReviews.hs:630-632
ClaimA statement in the review with a status and zero or more proof keys.ImpactReview.hs:136-142
Claim statusOne of Matches, Differs, or Unverified. It compares the evidence with the claim, not the base recording with the head recording.ImpactReview.hs:136; Policy.hs:211
MatchesThe recorded evidence agrees with the claim. The claim cites proofs recorded on both sides, and each cited head proof has exit code 0. The validation does not require a base exit code of 0.ImpactReview.hs:308-316; Policy.hs:211
DiffersThe recorded evidence contradicts the claim in the pull request description. The claim cites proofs recorded on both sides. The validation does not require either exit code to be 0. This claim leads the comment.ImpactReview.hs:308-316, 860; Policy.hs:211
UnverifiedThe claim has no proof, or the proof does not settle it. Only Unverified may cite no proof.ImpactReview.hs:308-316
Progress commentThe same GitHub comment while the review runs. It shows planned claims and their state; the final review body replaces it in place. It is not a second comment.ImpactReview.hs:696-711, 956-972
Prove requestA manual comment command (@monoscope prove it) that asks for another review proof.ImpactReview.hs:950-951
Golden fileA stored expected output that a test compares with generated output. The golden test fails if the rendered comment changes.test/golden/impact-review/

The review states move as follows. A mode that skips drafts is a review configuration that does not start automatic reviews for a draft pull request. A retry is a new agent attempt that puts an Incomplete run back in the queue; it does not reuse the old attempt or its proof budget. A review thread is the pull request conversation that holds the review comment while it changes from progress to final.

A checkpoint has one record and two hashes. The checkpoint identity is the Identity record: project, repository, base, image build identifier, preparation secure hash, and dependency. The cache key identityKey hashes the whole record, so a new base is a new cache entry. The checkpoint lineage is a second hash over repository, image build identifier, preparation secure hash, and dependency. It omits the base and the project. A lineage pointer can therefore name an ancestor checkpoint from a different base. The restore path replaces .git from the baseline directory and resets the working tree, so the resumed disk can serve a different base than the one it was built on (AgentWorkspace.hs:1422-1428, 1469-1470, 1533-1534).
