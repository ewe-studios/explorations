12 -- Framework Core: Manifest, Bootstrap, Body Finalizers, and the Send Policy

The proa_framework_core crate is the runtime-agnostic half of the server adapter. It does not know about Axum, Hyper, or any specific HTTP server. It turns a compiled component into a FrameworkResponse whose body is either a fully buffered byte blob or a stream of Bytes. Along the way it reads an island manifest, resolves metadata from a route tree, appends the RSJS seed tables and the island bootstrap script, and decides whether a render future may migrate between executor threads. That last decision, the Send policy, is the crate's most important idea: the distinction between Send and non-Send render graphs is carried by Rust's type system, not by a runtime flag.

The Crate Contract

The crate doc (proa_framework_core/src/lib.rs:4) names the job in one sentence: framework-agnostic contracts shared by Proa server adapters. It has one feature, rt-tokio, on by default. That feature is forwarded to proa_stream for eager parallel preloads. The crate itself never references a runtime.

// proa_framework_core/src/lib.rs:12

Seven modules. The public surface re-exports the island bootstrap, the manifest types, the Markdown response, the metadata cascade, the response finalizers, the route snapshot, and the route spec. Two back-compat re-exports from proa_core (drive_dyn_render, drive_dyn_send_render, and the dyn erasure trait) keep older call sites compiling.

The Island Manifest

The manifest describes every interactive island the build produced. It is deserialized from a JSON file at startup. The root type is IslandManifest (proa_framework_core/src/manifest.rs:12).

// proa_framework_core/src/manifest.rs:12
pub struct IslandManifest {
    pub islands: HashMap<String, IslandEntry>,
    #[serde(default)]
    pub assets: ManifestAssets,
    #[serde(default)]
    pub import_map: HashMap<String, String>,
    /// Filename of the SSR IIFE bundle (e.g. "ssr-entry.js") relative to dist dir.
    #[serde(default)]
    pub ssr_bundle: Option<String>,
}

IslandEntry (manifest.rs:37) holds one island. It has module_path (where the compiled module lives), an optional named export, a strategy, a module_preloads list, a providers list, and an optional hydrate_fn. strategy is HydrationStrategyConfig (manifest.rs:52), a serde-tagged enum with five variants.

// proa_framework_core/src/manifest.rs:52
#[serde(tag = "type", rename_all = "snake_case")]
pub enum HydrationStrategyConfig {
    Immediate,
    Idle,
    Visible,
    Interaction { event: String },
    Media { query: String },
}

Immediate hydrates as soon as the script loads. Idle waits for the browser idle callback. Visible waits for intersection with the viewport. Interaction waits for an event such as click. Media waits for a media query such as (min-width: 768px). Each strategy maps one to one onto proa_react::HydrationStrategy in bootstrap.rs:88.

ProviderSpec (manifest.rs:61) is a provider module with an optional export and a JSON props value. Providers supply shared client state to an island. ManifestAssets (manifest.rs:24) carries at most one CssAsset, a path plus optional byte size.

Loading and Validating a Manifest

IslandManifest::load_from_path (manifest.rs:99) reads the file, parses JSON, and calls validate. validate (manifest.rs:123) walks every module_path, every preload, and every provider module. It exists to stop a manifest write from becoming an arbitrary-code-serve bug.

// proa_framework_core/src/manifest.rs:141
fn validate_module_path(island: &str, module_path: &str) -> Result<()> {
    if module_path.is_empty() {
        anyhow::bail!("island {island:?} has empty module_path");
    }
    if module_path.starts_with("//") {
        anyhow::bail!(
            "island {island:?} module_path {module_path:?} is protocol-relative; \
             use an absolute https:// URL or a server-relative /path"
        );
    }
    if module_path.starts_with('/') {
        return Ok(());
    }
    if module_path.starts_with("https://") || module_path.starts_with("http://") {
        return Ok(());
    }
    anyhow::bail!(
        "island {island:?} module_path {module_path:?} must be an absolute URL \
         (https://...) or a server-relative path (/...)"
    );
}

Four things are accepted: a server-relative path starting with /, an https:// URL, an http:// URL (for local dev rigs), or nothing is rejected. Three things are rejected: an empty string, a protocol-relative //host/x URL, and a bare relative path such as ../evil.js. Protocol-relative URLs resolve against the page origin's scheme, so they are a scheme-hijack vector. Relative paths resolve against the page origin too, which turns a manifest write into a path traversal.

with_base_path (manifest.rs:77) prefixes every application-local URL with the public mount path. It deliberately leaves external URLs and import-map keys alone. The doc comment warns that it must be called once, because reapplying it double-prefixes.

Island Bootstrap

Bootstrap is the piece of HTML that wires browser React to the island markers a component rendered. render_bootstrap_for_islands (proa_framework_core/src/bootstrap.rs:16) is the public entry. It delegates to render_bootstrap_for_islands_with_import_map (bootstrap.rs:25), which does four things in order.

// proa_framework_core/src/bootstrap.rs:32
let mut unique = BTreeSet::new();
let mut collected = Vec::new();

for name in islands {
    let owned = name.as_ref().to_string();
    if !unique.insert(owned.clone()) {
        continue;
    }
    let entry = manifest
        .resolve_entry(&owned)
        .with_context(|| format!("No island named '{}' in manifest", owned))?;
    collected.push((owned, entry));
}

First it dedupes island names through a BTreeSet, so an island rendered twice is bootstrapped once. Second it resolves each name to its IslandEntry, failing with No island named 'X' in manifest for an unknown island. Third it writes a for each unique preload URL. Fourth it writes the import map and calls react_bootstrap. The import map uses the manifest's own import_map when present, or render_react_import_map otherwise.

convert_entry (bootstrap.rs:79) builds a ReactModuleDescriptor from the island name, module path, export, and mapped strategy. The strategy mapping in map_strategy (bootstrap.rs:88) is a straight five-arm match.

The Metadata Cascade

Metadata (title, description, Open Graph) flows from parent layouts to child pages. The flow is a cascade, not a simple override. The core type is CascadeValue (proa_framework_core/src/metadata.rs:14).

// proa_framework_core/src/metadata.rs:14
pub enum CascadeValue<T> {
    Set(T),
    Tombstone,
    #[default]
    Unset,
}

Set(T) overrides the parent. Tombstone explicitly clears the field and refuses inheritance. Unset inherits the parent value. resolve (metadata.rs:25) maps these three to the final Option: Set yields Some, Tombstone yields None, Unset yields the parent.

The Metadata trait (metadata.rs:55) is implemented by page and layout metadata providers. It defaults everything to Unset. A provider can return a title, flag absolute_title, return a description, and return Open Graph. TitleOnly (metadata.rs:38) is the simplest provider: a &'static str title with no other fields.

Title Templates

A title such as "%s | Base" is a template. ComputedRouteMeta::cascade (metadata.rs:88) walks local providers in order. When a title contains %s, it is stored as the title template, not the title. When a later provider supplies a plain title like Page, the template's %s is replaced, producing Page | Base. If a provider sets absolute_title, it overrides the template entirely. Open Graph title and description use the same template rule, tracked in og_title_template and og_description_template.

The final pass (metadata.rs:219) fills a still-empty Open Graph title from the page title when a template and raw page title both exist. This is why a page that only sets a description template can still inherit a complete Open Graph title.

This is why a component can set a status, add <code>Link</code> preload headers, and append multiple <code>Set-Cookie</code> headers without the framework dropping them.</p> <h2>The Send Policy</h2> <p>This is the crate's centerpiece. A render stream may hold request-local, non-<code>Send</code> state. A server whose body API requires <code>Send</code> cannot poll that stream directly. Proa does not force every component future to be <code>Send</code>. It carries the distinction in the type system.</p> <pre><code class="language-rust">// proa_framework_core/src/response.rs:58 pub type FrameworkLocalStream = Pin<Box<dyn Stream<Item = Result<Bytes, FrameworkError>> + 'static>>; // proa_framework_core/src/response.rs:63 pub type FrameworkSendStream = Pin<Box<dyn Stream<Item = Result<Bytes, FrameworkError>> + Send + 'static>>; </code></pre> <p><code>FrameworkLocalStream</code> has no <code>Send</code> bound. <code>FrameworkSendStream</code> requires the complete active future graph to be <code>Send</code>. The factory enum <code>FrameworkStreamFactory</code> (<code>response.rs:77</code>) has two variants, <code>Send</code> and <code>Local</code>. The doc comment on <code>FrameworkStreamFactory</code> states the rule plainly: adapters poll <code>Send</code> streams directly and place <code>Local</code> streams on a pinned local executor. No runtime flag can upgrade a local stream into the direct path.</p> <p>The <code>Send</code>-capable render functions exist because <code>WebRenderSend</code> components carry a compiler-proof <code>Send</code> future. <code>render_send_stream_html_response</code> (<code>response.rs:1190</code>) produces a <code>FrameworkSendStream</code>. The non-<code>Send</code> <code>render_stream_html_response</code> (<code>response.rs:1141</code>) produces a <code>FrameworkLocalStream</code>. Both stream the same document structure. Only the type boundary differs.</p> <p>The test <code>send_stream_moves_between_threads_without_losing_request_state</code> (<code>response.rs:2483</code>) proves the <code>Send</code> path. It renders a page on one thread, moves the stream to a second thread, and asserts the request path survives. The local path, by contrast, is driven by a local executor that does not require the future to migrate.</p> <div class="mermaid"> flowchart LR C[Component render future] --> S{Compiler-proved Send?} S -- yes --> FS[FrameworkSendStream] S -- no --> FL[FrameworkLocalStream] FS --> D[Adapter polls directly on its executor] FL --> L[Adapter pins it on a local executor] D --> T[HTTP transport] L --> T </div> <h2>The Streaming Drivers</h2> <p>There are four driver types, one per combination of Send and ordering. <code>OutOfOrderStreamDriver</code> (<code>response.rs:1363</code>) and <code>SendOutOfOrderStreamDriver</code> (<code>response.rs:1536</code>) render the shell, then loop over boundary events from a <code>StreamContext</code>. Each finished boundary gets its seed fragments, its runtime plan delta, its bootstrap delta, and a <code><template></code> buffer, then a batch swap script. Timed-out boundaries are blanked and their fallback preserved. Failed boundaries are blanked with an error log, and the stream keeps going rather than aborting.</p> <p><code>InOrderStreamDriver</code> (<code>response.rs:1707</code>) and <code>SendInOrderStreamDriver</code> (<code>response.rs:1842</code>) use an unbounded mpsc channel and a <code>select</code> loop between the render future and the channel receiver. The comment at <code>response.rs:1741</code> explains why the channel is unbounded: the producer and consumer are sub-futures of the same task, so the flush method cannot <code>.await</code> channel capacity without deadlocking. Backpressure against slow clients is applied one level up by the bounded bridge channel in the Axum layer.</p> <p><code>FRAMEWORK_SINK_PAGE_SIZE</code> (<code>response.rs:1962</code>) is <code>4096</code>, the logical page size retained for tests. <code>ChannelSink</code> (<code>response.rs:1966</code>) implements both <code>StreamChunkFlusher</code> and <code>SendStreamChunkFlusher</code> by forwarding each flushed chunk to the channel. The test <code>channel_sink_coalesces_one_logical_render_buffer_flush</code> (<code>response.rs:2543</code>) verifies a 9000-byte buffer flushes as one chunk.</p> <h2>The Markdown Response</h2> <p><code>MarkdownResponse<L></code> (<code>proa_framework_core/src/markdown.rs:64</code>) is the buffered Markdown analogue of <code>RouteResponse</code>. It wraps a <code>DynMdRender<L></code> box and a loader. The unopened plan is <code>Send</code>, even though its active finalization future is local, which is why a <code>Send</code> handler can return it and let the HTTP adapter drive finalization.</p> <p><code>finalize</code> (<code>markdown.rs:79</code>) installs the same request context HTML uses, drives the render, and calls <code>finish_markdown</code>. <code>finish_markdown</code> (<code>markdown.rs:101</code>) sets <code>Content-Type: text/markdown; charset=utf-8</code>, sets <code>Content-Length</code>, and chooses <code>FrameworkBody::Full</code> when the output is one page or <code>FrameworkBody::BufferedPages</code> when it spans pages. <code>render_sync_markdown_response</code> (<code>markdown.rs:91</code>) is the sync entry for <code>MdRenderSync</code> roots.</p> <h2>The Aha Moment</h2> <p><strong>Aha:</strong> The framework never asks whether a render future is <code>Send</code>. The answer is written into the type before the handler runs, and the type picks the executor.</p> <p>This is not a runtime capability flag. <code>RoutePlan::Async</code> and <code>RoutePlan::SendAsync</code> are distinct variants. <code>FrameworkStreamFactory::Send</code> and <code>FrameworkStreamFactory::Local</code> are distinct variants. A component that implements <code>WebRender</code> produces a local future and lands on the local path. A component that implements <code>WebRenderSend</code> produces a compiler-proved <code>Send</code> future and lands on the direct path. No code can promote the former to the latter.</p> <p>The benefit is portability without a universal <code>Send</code> tax. Server adapters that can poll local futures do not force every component to box and prove <code>Send</code>. Adapters that require <code>Send</code> use the <code>WebRenderSend</code> trait for the components that can support it. The local stream's doc comment (<code>response.rs:46</code>) says it directly: treat the local-only factory as an adapter limitation, not a reason to impose <code>Send</code> on all component futures.</p> <h2>Cross-References</h2> <ul><li>The render traits this plan dispatches on: <a href="./02-render-traits.html">02-render-traits.md</a>.</li><li>The <code>RenderMode</code> values that map to <code>AsyncDelivery</code>: <a href="./03-web-context.html">03-web-context.md</a>.</li><li>The streaming substrate the drivers wrap (<code>Suspense</code>, boundary drivers, page pool): <a href="./10-streaming.html">10-streaming.md</a>.</li><li>The <code>LoadKey</code> and <code>LoadRequest</code> types used for preloads: <a href="./09-data-loading.html">09-data-loading.md</a>.</li><li>The RSJS seed tables and runtime plan this crate appends: <a href="./17-rsjs-overview.html">17-rsjs-overview.md</a>.</li><li>The Axum adapter that consumes <code>FrameworkResponse</code> and applies the local executor: <a href="./13-framework-axum.html">13-framework-axum.md</a>.</li></ul> <p>Continue to <a href="./13-framework-axum.html">13-framework-axum.md</a>.</p> </article> <script>function toggleTheme(){var c=document.documentElement.getAttribute('data-theme'),n=c==='dark'?'light':'dark';document.documentElement.setAttribute('data-theme',n);localStorage.setItem('theme',n);}</script> </body> </html>
