22 -- Docs: Compile Markdown and MDX to a Static Rendering Registry

Proa's docs are the same shape as the framework they document: do every expensive step once, at build time, so the request path is a single zero-copy render. The build crate proa_docs_build walks a directory of Markdown/MDX, lowers MDX component tags to static HTML, syntax-highlights code with Syntect, validates links, and serializes a search index -- then emits one docs.generated.rs whose article HTML, source Markdown, and search JSON are all include_str!ed into the binary. The runtime crate proa_docs owns nothing but a &'static-only data model (Docs, DocPage, NavItem -- no String, no Vec, no Box anywhere) and renders the navigation shell around pre-baked article HTML. At request time there is no Markdown to parse, no code to highlight, no JSON to read from disk: render_with_base_path matches the path, hands the right DocPage to DocsShell, and streams the finished document through the same WebRenderSync trait every component in the framework uses.

The Two Crates

CrateLinesRole
`proa_docs_build`~8,100build-time compiler: Markdown/MDX, components, highlight, search, link check, Rust emit
`proa_docs`~1,900runtime: `&'static` data model, `DocsShell` renderer, assets, axum adapter

Only proa_docs is a dependency of application code, and it is pulled into a build only through include_docs! and its own tiny dependency set (proa_core, proa_macros, serde_json, sha2, base16ct, plus optional axum/http). proa_docs_build carries the heavy lifters -- pulldown-cmark (Markdown), syntect (highlighting), latex2mathml (math), thiserror, serde/serde_json, sha2, base16ct -- and never runs in the serving binary. The dependency direction is the same discipline as the fonts pipeline: the compiler is the only process that does real work, and the runtime is a thin, infallible renderer over data the compiler already made correct.

Part 1 -- The Runtime Data Model Is Zero-Copy

Docs, DocPage, Frontmatter

The entire runtime model is &'static references and Copy structs. Docs is the root aggregate; a page is a DocPage whose body is one pre-rendered HTML string and whose table of contents is a static slice of TocItems:

// proa_docs/proa_docs/src/model.rs (abbreviated)
pub struct Docs {
    pub config: DocsConfig,                 // base_path, site_name
    pub nav_title: &'static str,
    pub nav_icon: Option<&'static str>,
    pub pages: &'static [DocPage],
    pub nav: &'static [NavItem],
    pub search: Option<SearchArtifacts>,
}

pub struct DocPage {
    pub slug: &'static str,
    pub route_path: &'static str,
    pub markdown_path: &'static str,
    pub title: &'static str,
    pub description: Option<&'static str>,
    pub frontmatter: &'static Frontmatter,
    pub article_html: &'static str,   // the compiled body
    pub markdown: &'static str,       // the raw source, served at markdown_path
    pub toc: &'static [TocItem],
    pub prev: Option<PageLink>,       // nearest non-hidden predecessor
    pub next: Option<PageLink>,       // nearest non-hidden successor
}

pub struct Frontmatter {
    pub title: Option<&'static str>,
    pub description: Option<&'static str>,
    pub icon: Option<&'static str>,
    pub slug: Option<&'static str>,
    pub sidebar_title: Option<&'static str>,
    pub nav_order: Option<i32>,
    pub hidden: bool,
    pub draft: bool,
    pub search: Option<bool>,
    pub toc: Option<bool>,
    pub last_modified: Option<&'static str>,
}

Frontmatter is eleven fields: five display/slug strings, nav_order for explicit ordering, hidden/draft toggles, search/toc overrides, and last_modified. Docs::find_page and Docs::page_for_path normalize a slug through path_to_slug (strip the base path, a trailing index.html, and .html/.md suffixes) and binary-search-free .iter().find(...) over pages.

Navigation Is a Static Tree

NavItem is recursive and every kind is one of four NavItemKind variants -- Page, Group, Root, Separator -- with as_str() emitting "page"/"group"/"root"/"separator" for the data-nav-kind attribute:

// proa_docs/proa_docs/src/model.rs (abbreviated)
pub struct NavItem {
    pub kind: NavItemKind,
    pub title: &'static str,
    pub icon: Option<&'static str>,
    pub path: Option<&'static str>,
    pub children: &'static [NavItem],
}

pub enum NavItemKind { Page, Group, Root, Separator }

A Root item is a top-level content section; has_nav_roots drives whether the sidebar shows a section switcher, and active_nav_root(path) walks the tree to find the Root whose subtree contains the current page so the sidebar can swap between sections.

include_docs! Pulls the Registry Into the Binary

The generated registry is pulled in by a macro, not a module path the author hand-writes. The compiler emits docs.generated.rs into OUT_DIR, and the app opts in with one literal -- the source output directory name:

// proa_docs/proa_docs/src/lib.rs (verbatim)
#[macro_export]
macro_rules! include_docs {
    ($name:literal) => {
        include!(concat!(
            env!("OUT_DIR"),
            "/proa_docs/",
            $name,
            "/docs.generated.rs"
        ))
    };
}

include_docs!("docs") expands to include!(concat!(env!("OUT_DIR"), "/proa_docs/docs/docs.generated.rs")), so the generated proa_docs::Docs { ... } value is compiled into the crate as an ordinary static. This is the single seam between the build crate and the runtime crate: the compiler's only obligation is to produce a valid proa_docs::Docs expression at exactly that path.

Part 2 -- The Build Compiler

Configuration Is a Builder, Not a File

There is no config file format in proa_docs_build. Config is a Rust builder aggregate of DocsSources, CollectionSources, and Plugins, threaded through build.rs. DocsSource carries the per-site settings with these defaults:

// proa_docs/proa_docs_build/src/config.rs (defaults, abbreviated)
// DocsSource::new(root) defaults:
//   out_dir_name: "docs"      base_path: "/docs"      site_name: "Docs"
//   schema: PageSchema::default()                     meta_schema: MetaSchema::default()
//   postprocess: Postprocess::default()               markdown: MarkdownPipeline::default()
//   search: SearchConfig::orama_client()              link_validation: LinkValidation::default() // Warn
//   include_drafts: false

base_path is normalized to always start and not end with / (empty and "/" both become "/"). The MarkdownPipeline bundles six sub-configs: CodeHighlight (Syntect, hl-* classes, no theme), MathMode (Disabled | MathMl), ComponentIndexing, MermaidConfig (off by default), MdxConfig (a pile of normalization flags), and TypeScriptDocgen. MdxConfig::proa() is the opinionated preset: it turns on remove_layout_divs, lower_paragraph_tags, cards, files, agent_terminal, and image prefix rewriting (/images/ → /static/images/). SearchConfig is Disabled | OramaClient | StaticClient | Server | Custom(String); LinkValidation defaults to Warn mode with internal-route and hash checks on and external checks off, and strict() flips it to Error.

The Compile Pipeline

The real entry point is try_compile_to, which try_compile calls after requiring an OUT_DIR:

// proa_docs/proa_docs_build/src/compiler.rs (pipeline, abbreviated)
pub fn try_compile_to(config: Config, out_dir: &Path) -> Result<(), CompileError> {
    // 1. touch every collection and plugin (currently no-ops)
    // 2. if any source wants highlighting, build HighlightCache at out_dir/.proa-docs-highlight-cache
    // 3. for each source: compile_source(source, cache, out_dir.join("proa_docs").join(source.out_dir_name))
}

compile_source is where the per-site work happens:

flowchart TD SRC["source dir: *.md / *.mdx"] --> MDX["mdx::lower_mdx (line preprocessor)"] MDX --> FM["frontmatter::split_frontmatter + validate_schema"] FM --> MR["markdown::render_markdown (pulldown-cmark)"] MR --> COMP["components: Tag enum + render_tag"] MR --> SYN["syntax_highlight::highlight_lines (syntect)"] COMP --> HTML["article_html"] SYN --> HTML HTML --> PAGE["CompiledPage { slug, route_path, title, toc, hashes, search_text }"] PAGE --> SEARCH["search::build_search_json -> manifest.json + documents.json"] PAGE --> LINK["link_validation::validate_references (Warn or Error)"] PAGE --> EMIT["rust_emit::emit_docs -> docs.generated.rs"] SEARCH --> EMIT LINK --> EMIT EMIT --> INCLUDE["include_docs!(out_dir_name) in the app"]

Model building has two branches. If the source root has a meta.json, compile_folder_nav builds the navigation and page list from it, then append_unlisted_pages compiles any discovered Markdown files not already named. Otherwise collect_markdown_files finds every .md/.mdx, compiles each, and sorts pages by nav_order then slug; the nav is then just the non-hidden pages. meta.json is a Meta { title, icon, root, pages } whose pages are untagged MetaEntrys: a string (Item), a { "separator": "...", "icon": "..." } object, or a Group { title, pages } -- so navigation order, grouping, separators, and top-level roots are all authored in one file.

Per page, compile_page_rel runs a fixed sequence: read the file, lower MDX if the extension is .mdx and MDX is enabled, split and validate frontmatter, resolve it (skipping draft pages unless include_drafts), derive the slug from frontmatter or the relative path, compute route_path and markdown_path, render the Markdown, infer a title/description when frontmatter leaves them empty, and emit pages/{slug}.html plus pages/{slug}.md fragments. The result is a CompiledPage carrying slug, route_path, markdown_path, title, description, sidebar_title, the resolved frontmatter, article_html, markdown, toc, hashes, search_text, and the two include paths. The slug of the index file is the empty string, so route_path collapses to the base path and markdown_path becomes {base}/index.md.

Compile-time failures are a nine-variant CompileError (thiserror): Io, MissingOutDir, Frontmatter, Metadata, MdxLowering, SearchJson, LinkValidation(usize) (the number of broken links when mode is Error), TypeScriptDocgenMissing(usize) (type-table requests with no configured TS command), and UnknownNavIcon(String). Most component problems are not hard errors -- they surface as cargo:warning=docs components: diagnostics and the compiler proceeds with the offending block dropped or escaped.

Part 3 -- Markdown, MDX, Frontmatter

Markdown Is a Hand-Rolled Event Writer

render_markdown parses with pulldown-cmark and writes a flat HTML String directly from the event stream -- there is no intermediate IR:

// proa_docs/proa_docs_build/src/markdown.rs (abbreviated)
// Parser::new_ext(markdown, Options::ENABLE_TABLES | ENABLE_STRIKETHROUGH | ENABLE_TASKLISTS
//   | if pipeline.math.is_enabled() { Options::ENABLE_MATH } else { Options::empty() })
pub struct RenderedMarkdown {
    pub html: String,
    pub toc: Vec<TocEntry>,          // depth, id, title
    pub hashes: Vec<String>,         // every heading id, for link validation
    pub search_text: String,
    pub links: Vec<LinkReference>,   // every href, for link validation
    pub type_table_requests: Vec<TypeTableRequest>,
}

Heading ids are slugifyed -- lowercase ASCII alphanumerics kept, every other run collapsed to one -, empty becomes "section" -- and deduplicated with -2, -3, ... suffixes. Every heading id is pushed to hashes, but only headings deeper than H1 are pushed to the TOC, so the on-page menu starts at h2. Links record their href for later validation and pass the destination through safe_url, which lowercases the scheme and blanks javascript:/vbscript:; images take their alt text from the image title field. Task-list markers become .

The one custom syntax layered on CommonMark is TeX math: $...$/$$...$$ are compiled to MathML at build time with latex2mathml::latex_to_mathml (+ DisplayStyle for display math), re-escaped by normalize_mathml, and fall back to escaped source with a cargo:warning=docs math: when the conversion fails.

MDX Is a Line Preprocessor That Lowers Markdown to Markdown

mdx::lower_mdx is not a JSX parser and never evaluates expressions. It is a line-oriented transform that returns the input unchanged when config.enabled is false, and otherwise rewrites a fixed set of constructs. Line-oriented components become plain Markdown:

// proa_docs/proa_docs_build/src/mdx.rs (lowerings, abbreviated)
// <Cards> <Card title href description/> </Cards>      -> "- [title](href): description"
// <Files> <Folder name/> <File name/> </Files>         -> a ```proa-filetree fence
// <AgentTerminal/>                                     -> a ```text fence
// <img src alt/>                                       -> ![alt](src) after prefix_rewrites
// <p>...<strong/>...<code/>...</p>                     -> **...** and `...`

Container components (Callout, Tabs, Steps, CodeExplorer, Accordions, Demo) are deliberately not lowered: end_block forces each tag onto its own block with a trailing blank line so pulldown-cmark parses the Markdown between open and close tags as ordinary children instead of swallowing it into an HTML block. The brace grammar is narrowed to four special cases -- {'{'}/{'}'} escapes, {/ ... /} comment stripping, items={['a','b']} → data-items="a|b", and style={{...}} → style="kebab: value" -- while any other {expr} passes through as literal text. Hard lowering errors are only "unsupported MDX export statement", "unclosed block", "unclosed block", and "unclosed fenced code block".

Frontmatter Is Hand-Parsed Simple YAML

split_frontmatter requires the document to start with ---\n, scans for the closing \n---, and parses key: value lines by hand (no serde_yaml). parse_scalar maps true/false to Bool, an integer to Number(i64), and a matching "..."/'...' pair to String, so a flow list like [a, b] stays a single string that get_string_list later splits on commas. ParsedFrontmatter is a BTreeMap with no hardcoded keys; the concrete keys (title, description, icon, slug, sidebar_title, nav_order, hidden, draft, search, toc, last_modified, keywords) are resolved into ResolvedFrontmatter in compiler.rs. An optional PageSchema/MetaSchema enforces required-ness and scalar type per key, with messages like missing required frontmatter field title` and frontmatter field nav_order must be a boolean`.

Part 4 -- The Component System

Dispatch Is a Tag Enum, Not a Registry

There is no trait, macro, or runtime name registry for components. Dispatch is two plain stages: a Tag enum whose parse string-matches the exact tag text, and a match tag { ... } in render_tag that routes each variant to its renderer, appending raw HTML to a &mut String:

// proa_docs/proa_docs_build/src/components/tag.rs (variants, abbreviated)
pub enum Tag {
    TabsOpen(Vec<String>), TabsClose, TabOpen(Option<String>), TabClose,
    ExplorerOpen, ExplorerClose, CodeFileOpen(String), CodeFileClose,
    AccordionsOpen { exclusive: bool }, AccordionsClose, AccordionOpen { title: String, id: Option<String> }, AccordionClose,
    StepsOpen, StepsClose, StepOpen, StepClose,
    CalloutOpen { kind: CalloutKind, emoji: Option<String> }, CalloutClose,
    Demo(Demo),
}

open_tag_body requires the name to be followed by whitespace, /, or > so never matches . Container components keep their children as Markdown (parsed by the normal event loop and appended into the same buffer), while three line-oriented components -- Cards, Files, AgentTerminal -- are consumed earlier in lower_mdx and re-emitted as Markdown. CodeBlock (fenced code) and TypeTable (deferred docgen) are handled directly in markdown.rs. ComponentState tracks the open container, the tab/explorer group counters, and per-page diagnostics.
