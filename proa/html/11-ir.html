11 -- The IR: Expressions, Statements, Reactive Bindings, and Codegen

The proa_ir crate is one typed tree with a split brain. The same Expr tree runs two ways. On the server it is interpreted against a data scope. On the client it is compiled to JavaScript. The two paths must agree, so the server evaluator reimplements ECMAScript coercion and rounding semantics exactly. This document covers every layer: identifiers, values, expressions, statements, triggers, reactive attributes, forms, validation, the builder API, the three code generators, and the server evaluator.

The Layer Contract

The crate doc (proa_ir/src/lib.rs:4) states the design goals in four words. The IR must be complete, type-safe, optimizable, and portable. It builds up in layers.

// proa_ir/src/lib.rs:19
// - Types: Basic identifiers (SignalId, FieldId, Selector, etc.)
// - Values: Literal values that can appear in the IR
// - Expressions: Pure computations that produce values
// - Statements: Side effects (state updates, DOM operations, fetches)
// - Triggers: Events that cause effects to run

Expressions are pure. Statements have side effects. Triggers schedule effects. This split is enforced by the types themselves. Expr has no assignment node. Stmt has no value result. A handler is a Block of Stmt run under a Trigger.

The crate is #![forbid(unsafe_code)]. Expr and Value are Serialize + Deserialize, so a runtime-template compiler can store a compiled program as data. The server evaluation section covers how those stored programs run.

IrStr and the Identifier Types

IrStr (proa_ir/src/types.rs:18) is the string type for identifiers, property keys, and string literals.

// proa_ir/src/types.rs:18
pub type IrStr = Cow<'static, str>;

Compile-time construction borrows a &'static str. Deserialized programs own their strings. Every identifier is a newtype over IrStr. SignalId, FieldId, VarId, and Selector each have a const fn new(&'static str) that borrows, an owned(impl Into) for runtime strings, and as_str. The const constructors keep the macro and builder paths allocation-free.

The small enums live here too. Method (types.rs:99) has Get, Post, Put, Patch, Delete, serialized UPPERCASE. ToastLevel (types.rs:111) has Info, Success, Warning, Error, serialized lowercase. ContentType (types.rs:122) and ResponseType (types.rs:133) cover fetch options.

Value

Value (proa_ir/src/value.rs:23) is the literal data type. It has seven variants.

// proa_ir/src/value.rs:23
#[serde(untagged)]
pub enum Value {
    Null,
    Bool(bool),
    Int(i64),
    Float(f64),
    String(IrStr),
    Array(Vec<Value>),
    Object(#[serde(with = "object_entries")] Vec<(IrStr, Value)>),
}

Int and Float are one observable "JS number" type. Int exists only so authoring and serialization stay exact for integer data. Object keeps insertion order as a Vec of pairs. Duplicate keys follow JS object-literal semantics: the last entry wins on access. The object_entries serializer (value.rs:42) writes objects as JSON maps, not arrays of pairs, so serialized values look like and round-trip as JS objects.

Constructors are const fn: null, bool, int, float, string. object is the non-const constructor. From impls cover bool, i32, i64, f64, &'static str, String, Vec, and Option where T: Into.

Expr

Expr (proa_ir/src/expr.rs:16) is the expression language. It has 85 variants across nine families: primitives, property access, arithmetic, comparison, logic, strings, construction and arrays, type checks and conversion, and math. A few representative groups show the shape.

// proa_ir/src/expr.rs:16
#[serde(tag = "type", rename_all = "snake_case")]
pub enum Expr {
    Lit { value: Value },
    Signal { id: SignalId },
    Field { id: FieldId },
    Var { id: VarId },
    Scope { path: Vec<IrStr> },
    Response,
    Error,
    Event,
    Target,
    // ...
    Prop { expr: Box<Expr>, prop: IrStr },
    Index { expr: Box<Expr>, index: Box<Expr> },
    // ...
    FormatNumber { value: Box<Expr>, decimals: u8 },
    // ...
    CardType { expr: Box<Expr> },
}

The Scope variant is the server data root. Its path walks nested objects from the render scope. Missing segments resolve to Null. Signal, Field, Response, Error, Event, and Target are client-only roots. The FormatNumber variant is the money workhorse. Its doc example is Concat["$", FormatNumber(total_cents / 100, 2)].

The tree exposes a for_each_child walker (expr.rs:403). The match is exhaustive with no wildcard arm. Adding an Expr variant is a compile error until the walker learns its children. Consumers that need the whole subtree drive this with an explicit worklist, which keeps the walk allocation-bounded and immune to stack overflow on hostile deeply nested expressions.

Convenience constructors mirror the builder. Expr::lit, signal, field, var, scope, scope_path, response, error, prop, index, and the arithmetic, comparison, logic, and string operators all exist. From let literals coerce into Expr.

Reactive Attributes

Binding (proa_ir/src/reactive.rs:15) is the client computation model. It has seven variants.

// proa_ir/src/reactive.rs:15
pub enum Binding {
    Static,
    FormState { key: &'static str },
    FieldState { field: &'static str, key: &'static str },
    Not { inner: Box<Binding> },
    And { left: Box<Binding>, right: Box<Binding> },
    Or { left: Box<Binding>, right: Box<Binding> },
    Map { inner: Box<Binding>, expr: &'static str },
}

ReactiveAttr (reactive.rs:86) holds a default value and a binding. SSR outputs the default. If the binding is not Static, JS is generated to update the attribute. static_value, form_state, and field_state construct the three base cases. map_binding wraps a binding in a JavaScript expression where $ is the value.

The Not, BitAnd, and BitOr impls for ReactiveAttr are the clever part. They short-circuit at compile time.

// proa_ir/src/reactive.rs:161
impl BitAnd for ReactiveAttr<bool> {
    fn bitand(self, rhs: Self) -> Self::Output {
        ReactiveAttr {
            default: self.default && rhs.default,
            binding: match (&self.binding, &rhs.binding) {
                (Binding::Static, Binding::Static) => Binding::Static,
                (Binding::Static, _) if !self.default => Binding::Static, // false && x = false
                (_, Binding::Static) if !rhs.default => Binding::Static,  // x && false = false
                (Binding::Static, _) if self.default => rhs.binding,      // true && x = x
                (_, Binding::Static) if rhs.default => self.binding,      // x && true = x
                _ => self.binding.and(rhs.binding),
            },
        }
    }
}

true && x becomes just x. false && x becomes Static. BitOr does the dual. negated eliminates double negation, so !!is_valid returns the original FormState binding. These optimizations mean a disabled button written as is_submitting | !is_valid serializes to the smallest possible client binding, not a tree of boolean nodes.

ReactiveClass (reactive.rs:200) is the reactive string form. It has a base class plus a list of (condition, class_if_true, class_if_false) triples. default_class computes the SSR string.

Server Evaluation

eval (proa_ir/src/eval/mod.rs) interprets the server dialect of Expr against a ScopeStack and produces a Value. The module doc states the contract directly. The same IR compiles to JS for the client, so evaluation semantics are pinned to the JS emitters: f64 arithmetic and coercion, strict === comparison, UTF-16 string lengths, and JS method semantics.

ScopeStack (eval/mod.rs:42) is the data environment. It has a root value plus a stack of named bindings pushed for loop variables.

// proa_ir/src/eval/mod.rs:42
pub struct ScopeStack<'a> {
    root: &'a Value,
    vars: Vec<(IrStr, Value)>,
}

push_var and pop_var manage bindings. var looks up innermost-first. The interpreter pushes a binding for each ForEach style loop body and pops it after.

EvalBudget (eval/mod.rs:83) bounds evaluation. The defaults are DEFAULT_MAX_DEPTH = 64 (eval/mod.rs:91) and DEFAULT_MAX_ITERATIONS = 10_000 (eval/mod.rs:93). eval uses the default budget. eval_with_budget takes an explicit one.

EvalError (eval/mod.rs:107) has nine variants: DepthLimit, IterationLimit, UnknownVar, TypeMismatch, CompositeComparison, ClientOnly, Unsupported, InvalidRegex, and InvalidDecimals. Evaluation never panics. Malformed or over-budget input surfaces here.

The dispatcher is split into per-category handlers for a deliberate reason. The comment at eval/mod.rs:420 explains it.

// proa_ir/src/eval/mod.rs:420
// The evaluator is split into per-category handlers rather than one giant
// match: debug builds do not reuse stack slots across match arms, so a
// single ~85-arm function makes each recursion level cost tens of KB of
// stack and the depth budget alone cannot prevent overflow.

Each recursion level is a small Cx frame. The depth budget then keeps evaluation inside even a 2 MiB test-thread stack. eval_inner (eval/mod.rs:491) routes each variant to eval_access, eval_arith, eval_compare, eval_logic, eval_string_op, eval_construct, eval_array_op, eval_type_op, or eval_math. The match is exhaustive, so new variants fail compilation until routed.

The semantics helpers are the heart of the JS parity. jsnum.rs implements to_number (jsnum.rs:13), display (jsnum.rs:33), number_to_string (jsnum.rs:61), and js_round (jsnum.rs:252).

// proa_ir/src/eval/jsnum.rs:252
// JS `Math.round`: half-up toward positive infinity.
pub fn js_round(x: f64) -> f64 {
    if !x.is_finite() || x.fract() == 0.0 {
        return x;
    }
    let f = x.floor();
    if x < f + 0.5 {
        f
    } else {
        f + 1.0
    }
}

The doc comment is explicit about why. floor(x + 0.5) misrounds values like 0.49999999999999994, because the addition itself rounds up to 1.0. The exact-midpoint version is correct.

number_to_string matches ECMAScript shortest-round-trip formatting and switches to exponent form outside [1e-6, 1e21). utf16_len, utf16_lt, utf16_slice, and utf16_at make string length and indexing match JS UTF-16 code units, not Rust chars. parse_int_10 and parse_float reimplement the JS leading-prefix parsing rules.

tofixed.rs reimplements Number.prototype.toFixed. The problem is subtle. ECMAScript picks the integer closest to x * 10^d, choosing the larger one on exact ties. Rust's format!("{:.d}") rounds ties to even, so it disagrees on exactly representable ties like 0.125. The fix expands the double to its exact decimal digits and rounds half-up on the digit string. MAX_FRACTION_DIGITS is 100 (tofixed.rs:16). EXACT_PRECISION is 1100 (tofixed.rs:21), which exceeds the longest possible exact expansion of an f64 fraction.

date.rs formats epoch milliseconds in UTC. format_date (date.rs:19) supports tokens YYYY, YY, MM, M, DD, D, HH, H, mm, m, ss, s, and SSS. MAX_TIME_MS is 8.64e15 (date.rs:11). Out-of-range input yields "Invalid Date" like JS. The day-to-date conversion uses Howard Hinnant's civil_from_days algorithm (date.rs:62).

Add is special. js_add (eval/mod.rs:263) follows JS +: string concatenation if either operand is a string, numeric addition otherwise. strict_eq (eval/mod.rs:292) errors on arrays and objects, because JS compares them by reference identity and server values have no identity. prop_access (eval/mod.rs:345) is null-propagating: Null bases and missing properties yield Null. Duplicate object keys resolve to the last entry.

Server Dialect Validation

validate_server_dialect (proa_ir/src/dialect.rs:71) rejects client-only nodes before a program runs.

// proa_ir/src/dialect.rs:71
pub fn validate_server_dialect(expr: &Expr) -> Result<(), Vec<DialectError>> {
    validate_server_dialect_bounded(expr, usize::MAX)
}

The bounded variant stops collecting once the budget is full. DialectErrorReason (dialect.rs:23) is ClientOnly, Impure, or Unsupported. Now is Impure, because server renders must be deterministic. ParseDate is Unsupported. Everything else rejected is ClientOnly.

DialectError (dialect.rs:34) carries the offending variant name, a dot path into the tree, and the reason. The path points at the exact subexpression. An error like client-only expression Signal at cond.left.items[2]`` tells an authoring tool precisely where to look. The walker collects every offending node, not just the first, so a whole slot can be fixed in one round trip.

Stmt is not reachable from Expr, so no statement-level walk is needed. Expressions are pure.

The Builder API

The builder modules (proa_ir/src/builder/mod.rs:8) provide a fluent API for constructing IR by hand. This is the ergonomic path for tooling and tests. ExprBuilder (builder/expr.rs:16) wraps an Expr with chainable methods for every family: lit, signal, field, var, scope, scope_path, prop, index, arithmetic, comparison, logic, then_else, or_else, string and array operations, type checks, conversion, math, and validation helpers.

// proa_ir/src/builder/expr.rs:609
let expr = ExprBuilder::field("email")
    .len()
    .gt(0)
    .and(ExprBuilder::field("email").is_email())
    .build();

FormBuilder (builder/form.rs:18) builds a FormIR. signal, signal_persisted, field, field_with_rules, derived, derived_from, effect, and effect_when add members. on_input, on_change, on_blur, on_click, on_submit, and on_signal_change are shortcuts for effects. FieldBuilder (builder/form.rs:213) configures one field with validation, transforms, format masks, and disabled or readonly conditions. BlockBuilder (builder/form.rs:358) builds statement blocks. The block() and form() free functions are the entry points.

// proa_ir/src/builder/form.rs:555
let form = form("signup")
    .signal("loading", false)
    .field("email", |f| {
        f.required("Email is required").email("Invalid email").trim()
    })
    .field("password", |f| {
        f.required("Password is required").min_length(8, "At least 8 characters")
    })
    .derived_from("is_valid", ExprBuilder::form_valid)
    .on_submit(block().set("loading", true).build())
    .disable_submit_when_invalid()
    .build();

Code Generation

The codegen module (proa_ir/src/codegen/mod.rs) has two generations. The legacy JsCodegen (codegen/js.rs:17) compiles a FormIR to one self-contained IIFE. The newer split codegen separates a shared runtime from a tiny per-form config.

// proa_ir/src/codegen/mod.rs:38
// Legacy full codegen (includes everything inline)
pub use js::{expr_to_js, JsCodegen};

// New split codegen
pub use form::{FormCodegen, FormCodegenConfig};
pub use runtime::{
    generate_runtime, generate_runtime_minified, runtime_url, DEFAULT_CDN_URL, RUNTIME_VERSION,
};

JsCodegen emits an IIFE with $id, $s for signals, $f for fields, $e for errors, $t for touched state, $v for validators, and inline helper functions. Its emit_expr maps every Expr variant to a JavaScript expression. Signal becomes $s.name. Field becomes $f.name. Scope becomes $scope["segment"]. FieldHasError becomes $e.name !== null.
