02 -- The write path: claim_log_slot and one CAS versus on_event and the output gate

A push into walgit and a write into a celld cell both end in the bucket, but the order of operations is inverted.

walgit's push writes the durable objects first, then publishes them with one compare-and-swap (CAS). The first step claims a place in the log. A fresh nonce makes each attempt distinguishable, and a slot whose claimant died is burned so the sequence stays contiguous.

The write commits into the cell's own SQLite database (the embedded SQL database engine) before any bucket request. Then the output gate intercepts the response. It re-checks authority at release time, so a handler that started under a live lease cannot release after that lease expired.

%%{init: {"flowchart": {"htmlLabels": false}}}%% flowchart LR H["request event"] --> I["on_event"] I --> J["handler commits to SQLite"] J --> K["output gate holds the response"] K --> L["AwaitDurable effect"] L --> M["replicator proves durable"] M --> N["DurableReached"] N --> O["release the response"]

The acknowledgements certify opposite things. walgit's client sees ok only after the bucket accepts the manifest CAS: the acknowledgement says "the world can see this". celld's client sees ok only after a durability proof covers the write: the acknowledgement says "a crash cannot lose this". The two orderings are a consequence of the unit of state: walgit must publish before anyone can read, so publish is the ack; celld already holds the write locally, so the ack is about survival, not visibility. That difference is what the fencing document explains, and what the durability document measures.

The Aha Moment

Aha: walgit publishes into the shared log first and acknowledges on the CAS — "the world can see it". celld commits into a private SQLite first and acknowledges on the proof — "a crash cannot lose it". The two acknowledgements certify opposite things.
