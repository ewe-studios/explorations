Project Exploration: Lunora, a Cloudflare backend where the Durable Object is the database

Overview

Lunora is a type-safe, real-time backend for your own Cloudflare account. A Durable Object (a single-threaded Cloudflare object with its own SQLite storage) is the database. The same object holds the WebSocket connections of the clients that read the data. So the writer is also the broadcaster.

Lunora is alpha software. Its license is FSL-1.1-Apache-2.0. The central class ShardDO has 18,454 lines. See Overview.

flowchart LR C["Client"] --> W["Worker: gate, route, batch"] W --> S["ShardDO: one SQLite database, one writer, sockets"] W --> REG["ShardRegistryDO"] S --> CDC["__cdc_log"] CDC --> R2["R2: cdc segments"] S --> D1["D1 or Hyperdrive: global tables"] S --> Q["Queues, Workflows, Scheduler"]

Cloudflare services used

Durable Objects (with SQLite and WebSocket hibernation), Workers, D1, Hyperdrive, R2, KV, Queues, Workflows, Cron Triggers, Analytics Engine, Pipelines with R2 SQL, Vectorize, Workers AI with AI Gateway, and service bindings. The page Cloudflare services has one section for each.

Sharding in one minute

The shard is a Durable Object chosen by name. A table marked .shardBy(field) lives in the object named by that field value. Other tables live in the root shard __root__. A single ShardRegistryDO lists the shards for fan-out. The caller supplies the shard key, and I found no server check that it matches the row. There is no resharding, only a manual export and import. See Sharding design.

Change log and archive

Every shard keeps __cdc_log with a sequence number (_commitSeq) and an epoch. A sweep copies old rows into R2 as cdc/{shard}/{epoch}/{16-digit last seq}.json, advances a watermark, and only then deletes. A restore is detected as a timeline fork. See Change log and Storage tiers.

The five most important tricks

  1. Archive first, destroy second, with a watermark in SQLite and the epoch in the R2 prefix.
  2. A gate wrapper that never rejects, because a rejection from blockConcurrencyWhile resets the object.
  3. A schedule outbox written inside the transaction, so a crash cannot lose a deferred job.
  4. Fork detection with outside witnesses (consumer, replica, archive), because SQLite cannot report a restore.
  5. Range-gated invalidation with a per-flush diff cache for realtime fan-out.

Verdict

Strong core idea, careful handling of Cloudflare edge cases. The weak points sit outside one object: caller-chosen shard keys, no resharding, single registry and scheduler objects, a log archive ceiling of about 166 changes per second per shard, and write amplification from the default request log. Aha: the best parts (gate, outbox, archive) all come from treating the platform's failure modes as first-class. See Critical assessment.

Differences between code and docs

  • The code has 59 packages. AGENTS.md says 58.
  • The docs say routing is by schema. In the code the client passes shardKey.
  • The docs say actions run in the Worker. In the code they run on the shard.
  • Analytics Engine blob size is 5,120 bytes in the code. A doc says 16 KB.
